# CLAUDE.md

Указания для Claude Code (и любого другого агента) при работе с этим репозиторием.

## О проекте

**DendroLog** — десктопный просмотрщик логов на Qt 6 / C++17 (Windows и Linux).
Вкладки на несколько файлов со слиянием по времени, извлечение полей по схемам,
фильтрация, подсветка, таймлайн, статистика, сканер каталога, дочитывание
растущих файлов и чтение stdin; с 0.6 — закладки, память файла, сессии,
история переходов и однобайтные кодировки. Версия — единственный источник правды в
`project(VERSION)` в `CMakeLists.txt`, оттуда приходит define `DENDROLOG_VERSION`.

## Сборка и запуск

```sh
cmake -S . -B build                                       # конфигурация
cmake --build build --config Release --target DendroLog   # сборка
```

Результат: `build/Release/DendroLog.exe`. Локально используется Qt 6.8.3
(`msvc2022_64`), генератор «Visual Studio 17 2022». `project_configure.bat`
находит Qt сам (`scripts/find-qt.ps1`); для нестандартной установки задать
`QT_PATH` или `CMAKE_PREFIX_PATH`.

Важное про локальный `build/`:

- там остались **устаревшие артефакты** до переименования проекта —
  `build/LogViewer.vcxproj` и `build/Release/LogViewer.exe`. Не собирать цель
  `LogViewer`, не запускать этот exe: у него нет define версии и он не
  соответствует текущему коду. Собирать только `--target DendroLog`;
- вывод MSBuild **локализован на русский** — не искать в нём `error` или
  `Build succeeded`, ориентироваться на код возврата;
- рядом с exe лежит `DendroLog.ini`, поэтому dev-сборка работает в
  **portable-режиме** (`AppSettings::configDir()` возвращает каталог exe, если
  там есть ini или файл-маркер `portable`). Настройки пользователя в
  `%LOCALAPPDATA%` при этом не трогаются. Схемы полей лежат в
  `<configDir>/patterns/*.json`.

Аргументы командной строки: `DendroLog.exe file1 file2 …`, `--new-instance`
(принудительно отдельное окно), `-` / `--stdin` (читать поток), `--encoding
<имя>` (кодировка файлов и потока как выбор пользователя; разбор —
`OpenRouting::parseCommandLine`). По умолчанию
работает один экземпляр на пользователя: повторный запуск передаёт файлы (и
`--encoding`) в первичное окно. Правило «кто первичный» — одно, в
`SingleInstance` (Q-20): окно `--new-instance` и `-` ключ не занимает и чужих
файлов не принимает (пайп передать нельзя, поэтому при `-` всегда своё окно),
обычный запуск рядом с ним сам становится первичным; одновременные запуски
занимают ключ по очереди (`QLockFile`). Первичное окно — то, что держит ключ
(`SingleInstance::isPrimary`): только оно восстанавливает и пишет прошлый
сеанс (`last-session.json`). Путь-каталог (в командной строке, от второго
экземпляра, брошенный в окно) открывается в Directory Scanner, файл
`*.dlsession` — как сессия (вкладки добавляются к открытым) — правило в
`OpenRouting::plan`.

### Облачная сессия (Linux)

Qt 6.8 в `/opt/qt6` ставит setup script окружения (из conda-forge: в apt
только 6.4, а проекту нужен 6.5+; `download.qt.io` закрыт сетевой политикой).

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH=/opt/qt6
cmake --build build --parallel
ctest --test-dir build --output-on-failure -j$(nproc)
```

Полная сборка — около минуты на 4 ядрах, тесты с `-j4` — меньше двух минут (~105 с;
последовательно ~6 минут; дольше всех `logstore_equivalence`, ~50 с). Окна нет:
тесты сами ставят `QT_QPA_PLATFORM=offscreen`, приложение запускать с этой
переменной. Если `/opt/qt6` нет, setup script не отработал — сказать об этом
автору; Qt из apt не подойдёт. Windows-сборку и установщики даёт только CI
(артефакты запуска на каждый пуш в `main`).

`logstore_equivalence` — главный страховочный трос хранилища: эталон
поведения индексного бэкенда не написан прозой, им СЛУЖИТ резидентный. Тест
грузит одни и те же файлы обоими путями, прогоняет 36 конфигураций фильтров (с фильтром по файлу)
(включая рандомизированные по фиксированному seed) и сравнивает весь API
`LogStore` построчно. Мульти-файловая вкладка проверяется в двух сценариях
подключения: файл дописан в открытую вкладку и файлы открыты разом (все
подключены до первого батча). Известные и намеренные расхождения там не
замалчиваются, а закреплены отдельными проверками, которые упадут при их
изменении. Слияние файлов из разных часовых поясов сверяется не между
бэкендами, а с заранее заданным порядком: общую ошибку классификатора
сравнение бэкендов не увидит. То же с номерами физических строк: на них стоит
идентификатор строки (R-1), эталон — разбиение байтов файла
(`testdocs::expectedPhysicalLines`). Ключ строки сверяется по строкам, а не по
рядам: так он проверяется и на одно-файловой вкладке «не по порядку». Прогон
занимает ~47 с; поэтапный тайминг он печатает сам. Модели здесь без view, и
конец фильтра ждётся по `isFiltering()` без окна тишины `settle()` (P-10: окно
по 80 мс на каждое из ~1200 применений стоило 115 с).

`logview_state` — страховочный трос представления. Инвариант один («текущая
запись и позиция вьюпорта переживают изменение видимого набора»), а путей,
которые его нарушают, много, поэтому проверка табличная: инварианты × 12
триггеров (уровни, время, текст, маркеры, закладки, колонки, добавление файла) × три
пути хранилища × позиции. Новый путь, добавленный мимо общего механизма
восстановления, падает здесь сразу. Прогон ~37 с: после каждого действия
тест ждёт покоя по состоянию (`settleViews` / `idleViews`), а не паузу
(P-6; было ~155 с паузами `pump` и окнами `settle`).

`lineindex_smoke` среди прочего проверяет цену скана `SequentialLineReader`:
число перечитываний окна вперёд, назад и с «дрожанием» обязано оставаться
ограниченным, а не расти по строке на промах.

У `lineindex_smoke` есть режимы профилирования: `--bench <file> [schema]`,
`--bench-resident <file> [schema]` (резидентный `LogParser` без модели; схема
у обоих — `jsonl` / `logfmt` для ключевой схемы с ключами по умолчанию, путь к
файлу схемы или сама строка, с ней включено извлечение полей; файлы —
`scripts/generate_test_log.py --format jsonl|logfmt [--epoch] [--numeric-levels]`) и
`--bench-stages <file> [encoding]` (ступенчатая атрибуция I/O → декод → timestamp → level,
плюс стадия 4 — декод + level без timestamp, цена классификации уровня отдельно,
стадия 5 — декод + `detectTimestampMs` с опорной датой файла, горячий путь
индексатора без построения `QDateTime`, и стадия 6 — декодирование выбранной
кодировкой `TextDecoder` против `fromUtf8` стадии 1; кодировка — именем или
автоопределением по первой не-ASCII строке).

### Санитайзеры

Опция CMake `DENDROLOG_SANITIZER` (GCC/Clang): `address` — ASan + UBSan,
`thread` — TSan. Отдельный каталог сборки на каждый вариант; обычная сборка
флагов не получает.

```sh
cmake -S . -B build-asan -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_PREFIX_PATH=/opt/qt6 -DDENDROLOG_SANITIZER=address
cmake --build build-asan --parallel && ctest --test-dir build-asan --output-on-failure -j$(nproc)
```

Для TSan — то же с `build-tsan` и `thread`. Запускать через `ctest`: опции
рантайма, подавления и увеличенные таймауты он берёт из `tests/CMakeLists.txt`
(тест напрямую — с `TSAN_OPTIONS=suppressions=tests/sanitizers/tsan.supp`).
Прогон с `-j`: на CI (4 ядра) шаг Test — ASan около 3,5 минуты, TSan около 5
минут; локально рядом с другой нагрузкой — дольше (ASan ~5 минут). В CI — отдельный workflow
`.github/workflows/sanitizers.yml` (пуш в `main` и вручную); его красный
статус не блокирует сборку установщиков, но чинить его нужно так же.

- Подавления — `tests/sanitizers/{lsan,ubsan,tsan}.supp`, у каждой записи
  комментарий, почему это не наш дефект. **Находки в `src/` и `tests/` не
  подавлять**: исправить или записать задачей в `docs/roadmap.md`.
- Qt не инструментирован, и TSan не видит его мьютексов: передача данных через
  queued-сигнал, `QThreadPool` и `QFuture` выглядела бы гонкой. Об этих
  передачах ему сообщает `tests/sanitizers/tsan_qt_sync.cpp` (обёртки линкера
  `--wrap` над вызовами в Qt, список символов — в корневом `CMakeLists.txt`).
  Новый способ передать данные между потоками (например, queued
  `QMetaObject::invokeMethod` из воркера) даст ложные отчёты, пока его нет в
  этом слое, — дополнять слой, а не файл подавлений.
- Счётчик ссылок контейнеров Qt TSan тоже видит не сам. Шаблон «воркер читал
  свою копию `QList`/`QVector` и отпустил её, GUI-поток дописал в оригинал на
  месте» верен (так живут все снапшоты резидентного хранилища), но Qt читает
  счётчик relaxed, и TSan считал такую запись гонкой — нестабильно, по воле
  планировщика. `tests/sanitizers/tsan_qt_refcount.h` (подключается `-include`
  во все единицы трансляции TSan-сборки) объявляет это чтение acquire-чтением,
  и ребро «отпустил копию → пишу на месте» TSan получает от самого счётчика.
  В новом коде и тестах этот шаблон обходить не нужно.
- Чего счётчик НЕ упорядочивает: копию отпускает не тот поток, который читал.
  Так делает `QtConcurrent::mapped`/`filtered` по временной последовательности
  — её читают все потоки ядра, а освобождает один, последний, до
  `reportFinished`. Поэтому в `mapped`/`filtered` передавать итераторы по
  неизменяемому списку в `shared_ptr`, который держит и сам функтор (образец —
  `DirectoryScanner::startContentSearch`): функтор умирает вместе с ядром,
  после `reportFinished`, где слой уже свёл потоки ядра. И в любом случае
  буфер, отданный воркерам без ожидания их завершения, не переписывать —
  строить новый.
- Счётчики ссылок `QFuture` (`derefT` и `~QFutureInterfaceBase`, где
  последний владелец удаляет разделяемое состояние) слой упорядочивает ТОЧНО:
  ключ — указатель `d` конкретного будущего (поле открыто штатным для тестов
  Qt макросом `QFUTURE_TEST`, смещения не угадываются). Деструкторы копий
  одного `d` взаимно исключены невидимой для TSan спин-блокировкой, а ребро
  TSan — acquire/release на самом `d` до вызова настоящего деструктора.
  Несвязанные `QFuture` друг друга не упорядочивают; прежний общий мьютекс на
  все деструкторы прятал гонки между их потоками. Перемещённая копия
  (`d == nullptr`) рёбер не получает: ребро по адресу 0 связало бы все потоки.
  Грубыми остались ключи очереди событий, пула и `report*`/`wait*` у `QFuture`.
- `tests/tsan_canary` (только при TSan) проверяет сами прослойки, режимы
  парами «без отчётов / отчёт обязателен»: `clean` / `race` — слой передач,
  `cow` / `cow-race` — счётчик ссылок контейнеров, `future` / `future-race` —
  ребро деструктора `QFuture` (последний по результатам и последний по `d` —
  разные потоки; два несвязанных `QFuture` и настоящая гонка между их
  потоками), `thread` / `thread-race` — ребро «последний emit своего `QThread`
  (`StdinSpooler`) → `QThread::wait`» (запись до него упорядочена, после —
  нет). Режимы `*race` засчитывают отчёт по АДРЕСУ своих данных (хук
  рантайма `__tsan_on_report` + `__tsan_get_report_*`) и печатают
  «N report(s) on canary data»; от того, какой доступ TSan назвал первым,
  проверка не зависит. `*_blinded` — те же режимы с гоночными доступами под
  мьютексом (`DENDRO_CANARY_BLIND=1`): N обязано быть 0. Гоночные данные
  канарейки — на своей кэш-линии: флаг ожидания в том же 8-байтовом слове
  вытесняет из теневой ячейки TSan запись о гоночном доступе, и гонка
  пропадает. Упал любой `*race` — прослойка ослепила TSan, зелёным остальным
  тестам верить нельзя.
- Тест, который ждёт «тишины» по таймеру, под санитайзером ненадёжен: ждать
  состояние (`testdocs::settle` смотрит `isFiltering()`), а не время.

## С чего начать чтение

Порядок, в котором код складывается в голове быстрее всего:

1. `src/logentry.h` — что такое «строка лога» и как записи упорядочены
   (`operator<`: по времени, затем файл, запись, номер строки; строки без
   метки — в конец). Весь порядок в приложении — зеркало этого компаратора.
2. `src/logstore.h` — шов хранилища: весь доступ к данным идёт через этот
   интерфейс, у него две реализации.
3. `src/logmodel.h` — фасад модели поверх шва, настройки фильтров и роли.
4. `src/logviewwidget.h` — вкладка: модель + view + загрузка файлов и
   дочитывание. Самый полезный файл, чтобы понять жизненный цикл документа.
5. `src/LogListView.h` — представление с собственной геометрией и отрисовкой.
6. `src/mainwindow.h` — окно, доки, панели, глобальные действия.

У большинства модулей в начале заголовка есть блок-комментарий с описанием
и ловушками — он точнее этого файла и обновляется вместе с кодом.

## Архитектура

Исходники собираются в четыре цели, каждый файл — ровно в одну; новые `.cpp`/`.h`
нужно **явно добавлять в нужный список** в `CMakeLists.txt`, глоба нет. Пятая
цель — сторонний `miniz` (`third_party/miniz/`, статическая, приватно у
`dendrolog_core`; версия, URL и SHA-256 — в её `README.md`; чужой код не
правится, предупреждения гасятся флагами цели):

| Список | Цель | Что туда входит |
| --- | --- | --- |
| `DENDROLOG_CORE_SOURCES` | `dendrolog_core` (static) | данные, разбор, хранилище, модель, экспорт. **Без Qt Widgets** — зависеть от `appsettings`/`apptheme` и виджетов ядру нельзя |
| `DENDROLOG_WIDGETS_SOURCES` | `dendrolog_widgets` (static) | `LogListView`, вкладка `LogViewWidget`, тема, настройки, сканер каталога, панели (Text Filters, Row Highlighters, Entry Details, Statistics), стартовый экран, каталог и редактор схем, общие элементы UI — то, что нужно тестам из виджетов |
| `DENDROLOG_APP_SOURCES` | `dendrolog_app` (static) | оболочка: `MainWindow` (с `.ui`), вкладки (`LogTabWidget`, `LogTabBar`), Settings (с `.ui`), панель Search, таймлайн, `SingleInstance`, `UpdateChecker`, нейро-подсказчик и окно «Find a Schema» (`AiSchemaClient`, `SecretStore`, `SchemaCandidates`, `SchemaCandidatesWindow`, `AiConsentDialog`). Отдельно от `dendrolog_widgets` из-за Qt Network; линкует её тест окна `tests/mainwindow_smoke` |
| `PROJECT_SOURCES` | `DendroLog` (exe) | только `main.cpp` и ресурсы (`.qrc`, на Windows `.rc`) |

Тесты линкуются с библиотеками и сами исходники приложения не компилируют.
Новый класс оболочки — в `DENDROLOG_APP_SOURCES`, а не в exe: тогда его видит
оконный тест. Ресурсы (`.qrc`) остаются в exe: в статической библиотеке их
инициализатор выбросил бы линкер (исключение — `resources/ai/ai.qrc` в ядре: системный текст подсказчика, его держит `Q_INIT_RESOURCE(ai)` в `schemaproposal.cpp`); тест, которому нужны иконки и справка,
добавляет `resources/resources.qrc` в свои исходники сам (`theme_mode`,
`mainwindow_smoke`).

Швы для теста окна (программа их не вызывает, поведение для пользователя то
же): `AppSettings::overrideConfigDirForTesting` — все данные (ini, схемы,
память файлов, `last-session.json`) во временном каталоге;
`AppSettings::spoolRoot` — при подмене каталога настроек временные файлы распаковки в `<configDir>/spool`; `UpdateChecker::disableNetworkForTesting` — проверка обновлений без сети
отвечает `checkFailed`; `StdinSpooler::setInputDescriptorForTesting` — спулер stdin читает
пайп теста вместо дескриптора 0; ключ `SingleInstance` — параметр, у теста свой;
связь окна с ним — `MainWindow::attachSingleInstance` (из `main.cpp`), чтобы
путь второго экземпляра проходил тест. Действия с сочетаниями несут свойство
`commandId` — имя команды `ShortcutManager`, по нему тест их и находит.

**Хранение записей.** `LogStore` (`src/logstore.h`) — интерфейс доступа к
записям за фасадом `LogModel`, два бэкенда:

- `ResidentLogStore` — весь текст в памяти, путь по умолчанию;
- `IndexedLogStore` — блочный индекс строк (`LineIndex`, `LogIndexer`) + чтение
  текста с диска по требованию (`TextChunkCache` — 4 МБ чанки LRU на GUI-потоке,
  `SequentialLineReader` — для воркеров).

**Кодировка — на файл** (F-1, `docs/design/F-1.md`).
`FileEncoding` (декодер + источник: не решено / авто / BOM / пользователь,
сила решения автоматики и её свидетельство) живёт на файл: у индексной
вкладки — в `IndexedLogStore`, который копией отдаёт `TextDecoder` всем
читателям текста (слот `TextChunkCache`, снапшоты, фильтр-воркер, поисковая
база); у резидентной — в `LogViewWidget::m_fileEncodings`, парсер
(`ByteLineReader` — сырые байты строки и её точная позиция в файле; UTF-16/32
— `QTextStream`) декодирует не-ASCII строки сам. «Кодировки вкладки» нет: слитая вкладка читает каждый файл своим
декодером. Правило определения одно — `EncodingDetector::advance`, его зовут
индексатор (на каждый 8-МБ буфер) и парсер (на не-ASCII строку, пока решение
не окончательное), поэтому бэкенды решают одинаково по построению: пока в
файле только ASCII — «не решено» (переживает дозапись); первый байт ≥ 0x80 —
`decide` по окну 64 КБ от него, сигнал `encodingDecided` ДО порции с этой
строкой, стор/вкладка берут его без reset (прежние строки — ASCII). Решение
по малому свидетельству (меньше `kFinalHighBytes` = 256 байтов ≥ 0x80) —
**предварительное** (шаг 3а): `advance` копит свидетельство (байты ≥ 0x80
по порядку файла, промежутки ASCII сжаты до `'\n'` — от порций не зависит) по
следующим порциям и дописанному хвосту и, если ответ изменился, сообщает
пересмотр; набралось 256 — окончательное, больше не проверяется. BOM и выбор
пользователя окончательны всегда; выбор хранит решение автоматики рядом
(`FileEncoding::automatic()` — для «Определить автоматически»). Пересмотр и
ручная смена идут одним путём: индексная — `IndexedLogStore::
setFileEncoding`/`adoptDetectedEncoding` → `rereadWithNewDecoder` (без
переиндексации: индекс от кодировки не зависит, классификатор смотрит только
на ASCII; reset, при текстовых правилах — перефильтрация), резидентная —
`startReencode` (разбор в сторону, `replaceEntriesForFile` под одним reset;
отметки «новых» строк переходят к перечитанным записям). Позицию возвращает
якорь view. Переход порога в обе стороны и дозапись несут всё состояние,
включая свидетельство. Под выбором пользователя автоматика продолжает решать
РЯДОМ (`advance` над `automatic()`, декодер остаётся выбранным;
индексатор и парсер смотрят `detectionSettled`, а не `settled`), поэтому
«Detect automatically» (`LogViewWidget::restoreAutomaticEncoding`) возвращает
настоящее решение и после `--encoding`. Интерфейс (шаг 4): индикатор
`EncodingIndicator` в строке статуса — файл текущей строки, меню →
`LogViewWidget::setFileEncoding`; начальное состояние файла —
`addLogFile(path, FileEncoding)` (`--encoding`, объединение вкладок —
`addFilesFrom`); смена декодера переписывает фрагменты закладок и истории
по видимым строкам (`refreshTextFragments`). Запасная кодировка — настройка
`AppSettings::fallbackEncoding` (умолчание — по локали,
`TextEncodings::systemFallback`); вкладка берёт её сама и на смену
пересматривает предварительные решения (`EncodingDetector::reconsider`).
Фильтр сканера по содержимому (шаг 5) — то же правило в
`FileContentSearch::search` (ядро): BOM, иначе `advance` на каждый блок
чтения и `TextDecoder`; находка в не-ASCII строке под предварительным
решением предварительная — строки запоминаются и при пересмотре проверяются
новым декодером, ответ — как у файла, прочитанного итоговой кодировкой.
Запасная — значением (`DirectoryScanner::setFallbackEncoding`, её передаёт
панель); смена перепроверяет только файлы, решённые в однобайтную.

**ANSI-последовательности снимаются там же, где байты становятся текстом**
(F-3, `docs/design/F-3.md`): `TextDecoder::decode` снимает их из байтов
строки до декодирования (`AnsiEscape`, строка без ESC — один `memchr`), а
пути мимо декодера зовут ту же грамматику сами — ASCII-строка и UTF-16/32
резидентного парсера, `analyzeFileForStats`, широкая ветка
`FileContentSearch`. Текст строки нигде не содержит кодов: классификатор,
фильтры, поиск, поля, экспорт видят одно и то же на обоих бэкендах; файл и
индекс (сырые смещения) не меняются. Отпечаток строки (R-1) коды не учитывает
ни в тексте, ни в байтах. Цвет SGR — только для отрисовки: резидентный
парсер кладёт спаны в запись (`LogEntry::ansiStyles`, только у строк с
ESC), индексный читает сырые байты строки по требованию
(`TextChunkCache::lineAnsiStyles`); роль `LogModel::AnsiStyleRole` (только
при показе сырого текста строки) → `SyntaxHighlighter::withAnsi` в
`LogListView` по настройке `[View] ansiColors`, палитра — `AppTheme::ansiColor`.

Бэкенд выбирается в `LogViewWidget::addLogFile` по размеру файла и настройке
`AppSettings::indexedThresholdBytes()` (по умолчанию 512 МБ, `0` = всегда
индексный). **Один бэкенд на вкладку**: большой файл конвертирует вкладку целиком
и все её файлы перечитываются через индексатор; UTF-16 уходит обратно в
резидентный путь. Растущий файл, перешагнувший порог, конвертируется на лету.

**Ключ строки** (`RecordKey`, `src/recordid.h`, R-1) — файл, номер физической
строки, id записи, метка: полный ключ сортировки `LogEntry::operator<`.
`LogStore::keyAt(row)` / `rowForKey(key)` / `nearestRowForKey(key)` (прокси в
`LogModel`) — O(log N) на обоих бэкендах: резидентный — `lower_bound` по
компаратору «запись против ключа», зеркалу `operator<`; индексный — O(1) в
тождественном режиме, иначе `lower_bound` по `rowLess` (`visiblePlace`, на нём
же `nearestVisibleRowForLine` и место скрытой записи). Ключ действителен, пока
строка лежит с тем же id записи и меткой; «ближайшая видимая» — одна семантика
по всему хранилищу: видна — она, скрыта — следующая за её местом, за концом —
последняя. Номера строк двух бэкендов совпадают и равны разбиению файла по
`'\n'` (пустая последняя строка — строка): резидентный парсер читает **без**
`QIODevice::Text`.

Сохраняемый идентификатор (шаг 2, `docs/design/R-1.md`, «Сделано → PR 2»):
`SourceIdentity` (тот ли файл и цел ли прочитанный префикс — два чтения по
4 КБ) + `RecordId` (номер строки + отпечаток текста). Отпечаток строки — по
**ASCII-скелету** (серия символов ≥ U+0080 — один заполнитель): одинаков на
обоих бэкендах, в любой кодировке файла и по сырым байтам
(`RecordFingerprint::ofLineBytes`, без декодера); строки, различающиеся только
не-ASCII текстом, неразличимы — первая защита номер строки и источник. В
горячем пути загрузки не считается. Оборванный хвост с одиночным `'\r'`
оба пути показывают без него (`LineIndex::kEolProvisionalCr`: `'\r'` не
текст, но смещения точны); у недописанной строки отпечатка нет
(`RecordId::hasText`).

Разрешение (шаг 3, `docs/design/R-1.md`, «Сделано → PR 3») — `RecordLocator`
модели. Сохранённый идентификатор ждёт файл со своим путём; источник
проверяется раз на поколение строк файла, когда пришла первая порция (файл
уже читается или прочитан — сразу; строки сброшены — ждёт новых). Строка
ищется в порциях: ожидающие файла лежат по номеру строки, порция — O(log K +
найденные), сама порция не просматривается (инвариант 3,
`stats().examined`). Резидентная порция — в ПОРЯДКЕ ФАЙЛА (до сортировки по
времени: строки без метки уходят в конец), текст сверяется сразу; индексный
диапазон — после `appendIndexedRows`, отпечаток сырых байтов считается в
фоне. Конец прохода (`fileLoaded`) — ненайденные `LineAbsent`, идентичность
источника по концу прочитанного (`sourceFor`), недописанная строка, ставшая
полной, — `completed`. Запрос после того, как строка прошла, — поздний
проход (индексный — O(K), резидентный — один линейный проход). Закладки и
история переходов после сброса строк файла ищут свои строки через
`reacquire` — источник не проверяется, решают номер и отпечаток (строка того
же номера и текста в переписанном файле — та же строка), видимость роли не
играет. Пока идёт фоновая сверка, вкладка `isLoading()`.

Потоки (F-7) — файлы спула `<n>-stream-<имя>.log` в каталоге экземпляра
`SpoolDir` (их узнаёт `SpoolDir::isStreamFile`, источник `Stream`, идентичность
Ephemeral: ни недавних, ни памяти, ни сессий): `StdinSpooler` спулит stdin,
`CommandSpooler` — вывод команды. Вкладка открывает спул `addStream` растущим
логом (auto-reload + follow-tail); спулер команды принадлежит вкладке
(`addCommandOutput`), закрытие вкладки — `release()`: процесс завершается,
спул удаляется. Пинок спулера, пришедший посреди дочитывания, вкладка
повторяет по его концу (`onStreamGrew`). `FileChangeDetector` держит
якоря дочитывания в **сырых байтовых смещениях**.

**Разбор.** `LogPattern` (схемы извлечения полей, каскад «полный regex →
префиксные варианты → re-sync варианты» с литеральными пре-фильтрами),
`PatternHeuristics` (автоопределение схемы по строке), `SchemaStore`
(`patterns/*.json`), `LineClassifier` (уровень и timestamp в горячем пути
индексации, без построения `QDateTime`), `LogParser`.

Поля строки — функция «текст строки, схема» за интерфейсом `FieldExtractor`
(F-17, шаг 2, `src/fieldextractor.h`): `TemplateExtractor` — шаблон строки
(`src/linetemplate.h`, новый движок: одна строка вида
`{Timestamp:time} [{Thread}] {Level:level} {Message}`, разбор слева направо за
один проход, без регексов, у поля один вопрос — где оно кончается, и вид поля
есть ответ; шаблон с неопределённым концом поля не компилируется),
`KeyedExtractor` (`keyedline`), `LegacyPatternExtractor` (`LogPattern` до шага
9). С шага 3 F-17 поля в записях не хранятся: `FileSchema` держит извлекатель
(`FieldLayout::extractorFor`: шаблон строки версии 4 — `TemplateExtractor`,
иначе `LegacyPatternExtractor`), поля строки — `FileSchema::extract` через
`FieldSource` модели (показ, Entry Details, кэш) и `FieldScanner` (воркеры:
фильтр, Save View As, поиск). Загрузка до шага 7 ещё берёт `LogPattern`
схемы (граница записи, ключи ключевой схемы). Сканеры видов поля (`TokenScan`) —
общие: метка и слово уровня С ПОЗИЦИИ — `LineClassifier::timestampLengthAt` /
`levelLengthAt` (только форма; эталон — `PatternHeuristics::
timestampAtDetectPattern` и `levelDetectPattern` по позиции, закреплено в
`lineindex_smoke`). Встроенные схемы шаблонами — данные `resources/templates/`
(ещё не устанавливаются, шаг 9); перевод блочной схемы — `SchemaConverter::
fromBlocks`. Вывод шаблона по образцам (F-17, шаг 4) — `SchemaInference::infer`:
строки-кандидаты читаются «в лад» теми же сканерами `TokenScan`, элемент —
то, с чем согласны ≥ 95 % строк, необязательный участок — 15–95 %, поле
слов — до якоря следом, без якоря — «трудная граница» (padded, width,
words, of) или `Message` с заметкой; варианты (полный и осторожный)
компилируются всегда и судятся `SchemaFit`. Пока зовёт только тест (окно
подбора — шаг 5).

Словарь уровней («какое слово — какой уровень») записан один раз:
`kLevelWords` в `src/logentry.h`. Из него строятся регексы `PatternHeuristics`
(блок Level схемы и эталон `levelDetectPattern`), `StrToLevel` и подсветка
ключевых слов; `LineClassifier::detectLogLevel` повторяет его вручную ради
скорости. Регистр сворачивается только для ASCII. Новое слово — это таблица,
ручной сканер, заданное соответствие в `lineindex_smoke`
(`testLevelVocabulary`) и таблица в обеих справках.

Политика времени — одна на всё приложение и живёт только в
`LineClassifier`: метка без зоны — локальное время машины, явная зона (`Z`,
`±hh[:mm]` вплотную, `±hh[:]mm`/`UTC`/`GMT` через пробел, в пределах ±14:00)
задаёт точный момент, дробь любой длины усекается до миллисекунд. Текст строки
не меняется — зона влияет на момент (порядок, фильтр, таймлайн). Момент — мс
epoch, «метки нет» — только `kNoTimestampMs` (`logentry.h`, минимум `qint64`)
во всём хранилище: индекс, `LogEntryMeta`, `RecordKey`, статистика (F-13).
Отрицательный момент — метка до 1970 года, ровно эпоха — 0; проверять
`hasTimestampMs`, а не `>= 0`. Годы 0001–9999 разности не переполняют. Формы:
ISO и `yyyy/MM/dd` (nginx error) и access `dd/Mmm/yyyy:HH:mm:ss` — где угодно
в строке (самая левая); фолбэк-формы `dd/MM/yyyy`, `MM/dd/yyyy`, `dd.MM.yyyy`
и syslog `Mmm dd HH:mm:ss` — только с позиции 0, и метка на позиции 0
главнее. Месяцы — английские сокращения, регистр сворачивается для ASCII.
У syslog нет года: метка получает последний год, в котором её день не позже
опорной даты + 1 день; опорная дата — mtime файла
(`LineClassifier::yearReferenceForFile`), её на каждый проход (и на каждую
дозапись) берут `LogParser`, `LogIndexer` и `analyzeFileForStats` и только
передают классификатору; без неё — сегодня. Время без даты (F-11,
`docs/design/F-11.md`): `HH:mm:ss[.fff]` с позиции 0 или 1 за `[`, без зоны,
и только с контекстом файла (`ClockDates` — параметр `detectTimestamp[Ms]`;
без него — Go to, граница фильтра из текста — не метка). Дата — по
состоянию разбора: последняя такая строка — дата, при которой её момент
ближе всего к mtime (раньше mtime + 12 ч), к началу файла — минус сутки на
каждый шаг назад больше чем на час. Проход, встретив первую такую строку при
пустом состоянии, считает переходы до конца файла предпросмотром
(`LineClassifier::clockRunInFile`, голова строки без декодирования);
состояние (`ClockDateState`) после прохода лежит в `LogFile::clockState`, и
дозапись обоих бэкендов продолжает с него, проход с начала файла — заново;
сканер несёт его в `StatsResume` и вместо предпросмотра сдвигает From/To в
конце. Ручной сканер обязан совпадать с регексами `PatternHeuristics`
(`isoTimestampDetectPattern`, `accessTimestampDetectPattern`,
`syslogTimestampDetectPattern`, `clockTimestampDetectPattern`,
`timestampSuffixDetectPattern`), а
семантика — с заранее известными моментами: оба закреплены в
`lineindex_smoke`. Блок Timestamp схемы (`timestampRegex`) понимает те же
виды, включая зону access-лога внутри скобок. Значение ключа ключевой схемы
(F-4) читает тот же классификатор (`timestampFromValue`): строка — тем же
сканером, число или строка из цифр — эпоха, единица по величине (< 1e11 —
секунды, < 1e14 — мс, < 1e17 — мкс, иначе нс) или из схемы, момент вниз до
мс, только годы 0001–9999; времени без даты у значения нет. На загрузке
(F-4, PR 2) строку классифицирует одна функция —
`LineClassifier::classifyLine(keyedSchema, …)` у `LogParser`, `LogIndexer` и
`analyzeFileForStats`: ключевая схема (только при включённом извлечении
полей) — момент и уровень из ключей, ключа нет или значение не читается —
эвристика по строке; без ключевой схемы — только эвристика. Сканер каталога
схему не задаёт — его счётчики по эвристике, как у вкладки без схемы.

Граница записи — тоже одно правило, `LineClassifier::isPrimaryLine`, у
`LogParser`, `LogIndexer` и `analyzeFileForStats` (F-12,
`docs/design/F-12.md`): строка начинает запись, если её распознала схема
(только при включённом извлечении полей; ключевая — по правилу `keyedline`:
`{` / пара `key=value` с позиции 0 и ключ роли, регексная — `extractFields`),
ИЛИ у неё есть метка и слово
уровня, ИЛИ метка ВЕДУЩАЯ — с позиции 0, с позиции 1 за `[` либо access-форма
за `[` в строке без ведущего пробела/табуляции. Флаг ведущей метки отдаёт
`detectTimestamp[Ms]` (параметр `leading`), правило построчное, без
состояния — дозапись и порции индексатора его не несут. Метка в середине или
под отступом (тело JSON/SQL, текст исключения) записи не начинает. Эталон
флага — регекс-эквивалентность в `lineindex_smoke`, корпус границ —
`testRecordBoundariesBackends` там же.

**Модель.** `LogModel` — фасад над store. Фильтрация: `FilterRuleSet`
(Include/Exclude, AND/OR, AND связывает сильнее; на правило — свои
case-sensitive/regex; привязка правила к полю по **имени**, разрешается в
`bindFields()`; правило, чьей колонки нет в схеме, — нейтральное, как с
невалидным регексом, а не поиск по всей строке, `fieldMissing()`; правило
по полю решается на ЗАПИСИ — по полям её первой строки, решение действует на
все строки записи; правила по всей строке — построчные; поля — лениво через
`FieldRecordCursor`: предфильтр образца по строке, разбор до нужной колонки,
один на запись, F-17, шаг 3). До 100k записей резидентный фильтр считается синхронно (кроме правил по полю при схеме с `Background`-извлекателем — всегда джобом, инвариант 12), выше —
`QtConcurrent` по снапшоту с поколением и cancel-флагом; на индексном бэкенде
фильтр **всегда** асинхронный.

**Представление.** `LogListView` — собственная отрисовка (кэш pixmap строк,
префикс-суммы высот). Индексная вкладка включает `hugeRowMode` с первой строки
(резидентная — свыше 2 млн строк): только uniform-высоты, вся геометрия O(1),
плотные кэши не ведутся, wrap/toggle отключены.

С переносом строк высоты до первой отрисовки — ОЦЕНКИ по длине текста;
отрисовка уточняет их лениво, от первой видимой строки вниз. Поэтому всё,
что ставит прокрутку на строку (`scrollTo`, якоря при `setWordWrap`), сначала
уточняет высоты строки и тех, что окажутся над ней на экране
(`refineHeightsAbove`), и обновляет диапазон скроллбара; вид у самого низа
после отложенного пересчёта высот остаётся у низа. Пересчёт после resize
отложен на 150 мс и возвращает вид к якорю — первой видимой строке; пока он
ждёт, якорь снимается заново при каждой смене позиции (`captureResizeAnchor`),
иначе пересчёт отменил бы переход или фильтр, сделанные в этом окне.
Reset, оставивший модель пустой (конверсия вкладки в индексную), якорь не
теряет: ключ выбранной (или верхней) строки снят перед reset, и строка
ставится, когда придёт вставкой (`AwaitedAnchor`, один `rowForKey` на
вставку, пока ждём; частичные данные следующих reset его не заменяют; конец
загрузки без строки — `settleAwaitedAnchor`, к ближайшей видимой). Отложенное
восстановление после reset уступает всему, что поставило позицию позже
(`m_positionEpoch`). Проверяется строгими
`checkGeometry`/`checkKeyboard` в `logview_state` с переносом строк.

## Сквозные сценарии

Шесть путей, через которые проходит почти всё; по ним удобно искать место для
правки.

**Открытие файла.** Архив с набором файлов (zip, tar, `.tar.gz` — по имени или содержимому, `ArchiveFormats::detect`) вкладкой не открывается: окно отдаёт его в Directory Scanner (`SourceUnpacker::unpackArchive`), а член из каталога извлечения вкладка извлекает себе сама (`unpackArchiveMember`). Сжатый файл (`.gz` без tar внутри, по сигнатуре) сначала распаковывается во временную копию (`LogViewWidget::addArchive` → `SourceUnpacker`), дальше — как обычный по пути копии. `MainWindow::openRecentFile` (drag&drop, командная
строка и `SingleInstance` — через `openFilesFromCommandLine`, где
`OpenRouting::plan` отделяет файлы от папки для сканера) → выбор вкладки → `LogViewWidget::addLogFile` →
по размеру файла и `indexedThresholdBytes` выбирается бэкенд:

- резидентный: `LogParser::startParsing` → сигнал `entriesParsed` батчами →
  `handleEntriesParsed` сортирует батч и зовёт `LogModel::mergeEntries` —
  вставка сериями `beginInsertRows`, без reset;
- индексный: `IndexedLogStore::attachFile` + `LogIndexer::startIndexing` →
  `indexBatchReady` → `appendIndexedRows`.

`LogListView` узнаёт о новых строках из сигналов модели и пересчитывает
высоты и prefix-суммы. Схема полей при этом берётся текущая выбранная —
автоопределение живёт в редакторе схем, а не в пути загрузки.

**Фильтрация.** Кнопки уровней, доки Time Filter / Text Filters / Row
Highlighters и протяжка по таймлайну — все меняют настройки в `LogModel`
(`setLogLevelFilter`, `setTimeRangeFilter`, `setFilterRules`,
`setRowMarkers`) → `applyFilter()` → бэкенд пересобирает видимый список:
резидентный до 100k записей синхронно и с reset, выше — джобом в пуле;
индексный — всегда джобом. По завершении: `modelFiltered` → `LogViewWidget` →
`MainWindow::handleModelFiltered` (счётчики, кнопки-индикаторы). Search
Results сюда не привязан: `modelFiltered` приходит и после каждой дописанной
порции — за видимым набором следит `SearchResultsController` по сигналам
модели. `LogListView` на reset восстанавливает выделение и позицию по
якорю-записи — см. инвариант 10.

**Дочитывание хвоста.** Таймер авто-обновления или F5 →
`LogViewWidget::reloadChangedFiles` → `FileChangeDetector` по якорю решает:
дозапись (читаем с сохранённого смещения: `m_reloadParser` либо
`startIndexingFrom`) или файл переписан (полная перезагрузка,
`dropRowsForFile` + `startFullReload`). Переписан — значит не совпало начало
или 4 КБ перед концом прочитанного (те же области и хеш, что у
`SourceIdentity`: вид и закладки не расходятся), либо файл короче якоря.
Начало читается, только если сменились размер или mtime либо mtime свежее
3 с: проверка нетронутого файла — одно открытие и одно чтение 4 КБ. Новые строки помечаются «новыми»
(`IsNewRole`, зелёный маркер в жёлобе); пометка ставится ДО вставки строк,
чтобы `LogListView` на `rowsInserted` за O(1) посчитал батч в плашку
«↓ N new lines», если вид не у хвоста. Если растущий файл перешагнул порог,
вкладка на лету конвертируется в индексную.

Оба пути держат одинаковую семантику хвоста. Продолжение многострочной записи,
дописанное отдельной порцией, остаётся в своей записи, номера строк идут
дальше. Последняя строка без `'\n'` показывается предварительно и при
следующей дозаписи перечитывается со своего начала: индексатор —
`lastLineProvisional`, резидентный путь — `LogParser::tailState` + `removeEntry`
в `FileReloadState`. Якорь дочитывания ставится по точному концу прочитанного,
а не по текущему размеру файла.

Кодировка хвоста (F-1). Индексатор берёт состояние файла из стора
(`fileEncoding` → `startIndexingFrom`); резидентный путь — из
`m_fileEncodings` вкладки, плюс кодировку потока из `tailState`
(`TextEncoding`) → `startParsingFrom`. «Не решено» (файл пока ASCII)
переживает дозапись: первая не-ASCII строка хвоста решает кодировку тем же
правилом (`EncodingDetector::advance`), решённый файл дальше читается своей
кодировкой. Растущий файл, перешагнувший порог, передаёт индексатору уже
решённую кодировку (и выбор пользователя), откат индексатора в резидентный
путь — обратно.

UTF-16/32 (только резидентный путь): BOM есть лишь в начале файла, поэтому
кодировку дозаписи парсер получает явно (`tailState` → `startParsingFrom`).
Конец прочитанного и начало оборванной строки считаются в кодовых единицах
кодировки: порция, оборванная посреди символа, перечитывается с начала
строки. Файл, возвращённый индексатором в резидентный путь, вкладка помнит
(`m_residentOnlyFiles`) и по порогу не конвертирует, пока он не переписан.

**Смена схемы полей.** Схема — у вкладки (F-5, PR 1), у файла слитой
вкладки может быть своя (PR 3: «Applies to» → файл — `applyToFile`, тот же
`applyToView` со схемами файлов; `setFieldSettings(settings, files)`). Комбобокс схем,
галочка «Show selected fields only» (и кнопка Fields тулбара), колонки, редактор →
`MainWindow` передаёт выбор `FieldSchemaController` (`selectSchema`,
`setShowFields`, `setVisibleFieldNames`, `replaceCatalogue`) — он
относится к вкладке дока (`setCurrentView` из `connectToLogView`) и
становится схемой по умолчанию; «Apply Schema to All Tabs» — `applyToAllViews`;
сохранённая схема вкладки (сессия, `Ctrl+Shift+T`, память файла) — сигнал
`savedFieldSettingsFound` из `applyState` → `resolveSaved`. Всё сходится в
`applyToView(view, settings)`. Поля — функция текста и схемы (F-17, шаг 3),
в записях их нет, поэтому смена схемы — O(1) на обоих бэкендах: вкладка
ставит схему (`setFieldSettings`: раскладка колонок заново, схемы файлов в
модели — `LogModel::setFileSchemas` → `FieldSource::setSchemas`: поколение,
кэш полей пуст, одна перерисовка видимого, если поля показаны), показ
колонок (`setFieldDisplaySelection`), и только если среди применённых
правил вкладки есть правила по полю — `bindFields` и перефильтрация
(`filtersRebound`). Ни reset, ни прохода по записям, ни остановки
читателей полей (фильтр-воркеры, Search, Save View As держат свой снимок
схем — `FieldScanner`). Галочка «Show selected fields only» — только показ:
правила по полю и Entry Details от неё не зависят. Загрузка до шага 7 F-17
берёт схему файла при любом показе (граница записи по схеме, у ключевой —
момент и уровень из ключей); парсеры и индексатор получают её на старте
прохода. Ключевая схема (F-4) — тот же путь, но смена того, что схема
решает при ЧТЕНИИ (`LogViewWidget::readingSignature`: ключевая часть без
колонок; F-4, PR 3), вкладка ловит сама в `setFieldSettings` и перечитывает
те свои файлы, у которых подпись сменилась (подпись — на файл,
`beginSchemaChange` / `endSchemaChange`, `rereadAfterSchemaChange`; смена
схемы одного файла перечитывает только его): резидентный —
`startReencode(rekey)` (разбор в сторону, `invalidateFileRows`,
`replaceEntriesForFile` под одним reset, порция локатору в порядке файла),
индексный — `startFullReload`; файл в полёте — по концу прохода
(`schemaRereadPending`). Позиция (строка, место на экране) — через
`RecordLocator` после сброса строк её файла (`requestRereadPosition` →
`m_pendingPosition`), закладки и история — так же. Регексная → регексная
и смена показа полей файл не перечитывают. По `schemaApplied(view)`
активной вкладки окно обновляет колонки панелей фильтров и повторяет поиск.

**Поиск.** Быстрый поиск в тулбаре (F3 / Shift+F3) — `QuickSearch` вкладки:
запрос `TextQuery` из `QuickSearchField` (невалидный регекс не запускается,
запущенный запрос уходит в историю), скан снапшота видимых строк
`LogScanSnapshot::findRowWithText` (обход `scanRowsFrom`, текст — через
`LineCursor` снапшота) в пуле с отменой, затем
`LogListView::showSearchMatch` и `goToRow`. Старт — `QuickSearch::startRowFor`:
от строки, ВЫБРАННОЙ пользователем (инвариант 10, `LogListView::
userSelectedRow`), а если её скрыл фильтр — от её места среди видимых (якорь
view, `LogStore::placeAmongVisible`). Вставки строк за время скана пересчитывают
найденный номер; reset/удаление — `invalidated()`, вкладка ищет заново от
того же выбора.
Синхронный `LogModel::findOccurrence` (и обёртки `findNext/PreviousOccurrence`
для базлайн-хука) идёт через ту же `findRowWithText` — один обход на оба
бэкенда и оба пути; эталон семантики в тесте `quick_search` — независимый
перебор.
Следующая / предыдущая ошибка (F8 / Shift+F8, предупреждение — F7) —
`LogViewWidget::goToLevel`: от ВЫБРАННОЙ строки (инвариант 10) по видимым
строкам, через край заворачивает. Цель — первая показанная строка записи
нужного уровня: продолжения многострочной записи наследуют её уровень, и
без этого F8 шагал бы по каждой строке стек-трейса. Реализация одна на оба
бэкенда — `LogScanSnapshot::findRowWithLevel` поверх снапшота видимых строк
(только метаданные; индексный бэкенд текст не читает), `LogStore::
findRowWithLevel` зовёт её же. До миллиона видимых строк — синхронно, больше
— `QuickSearch::startLevel` в пуле: проход по сотням миллионов строк на
GUI-потоке — фриз (100 млн слитых строк ≈ 340 мс). Перестройка модели посреди
фонового скана — исход `Interrupted` («нажмите ещё раз»), без попыток угадать

Тем же путём — следующая / предыдущая строка файла из контекстного меню чипа
легенды (`FileLegend::goToFileLine`, S-14): `LogScanSnapshot::findRowOfFile`

Итог фонового поиска отброшен, если пользователь сделал что-то во view после
старта (`userActionCount`); перестройка модели без действий пользователя — поиск
заново от того же выбора, как у F3 (не «нажмите ещё раз», как у F8: слитая

Панель Search — недеструктивная (фильтрует Text Filters, отдельная панель):

## Потоки

GUI-поток владеет всем состоянием модели и вью. Фоновая работа:

| Кто | Где выполняется |
| --- | --- |
| `LogParser`, `LogIndexer` | приватные `QThreadPool` на объект, atomic-abort, деструктор ждёт воркеров. Кодировку файла индексатор получает копией на старте прохода и сообщает решение сигналом `encodingDecided` (queued, раньше порции) |
| Фильтрация (оба бэкенда) | `QtConcurrent::run`, снапшоты входных данных (у индексного — и декодеры файлов, копией), поколение + cancel-флаг; у резидентного при `Background`-извлекателе — ещё джобы порций (`startBatchFilterJob`, тот же cancel по поколению) |
| Статистика, таймлайн | `QtConcurrent::run` поверх `LogScanSnapshot` |
| Отметки на скроллбаре | `ScrollbarMarks`: `QtConcurrent::run` поверх `LogScanSnapshot` вкладки и выдачи Search (слияние по файлу и номеру строки), поколение + cancel-флаг; закладки — на GUI-потоке |
| Сверка строк `RecordLocator` | `QtConcurrent::run` на индексном пути: K позиционных чтений своим дескриптором по смещениям, снятым из индекса на GUI-потоке, отпечаток сырых байтов; результат — `QFutureWatcher` на GUI-потоке, отбрасывается по поколению файла; одно задание за раз, отмена флагом (закрытие вкладки не ждёт) |
| Мера схемы на файле | `SchemaFitJob`: `QtConcurrent::run` по `LogStore::scanSnapshot(false)` (текст — `LineCursor` снапшота, индексный читает диск в воркере), копии схем; поколение + cancel-флаг, итог — `QFutureWatcher` на GUI-потоке, reset модели отбрасывает расчёт; запуск по требованию (редактор схем), не на батч |
| Поля строк | `FieldSource` модели — только GUI-поток (показ, Entry Details; кэш «файл + строка»); воркеры (фильтр, Save View As, поиск) берут `FieldScanner` — снимок схем (неизменяемые `FileSchema` с извлекателем по `shared_ptr`) и считают поля сами; счётчики — атомарные. `Background`-извлекатель (F-17, шаг 6) — только в воркере: фоновое задание `FieldSource` (`QtConcurrent::run` в общем пуле `FieldSource::backgroundPool()` с потоками `LowPriority` + `QFutureWatcher`, одно на модель, текст и схема строки — значением, поколение, флаг отмены), фильтр по полю с ним — всегда фоновый джоб |
| `DirectoryScanner` | глобальный пул для статистики (флаг отмены на дерево: новый `scan()` и деструктор его поднимают) + ВЫДЕЛЕННЫЙ пул для фильтра по содержимому |
| `StdinSpooler` | собственный `QThread`, блокируется в чтении stdin |
| `CommandSpooler` | `QProcess` на GUI-потоке: чтение канала и запись в файл спула — в его `readyRead` (без своих потоков); ОС-процесс живёт отдельно, `release` и деструктор его завершают |
| `SourceUnpacker` | `QtConcurrent::run` в приватный `QThreadPool` на один поток, одно задание за раз (номер задания в `Result::job`); воркер получает пути и копию настроек (функция места, резерв, интервал), отмена — atomic-флаг (его же видит `GzipDevice::setAbortFlag` на каждом блоке входа), прогресс и итог — сигналы, доставленные queued на поток объекта; деструктор отменяет и ждёт |
| `SpoolItem` | удаление временного файла или каталога — `QtConcurrent::run` в глобальный пул (копия бывает на десятки ГБ; при `closingDown()` — синхронно); последний элемент там же удаляет каталог экземпляра. `SpoolDir::removeOrphans` синхронный — вызывающий зовёт его в фоне |
| Память файла | `FileMemoryStore`: запись JSON — свой `QThreadPool` на один поток (по порядку), `QSaveFile`; чтение перечня каталога и ожидание записей при открытии файла — пока на GUI-потоке (S-12) |
| Окно «Find a Schema» | `SchemaCandidates`: `QtConcurrent::run` по `scanSnapshot(false)` (выборка строк, `SchemaFit::rank` каталога, `SchemaInference`) + `QFutureWatcher`, поколение и флаг отмены, reset модели — пересчёт через 500 мс; проверка ответа модели (`checkTemplate`) — тоже `QtConcurrent::run` + `QFutureWatcher` (тяжёлый `/регекс/` — в бюджете, не на GUI-потоке) |
| Запрос к модели | `AiSchemaClient`: `QNetworkAccessManager` на GUI-потоке, своих потоков нет |
| Save View As | `ViewExportJob`: пул, снапшот строк и выбора колонок, `FieldScanner` для полей, отмена |

Правила: воркеры получают снапшоты, а не живые структуры; результат
применяется на GUI-потоке через `QFutureWatcher` и отбрасывается, если
поколение устарело; сигнальную хореографию модели ведёт только `LogModel`.

## Инварианты, которые легко сломать

1. **Нет `allEntries()` / `filteredEntries()`.** Доступ к записям — только через
   API `LogStore` (`entryAt`, `visibleMetaAt`, `visibleTimestampAt`,
   `firstVisibleRowAtOrAfter`, `scanSnapshot`, `logicalRecordLines`, …). Код,
   который материализует весь вектор, ломает индексный бэкенд на первом же
   гигабайтном файле.
2. **`LogStore` — не `QObject`.** Всю сигнальную хореографию модели
   (`beginInsertRows`/`reset`/`dataChanged`/`modelFiltered`) ведёт `LogModel` и
   **только на GUI-потоке**; воркеры доставляют результаты queued-вызовами.
3. **GUI-путь обработки батча обязан быть O(1)**: индексатор публикует пачки
   ~600k строк, любая линейная работа на `rowsInserted` — это фриз.
   Раскладка колонок вкладки (F-5) растёт при подключении файла, а не на
   батч; перенос полей в колонки вкладки (`FileSchema::toLayout`) — в
   воркере или при извлечении строки по требованию.
4. **`LogEntry` неизменяем после публикации; поля — функция текста и схемы**
   (F-17, шаг 3). В записи полей нет: всё, что парсер ставит записи
   (`setRecordHead`, `setSchemaMatched`, `setAnsiStyles`), — до публикации.
   Поля строки — `FileSchema::extract(текст)` в колонках ВКЛАДКИ (F-5:
   `columnOf` схемы файла), и получают их только через `FieldSource` модели
   (GUI-поток: `fieldsFor` / `LogModel::fieldsOf`, кэш) или `FieldScanner`
   (снимок схем для воркера). Смена схемы — `LogModel::setFileSchemas`, O(1):
   записи не трогаются, читателей полей останавливать не нужно — у каждого
   свой снимок. Правило фильтра по полю решается по полям ПЕРВОЙ строки
   записи (`LogEntry::recordHead`, у индексного — lower_bound по id записи,
   `FieldRecordCursor`): новый путь фильтрации обязан сообщать курсору запись
   строки (`setLine`), иначе продолжения разойдутся со своей записью.
5. **Байты, а не символы.** Индексатор считает смещения сам, файл открывается
   **без** `QIODevice::Text` (`QTextStream` не даёт байтовых позиций).
6. **Цвета уровней живут только в `AppTheme`** (`forLevel`/`dimForLevel`).
7. **Фильтры Time/Text/Markers — пер-вкладочные**, и схема полей тоже
   (F-5, PR 1): схема, показ полей и выбор колонок — состояние вкладки
   (`LogViewWidget::fieldSettings`), док Log Fields показывает и меняет
   активную (`FieldSchemaController::setCurrentView`), новая вкладка берёт
   схему по умолчанию — последний выбор в доке; всем вкладкам сразу — только
   «Apply Schema to All Tabs». У файла слитой вкладки может быть своя схема
   (F-5, PR 3: `LogViewWidget::m_fileSchemas`, `setFileSchema`, «Applies to»
   дока — `FieldSchemaController::setTargetFile`; показ полей и колонки
   — вкладки, колонки — объединение схем файлов по имени, раскладка только
   растёт до смены схемы пользователем); снимок несёт её в
   `TabSource.schema` (только отличную от схемы вкладки), память файла
   слитой вкладки — схему файла. Правила Text Filters и Search привязываются к
   схеме вкладки, к которой их применяют (`FieldSchemaController::bindRules
   (view, …)`); сохранённое состояние несёт схему вкладки (`ViewState.fields`),
   `applyState` ставит её до фильтров. Apply/Reset действуют на активную вкладку; новая вкладка стартует без
   фильтров — кроме вкладки, к которой применено сохранённое состояние
   (`LogViewWidget::applyState`, R-4): маркеры ставятся сразу, фильтры — сразу
   (`StateFilters::Apply`: сессия — `SessionController::open`, схему сессии
   окно ставит ДО вкладок; последняя сессия; `Ctrl+Shift+T` —
   `SessionController::reopenClosedTab`) или предлагаются вернуть
   одним щелчком (`Offer`: память файла — `LogViewWidget::addLogFile` ставит
   новой вкладке маркеры, закладки и позицию, а фильтры — только по щелчку
   на плашке «Restore Filters»; файл, добавленный вторым, — только закладки).
   Показ полного лога (R-3, `FullLogController`) — тоже пер-вкладочный:
   модель вкладки в это время без фильтров, настоящие (приостановленные)
   держит контроллер, и `captureState` снимает их, а не пустые. Фильтры
   модели ставятся только её сеттерами: `LogModel::filterSettingsChanged`
   заканчивает показ сам, новый путь ничего дополнительно не делает.
   Правила привязываются к схеме
   вкладки при применении; панели Text Filters и Row Highlighters при этом не
   переписываются — они показывают свои правила, а не применённые. Вкладка,
   получившая снимок, даже без файлов (все пропали), обычным открытием файла
   не занимается: пустая для этого — только `LogViewWidget::isBlank`
   (`MainWindow::tabForOpening`).
8. **`LogListView` подавляет раскладку `QListView`** (`doItemsLayout` минует
   базу). Поэтому все потребители базовой геометрии замещены собственными
   (`visualRect`, `indexAt`, `setSelection`, `moveCursor` через
   `rowAtY`/`rowYOffset`). Трогая навигацию или выделение, проверять весь этот
   набор целиком — пропущенная виртуалка проявляется как «current двигается, а
   подсветки нет».
9. Карточки в панелях делать на `CardFrame`, а не рисовать рамки заново.
   Поля и промежутки корневых раскладок панелей и диалогов не задавать
   числами — их даёт `CompactStyle`; явные значения только там, где нужно
   отличие (0 у обёрток, плотные строки внутри карточек).
10. **Якорь выделения обновляется только по выбору ПОЛЬЗОВАТЕЛЯ.**
    `LogListView` восстанавливает позицию после фильтрации по
    `m_persistentSelection` — записи, а не номеру строки. Но текущую строку
    назначает и сам Qt: `QAbstractItemView::focusInEvent` при возврате фокуса
    ставит её через `moveCursor(MoveNext)` с `NoUpdate`, НЕ выделяя. Такую
    строку принимать за выбор нельзя — иначе следующий фильтр утащит вьюпорт
    к началу файла. Отсюда `m_inFocusIn` в `currentChanged` и проверка
    `isRowSelected` перед прокруткой к текущей строке в обработчике
    массового `dataChanged`. Любой новый код, который прокручивает к
    `currentIndex()`, обязан сначала убедиться, что строка выделена
    (`LogListView::userSelectedRow`). Обратная сторона: переход к строке по
    действию пользователя (Go to, таймлайн, статистика, Search, быстрый
    поиск, F8, закладки F2 и панель Bookmarks, «↓ N новых строк», Alt+←/Alt+→) идёт только через `LogListView::goToRow` (к записи —
    `LogViewWidget::goToEntry`): он выделяет строку, ставит якорь и снимает
    follow-tail. Он же — единственная точка записи истории переходов
    (`NavHistory`, R-7): новый источник переходов через `goToRow` попадает в
    историю сам, а переход мимо него — нет; возврат по истории идёт через
    `goToRow` с `NavKind::History` и записей не создаёт. Восстановленная
    позиция (R-4) — не переход: `LogListView::setViewAnchor` ставит строку
    выбором пользователя (выделение, якорь), но историю не пишет, а вкладка
    зовёт его, только если `userActionCount()` не изменился с момента
    применения состояния — пользователь, успевший выбрать строку, прокрутить
    или нажать клавишу (не модификатор и не `Ctrl+C`), главнее. Отложенное восстановление позиции после
    reset тоже уступает действию, сделанному до его срабатывания. `setCurrentIndex` + `scrollTo` снаружи view follow-tail не
    снимают — следующая дозапись вернула бы вид к хвосту. Цель в последних
    полэкрана ставит вид у самого низа; чтобы «прилипание» к хвосту
    (`handleRowsInserted`) не увело его на дозаписи, `goToRow` держит флаг
    `m_holdAfterGoTo` — его снимает только прокрутка самим пользователем.
11. **У индексной вкладки два порядка строк.** Один файл — порядок файла
    (`row == line`), несколько — `lessRef` (время, как `LogEntry::operator<`).
    Порядок определяется ЧИСЛОМ файлов, а не содержимым `m_allRefs`.
    `identityAll()` описывает отображение row → line: у поисковой базы из
    отфильтрованного одного файла оно не тождественное (`m_explicitBase`),
    но порядок всё ещё файловый. Все бинарные поиски и слияния по `m_allRefs`/`m_visibleRefs`
    идут через `rowLess`, который выбирает порядок по режиму; всё, что
    ВСТАВЛЯЕТСЯ в слитый список (батч индексатора, результат фильтра по
    диапазону), сперва сортируется. `lessRef` напрямую — только для сортировки
    в порядок слитой вкладки.
12. **`Background`-извлекатель не вызывается на GUI-потоке** (F-17, шаг 6).
    Поля для показа — только `FieldSource::fieldsFor` (`LogModel::fieldsOf` /
    `fieldLookupOf`): у медленного извлекателя это `Pending` и фоновое
    задание, показ — сырой текст, по готовности — `dataChanged` с
    `FieldsReadyRole` (view держит якорь, инвариант 10). Фильтр с правилами по
    полю при такой схеме (`LogModel::fieldRulesInBackground`) — только джоб в
    воркере: синхронный резидентный путь, решение дописанной порции и
    точечная переоценка строки индексного стора уходят в фоновый джоб. Новый
    путь, который зовёт `FileSchema::extract` / `FieldScanner` на GUI-потоке,
    обязан проверить `cost()` (известное нарушение — окно «Find a Schema»,
    S-27); страховка — подставной блокирующий извлекатель в `field_source`.

## Как проверять изменения

Пользователь просил **не отлаживаться скриншотами**. Порядок предпочтений:

1. **Оконный смоук `tests/mainwindow_smoke`** — первый способ проверить
   склейку окна (меню, действия, сочетания, доки, сигналы между панелями):
   сценарий дописывается туда и идёт через `QAction::trigger`, сочетания
   (`press` → `QTest::keyClick` в активное окно), кнопки и `findChild`.
   Модальный диалог — `g_driver->expect(обработчик)` до действия, иначе
   драйвер закроет его сам. Логику при этом проверяют не здесь, а тестом
   контроллера или вкладки.
2. **Offscreen-харнес в `tests/`** — `qputenv("QT_QPA_PLATFORM","offscreen")` +
   `QApplication`, панель конструируется напрямую, контролы ищутся через
   `findChild<T*>(objectName)`, клики — `button->click()`, ожидание — цикл
   `QCoreApplication::processEvents` в предикате. Так проверяются даже
   `QFileSystemWatcher`, дебаунсы и таймеры (см. `tests/dirscanner_smoke`).
3. **Временный env-gated хук в `MainWindow`** (QTimer в конструкторе → выполнить
   действие → сдампить состояние в файл), если нужен живой оконный контекст.
4. Синтетические клики мышью — крайний случай: `SetCursorPos` у края экрана
   однажды свернул все окна пользователя, а `SendKeys` может молча не доходить
   до приложения.

Постоянные env-хуки в коде:

| Переменная | Что делает |
| --- | --- |
| `DENDRO_BASELINE_DUMP=<каталог>` | После загрузки первого файла прогоняет фиксированную серию фильтров, дампит `baseline.json` / `baseline_view.txt` и выходит. Работает через стабильный API модели, поэтому даёт байтовый базлайн при рефакторингах хранилища и сравним между бэкендами (на индексном `midLen` — оценка, из сравнения исключается). |
| `DENDRO_UI_TRACE=<файл>` | Хартбит 100 мс; разрывы между метками = фризы event loop. |
| `DENDRO_SLOW_EVENTS=<файл>` | Каждая доставка события на GUI-потоке дольше 100 мс: `ms;класс;тип`. Точнее, чем `DENDRO_UI_TRACE`, — сразу указывает на виновника. |

Тестовые логи генерируются `scripts/generate_test_log.py`, фикстуры кладутся в
`testdata/` (gitignored).

## Работа по плану

**Сначала свежий `main`.** Облачная сессия может стартовать с устаревшего
снимка репозитория — на часы и десятки коммитов позади (замечено 18 ноября:
сессии, запущенные в 11–13 UTC, получили `main` от 10:39). Первым действием:
`git fetch origin main && git merge --ff-only origin/main`, затем перечитать
этот файл и `docs/roadmap.md` — прочитанное при старте могло быть старым.

Что делать дальше — в **`docs/roadmap.md`**: задачи с ID, зоной и критерием
готовности, а в конце раздел «Процесс» (виды сессий, шаги, параллельность).
Одна задача или шаг дизайн-документа — одна сессия. Задачи объёма L делаются по
`docs/design/<ID>.md`. Сначала падающий offscreen-тест на критерий готовности,
потом реализация. Логику, которой нужен `MainWindow`, выносить в контроллер без
виджетов (образец — `SearchResultsController`).

**Сдача — прямо в `main`, без PR.** Пушить, когда сборка и полный `ctest`
зелёные. Пуш отклонён — `git fetch origin main`, влить, пересобрать, прогнать
тесты, пушить снова; force-push в `main` запрещён. После пуша дождаться CI по
своему коммиту (Windows и Linux) и чинить следующим коммитом, если он упал.

**Решения принимает исполнитель.** Автор передал продуктовые решения агентам:
брать рекомендованный вариант из дизайн-документа, иначе — самый простой
обратимый, и записывать решение в документ задачи или сообщение коммита.
Спрашивать автора только о необратимом и внешнем: публикации вне репозитория,
удаление пользовательских данных. Теги и релизы — см. «Релизы» ниже.

Коммиты: без трейлеров-атрибуции (`Co-Authored-By` и подобных). Пушить в

**Релизы.** Теги и релизы — по слову автора. 19 ноября 2026 автор дал его

делать релизы сам», «я разрешаю ставить теги тебе». На исполнителей задач это
не распространяется: исполнитель готовит релизный коммит (версия,
`CHANGELOG.md`, справки), тег не ставит и релиз не запускает. Планировщик
выпускает релиз, когда релизный коммит принят — зелёные CI и Sanitizers по
нему и локальный полный `ctest`: Actions → Release → Run workflow с версией и
коммитом (`.github/workflows/release.yml`). Конвейер собирает и тестирует
этот коммит на обеих платформах, после этого сам ставит тег `vX.Y.Z` и
публикует GitHub Release с разделом версии из `CHANGELOG.md`. Коммит релиза — вершина `main` (или коммит с теми же
файлами `.github/workflows`): поставить тег на коммит с другими
workflow-файлами конвейер не может, и проверяет это до сборки — поэтому
релизный коммит делается ПОСЛЕ последней правки workflow. Отправка тега из
облачной сессии (`git push origin vX.Y.Z`) закрыта её прокси — не повторять.
После релиза раздел версии в `CHANGELOG.md` заморожен: новое — в
`[Unreleased]`.

## Ловушки платформы и инструментов

- **MSVC**: смена `struct` → `class` меняет манглинг. Forward-декларации должны
  совпадать по ключевому слову, иначе `LNK2019` в неожиданном месте.
- **Qt 6 `QHash::erase`** делает backward-shift и инвалидирует чужие итераторы —
  вытеснение из кэша делать **до** вставки, а не после.
- **`QVector`**: в многопоточном коде `constLast()`, не `last()` — второй делает
  detach вне мьютекса.
- **Style sheet и смена палитры**: виджет со своим `setStyleSheet` и все его
  дети не получают ни новой палитры приложения, ни `PaletteChange`
  (`QWidgetPrivate::propagatePaletteChange` пропускает `WA_StyleSheet`). Их
  доводит `ColorSchemeController::repolishStyledWidgets`. Цвет, вписанный в
  строку стиля из палитры, пересчитывать в `changeEvent(PaletteChange)`, и
  брать палитру родителя, если стиль меняет цвет самого виджета
  (`MutedLabel`). Проверка — сравнение картинок в `theme_mode`: новую панель
  добавить туда.
- **`QTextStream::pos()`** посреди потока считает от нуля, если устройство
  сдвинули `seek` ДО создания потока (опорная позиция буфера — 0, пока буфер
  не прочитан целиком). Двигать сам поток: `in.seek(offset)`. И он не
  дешёвый: посреди потока `pos()` перечитывает буфер ПО БАЙТУ от места, где
  конец строки последний раз совпал с границей его 16-КБ блока чтения, —
  ~130 нс на байт, на сотнях МБ — секунды на вызов (Q-18). Позицию строки в
  цикле не спрашивать у потока: `ByteLineReader` или свой счётчик байтов.
  Один вызов в конце прохода (буфер прочитан целиком) — дёшев.
- **Таблицы в `QTextBrowser`**: не задавать `width="100%"` текстовой колонке —
  соседние числовые ячейки схлопнутся в нулевую ширину и числа рассыплются в
  столбик по цифре. Числовым ячейкам — `white-space: nowrap`.
- **В тестовых exe `qWarning()` не доходит до stderr** (уходит в отладчик).
  Для временной трассировки — `fprintf(stderr, …) + fflush(stderr)`, ловить
  через `cmd /c "app.exe 2> file"`: PowerShell'ный `2>&1` заворачивает строки в
  `ErrorRecord`.
- **Пайпы тестировать через `cmd /c "gen | app -"`** — PowerShell-джоб портит
  байты в пайпе.
- **Переносы строк**: рабочее дерево CRLF (`core.autocrlf=true`, `.gitattributes`
  фиксирует только `*.bat`/`*.cmd`). Полная перезапись файла даёт LF — после
  такой правки нормализовать обратно в CRLF.
- Комментарии в коде смешанные, русский и английский. Писать в стиле того файла,
  который правишь.

## Состояние и известные слабые места

Поддержка больших логов доведена до рабочего состояния: 2 ГБ / 23,8 млн строк
индексируются за ~10–13 с, пик RAM ~663 МБ (резидентно тот же файл требовал
единицы гигабайт), худший фриз GUI ~117 мс. Цель — ~20 ГБ / 200 млн строк.

Что на индексном бэкенде осталось слабым:

- одно-файловая индексная вкладка вообще не сортирует (`row == line`) — это
  намеренный компромисс ради нулевой цены памяти, но тот же файл выше и ниже
  порога 512 МБ показывается в разном порядке. Закреплено в
  `testSingleFileOrdering`;
- слитая индексная вкладка без фильтра вставляет батч индексатора сериями
  (`appendIndexedRows` → `insertSortedRefs`), дозапись хвоста — одна серия в
  конце без reset. Но при загрузке нескольких файлов, чьи батчи чередуются во
  времени, серий больше 64 и это по-прежнему **reset на батч**: выделение и
  прокрутка восстанавливаются по якорю на каждой порции;
- добавление второго файла в открытую вкладку с огромным файлом, строки
  которого НЕ упорядочены по времени, переупорядочивает его на GUI-потоке.
  Сортируются записи, а не строки: устойчиво, по ключам из снапшота индекса,
  без мьютекса и без `lessRef` (`materializeAllRefs`). Это O(M log M) по
  4-байтовым id записей, а не прежние минуты, но всё ещё пауза на десятках
  миллионов записей. На упорядоченном файле — одна проверка, без сортировки;
- ручная GUI-проверка скролла, деталей и маркеров на 2–20 ГБ не делалась.

Что слабо после этапа 0.6 (задачи — в `docs/roadmap.md`):

- `mainwindow.cpp` ~4500 строк, конструктор ~750, `logviewwidget.cpp` ~1900
  (память файла, состояние, кодировки резидентного пути) — переносы M-1…M-7;
  оконный смоук (`tests/mainwindow_smoke`) их страхует, но покрывает не всё
  (P-9);
- память файла читает каталог и ждёт записи на GUI-потоке при открытии файла
  (S-12) — на сетевом диске открытие может подвиснуть;
- отпечаток строки не различает строки, отличающиеся только не-ASCII
  текстом (решение R-1);
- возможности 0.6 (закладки, сессии, отметки скроллбара, кодировки) на
  настоящем дисплее Windows не проверялись — список для автора:
  `docs/release-checklist-0.6.0.md`.
