# CLAUDE.md

Указания для Claude Code (и любого другого агента) при работе с этим репозиторием.

## О проекте

**DendroLog** — десктопный просмотрщик логов на Qt 6 / C++17 (Windows и Linux).
Вкладки на несколько файлов со слиянием по времени, извлечение полей по схемам,
фильтрация, подсветка, таймлайн, статистика, сканер каталога, дочитывание
растущих файлов и чтение stdin. Версия — единственный источник правды в
`project(VERSION)` в `CMakeLists.txt`, оттуда приходит define `DENDROLOG_VERSION`.

## Сборка и запуск

```sh
cmake -S . -B build                                       # конфигурация
cmake --build build --config Release --target DendroLog   # сборка
```

Результат: `build/Release/DendroLog.exe`. Локально используется Qt 6.8.3
(`msvc2022_64`), генератор «Visual Studio 17 2022». `project_configure.bat`
находит Qt сам (`scripts/find-qt.ps1`); для нестандартной установки задать
`QT_PATH` или `CMAKE_PREFIX_PATH`.

Важное про локальный `build/`:

- там остались **устаревшие артефакты** до переименования проекта —
  `build/LogViewer.vcxproj` и `build/Release/LogViewer.exe`. Не собирать цель
  `LogViewer`, не запускать этот exe: у него нет define версии и он не
  соответствует текущему коду. Собирать только `--target DendroLog`;
- вывод MSBuild **локализован на русский** — не искать в нём `error` или
  `Build succeeded`, ориентироваться на код возврата;
- рядом с exe лежит `DendroLog.ini`, поэтому dev-сборка работает в
  **portable-режиме** (`AppSettings::configDir()` возвращает каталог exe, если
  там есть ini или файл-маркер `portable`). Настройки пользователя в
  `%LOCALAPPDATA%` при этом не трогаются. Схемы полей лежат в
  `<configDir>/patterns/*.json`.

Аргументы командной строки: `DendroLog.exe file1 file2 …`, `--new-instance`
(принудительно отдельное окно), `-` / `--stdin` (читать поток). По умолчанию
работает один экземпляр на пользователя: повторный запуск передаёт файлы в уже
открытое окно (`SingleInstance`); пайп передать нельзя, поэтому при `-` всегда
открывается своё окно.

## Тесты

```sh
ctest --test-dir build -C Release --output-on-failure
```

Четыре теста без окна, зарегистрированы в CTest при `BUILD_TESTING`; CI
(`.github/workflows/build.yml`) собирает и гоняет их на Windows и Linux:

| Тест | Что проверяет |
| --- | --- |
| `tests/pattern_smoke` | движок схем `LogPattern` + автоопределение |
| `tests/lineindex_smoke` | `LineIndex`/`LogIndexer`: смещения, дозапись, золотое сравнение с `LogParser` |
| `tests/dirscanner_smoke` | `DirectoryScanner` и панель: скан, фильтры, режимы обновления |
| `tests/logstore_equivalence` | **дифференциальный**: резидентный и индексный бэкенды на одних данных обязаны давать одно и то же |
| `tests/logview_state` | **табличный**: состояние `LogListView` (выделение, прокрутка, геометрия, клавиатура) переживает изменения данных |

Общие для тестов фикстуры и загрузка документа обоими путями хранилища —
`tests/common/testdocuments.h`.

`logstore_equivalence` — главный страховочный трос хранилища: эталон
поведения индексного бэкенда не написан прозой, им СЛУЖИТ резидентный. Тест
грузит одни и те же файлы обоими путями, прогоняет 33 конфигурации фильтров
(включая рандомизированные по фиксированному seed) и сравнивает весь API
`LogStore` построчно. Мульти-файловая вкладка проверяется в двух сценариях
подключения: файл дописан в открытую вкладку и файлы открыты разом (все
подключены до первого батча). Известные и намеренные расхождения там не
замалчиваются, а закреплены отдельными проверками, которые упадут при их
изменении. Прогон занимает ~50 с; поэтапный тайминг он печатает сам.

`logview_state` — страховочный трос представления. Инвариант один («текущая
запись и позиция вьюпорта переживают изменение видимого набора»), а путей,
которые его нарушают, много, поэтому проверка табличная: инварианты × 11
триггеров (уровни, время, текст, маркеры, колонки, добавление файла) × три
пути хранилища × позиции. Новый путь, добавленный мимо общего механизма
восстановления, падает здесь сразу. Прогон ~85 с.

`lineindex_smoke` среди прочего проверяет цену скана `SequentialLineReader`:
число перечитываний окна вперёд, назад и с «дрожанием» обязано оставаться
ограниченным, а не расти по строке на промах.

У `lineindex_smoke` есть режимы профилирования: `--bench <file> [pattern]` и
`--bench-stages <file>` (ступенчатая атрибуция I/O → декод → timestamp → level).

## С чего начать чтение

Порядок, в котором код складывается в голове быстрее всего:

1. `src/logentry.h` — что такое «строка лога» и как записи упорядочены
   (`operator<`: по времени, затем файл, запись, номер строки; строки без
   метки — в конец). Весь порядок в приложении — зеркало этого компаратора.
2. `src/logstore.h` — шов хранилища: весь доступ к данным идёт через этот
   интерфейс, у него две реализации.
3. `src/logmodel.h` — фасад модели поверх шва, настройки фильтров и роли.
4. `src/logviewwidget.h` — вкладка: модель + view + загрузка файлов и
   дочитывание. Самый полезный файл, чтобы понять жизненный цикл документа.
5. `src/LogListView.h` — представление с собственной геометрией и отрисовкой.
6. `src/mainwindow.h` — окно, доки, панели, глобальные действия.

У большинства модулей в начале заголовка есть блок-комментарий с описанием
и ловушками — он точнее этого файла и обновляется вместе с кодом.

## Архитектура

Новые `.cpp`/`.h` нужно **явно добавлять в `PROJECT_SOURCES`** в `CMakeLists.txt` —
глоба нет.

**Хранение записей.** `LogStore` (`src/logstore.h`) — интерфейс доступа к
записям за фасадом `LogModel`, два бэкенда:

- `ResidentLogStore` — весь текст в памяти, путь по умолчанию;
- `IndexedLogStore` — блочный индекс строк (`LineIndex`, `LogIndexer`) + чтение
  текста с диска по требованию (`TextChunkCache` — 4 МБ чанки LRU на GUI-потоке,
  `SequentialLineReader` — для воркеров).

Бэкенд выбирается в `LogViewWidget::addLogFile` по размеру файла и настройке
`AppSettings::indexedThresholdBytes()` (по умолчанию 512 МБ, `0` = всегда
индексный). **Один бэкенд на вкладку**: большой файл конвертирует вкладку целиком
и все её файлы перечитываются через индексатор; UTF-16 уходит обратно в
резидентный путь. Растущий файл, перешагнувший порог, конвертируется на лету.

`StdinSpooler` спулит поток в `%TEMP%\DendroLog-stdin-PID.log`, он открывается
вкладкой растущего лога (auto-reload + follow-tail). `FileChangeDetector` держит
якоря дочитывания в **сырых байтовых смещениях**.

**Разбор.** `LogPattern` (схемы извлечения полей, каскад «полный regex →
префиксные варианты → re-sync варианты» с литеральными пре-фильтрами),
`PatternHeuristics` (автоопределение схемы по строке), `SchemaStore`
(`patterns/*.json`), `LineClassifier` (уровень и timestamp в горячем пути
индексации, без построения `QDateTime`), `LogParser`.

**Модель.** `LogModel` — фасад над store. Фильтрация: `FilterRuleSet`
(Include/Exclude, AND/OR, AND связывает сильнее; на правило — свои
case-sensitive/regex; привязка правила к полю по **имени**, разрешается в
`bindFields()`). До 100k записей резидентный фильтр считается синхронно, выше —
`QtConcurrent` по снапшоту с поколением и cancel-флагом; на индексном бэкенде
фильтр **всегда** асинхронный.

**Представление.** `LogListView` — собственная отрисовка (кэш pixmap строк,
префикс-суммы высот). Индексная вкладка включает `hugeRowMode` с первой строки
(резидентная — свыше 2 млн строк): только uniform-высоты, вся геометрия O(1),
плотные кэши не ведутся, wrap/toggle отключены.

## Карта модулей

**Данные и хранилище**

| --- | --- |
| `logentry.h` | `LogEntry` — одна физическая строка: id логической записи, номер строки в файле, метка, уровень, текст, файл-источник, извлечённые поля. Доступ только через аксессоры; `setFields` — единственный мутатор |

| `logstore.h` | Интерфейс доступа к записям (счётчики, точечный доступ, навигация, поиск, снапшоты, фильтрация). Не `QObject` |

| `indexedlogstore.*` | Индексный бэкенд: в памяти только индекс строк, текст — с диска. `RowRef = (fileId << 40) \| line`, два порядка строк (см. инвариант 11) |

## Сквозные сценарии

Пять путей, через которые проходит почти всё; по ним удобно искать место для
правки.

**Открытие файла.** `MainWindow::openRecentFile` (или drag&drop, командная
строка, `SingleInstance`) → выбор вкладки → `LogViewWidget::addLogFile` →
по размеру файла и `indexedThresholdBytes` выбирается бэкенд:

- резидентный: `LogParser::startParsing` → сигнал `entriesParsed` батчами →
  `handleEntriesParsed` сортирует батч и зовёт `LogModel::mergeEntries` —
  вставка сериями `beginInsertRows`, без reset;
- индексный: `IndexedLogStore::attachFile` + `LogIndexer::startIndexing` →
  `indexBatchReady` → `appendIndexedRows`.

`LogListView` узнаёт о новых строках из сигналов модели и пересчитывает
высоты и prefix-суммы. Схема полей при этом берётся текущая выбранная —
автоопределение живёт в редакторе схем, а не в пути загрузки.

**Фильтрация.** Кнопки уровней, доки Time Filter / Text Filters / Row
Highlighters и протяжка по таймлайну — все меняют настройки в `LogModel`
(`setLogLevelFilter`, `setTimeRangeFilter`, `setFilterRules`,
`setRowMarkers`) → `applyFilter()` → бэкенд пересобирает видимый список:
резидентный до 100k записей синхронно и с reset, выше — джобом в пуле;
индексный — всегда джобом. По завершении: `modelFiltered` → `LogViewWidget` →
`MainWindow::handleModelFiltered` (счётчики, кнопки-индикаторы, обновление
Search Results). `LogListView` на reset восстанавливает выделение и позицию
по якорю-записи — см. инвариант 10.

**Дочитывание хвоста.** Таймер авто-обновления или F5 →
`LogViewWidget::reloadChangedFiles` → `FileChangeDetector` по якорю решает:
дозапись (читаем с сохранённого смещения: `m_reloadParser` либо
`startIndexingFrom`) или файл переписан (полная перезагрузка,
`dropRowsForFile` + `startFullReload`). Новые строки помечаются «новыми»
(`IsNewRole`, зелёный маркер в жёлобе). Если растущий файл перешагнул порог,
вкладка на лету конвертируется в индексную.

**Смена схемы полей.** Комбобокс схем или редактор → `MainWindow` меняет
схему у парсера вкладок и зовёт переизвлечение полей: резидентный путь —
`QtConcurrent::map` по записям, ОБЯЗАТЕЛЬНО с `cancelPendingFilter(wait)`
до и `reapplyFilterIfStale()` после (инвариант 4); индексный — просто новая
схема в store, поля извлекаются по требованию. Дальше `setAvailableFields` +
`bindFields` у правил фильтрации и `refreshDisplay`.

**Поиск.** Быстрый поиск в тулбаре — `LogModel::findNext/PreviousOccurrence`
(на индексе это синхронный дисковый скан) + `LogListView::showSearchMatch`.
Панель Text Filters в режиме Search — недеструктивная: результаты идут во
вторую пару `LogModel` + `LogListView` в доке Search Results поверх тех же
записей активной вкладки.

## Потоки

GUI-поток владеет всем состоянием модели и вью. Фоновая работа:

| Кто | Где выполняется |
| --- | --- |
| `LogParser`, `LogIndexer` | приватные `QThreadPool` на объект, atomic-abort, деструктор ждёт воркеров |
| Фильтрация (оба бэкенда) | `QtConcurrent::run`, снапшоты входных данных, поколение + cancel-флаг |
| Статистика, таймлайн | `QtConcurrent::run` поверх `LogScanSnapshot` |
| Переизвлечение полей | `QtConcurrent::map` по резидентным записям |
| `DirectoryScanner` | глобальный пул для статистики + ВЫДЕЛЕННЫЙ пул для фильтра по содержимому |
| `StdinSpooler` | собственный `QThread`, блокируется в чтении stdin |

Правила: воркеры получают снапшоты, а не живые структуры; результат
применяется на GUI-потоке через `QFutureWatcher` и отбрасывается, если
поколение устарело; сигнальную хореографию модели ведёт только `LogModel`.

## Данные на диске

| Что | Где |
| --- | --- |
| Настройки, геометрия окна, доки, недавние файлы, профили фильтров, шорткаты | `<configDir>/DendroLog.ini`, группы `[App]`, `[Window]`, `[View]`, `[Files]`, `[RecentFiles]`, `[Filters]`, `[Shortcuts]`, `[Theme]`, `[EntryDetailsPanel]` |
| Схемы полей | `<configDir>/patterns/*.json` (по файлу на схему, каталог — источник правды) |
| Спул stdin | `%TEMP%\DendroLog-stdin-<pid>.log` |

`configDir()` — каталог exe в portable-режиме (есть файл-маркер `portable`
или уже лежащий рядом ini), иначе `QStandardPaths::AppConfigLocation`.

## Инварианты, которые легко сломать

1. **Нет `allEntries()` / `filteredEntries()`.** Доступ к записям — только через
   API `LogStore` (`entryAt`, `visibleMetaAt`, `visibleTimestampAt`,
   `firstVisibleRowAtOrAfter`, `scanSnapshot`, `logicalRecordLines`, …). Код,
   который материализует весь вектор, ломает индексный бэкенд на первом же
   гигабайтном файле.
2. **`LogStore` — не `QObject`.** Всю сигнальную хореографию модели
   (`beginInsertRows`/`reset`/`dataChanged`/`modelFiltered`) ведёт `LogModel` и
   **только на GUI-потоке**; воркеры доставляют результаты queued-вызовами.
3. **GUI-путь обработки батча обязан быть O(1)**: индексатор публикует пачки
   ~600k строк, любая линейная работа на `rowsInserted` — это фриз.
4. **Воркеры читают только** `message`/`timestamp`/`level`/`id`/`sourceFile`:
   `fields` конкурентно мутирует переизвлечение схемы. Перед `QtConcurrent`-
   переизвлечением полей звать `cancelPendingFilter(wait)`, после —
   `reapplyFilterIfStale()`.
5. **Байты, а не символы.** Индексатор считает смещения сам, файл открывается
   **без** `QIODevice::Text` (`QTextStream` не даёт байтовых позиций).
6. **Цвета уровней живут только в `AppTheme`** (`forLevel`/`dimForLevel`).
7. **Фильтры Time/Text/Markers — пер-вкладочные**, Fields — глобальный.
   Apply/Reset действуют на активную вкладку; новая вкладка стартует без фильтров.
8. **`LogListView` подавляет раскладку `QListView`** (`doItemsLayout` минует
   базу). Поэтому все потребители базовой геометрии замещены собственными
   (`visualRect`, `indexAt`, `setSelection`, `moveCursor` через
   `rowAtY`/`rowYOffset`). Трогая навигацию или выделение, проверять весь этот
   набор целиком — пропущенная виртуалка проявляется как «current двигается, а
   подсветки нет».
9. Карточки в панелях делать на `CardFrame`, а не рисовать рамки заново.
10. **Якорь выделения обновляется только по выбору ПОЛЬЗОВАТЕЛЯ.**
    `LogListView` восстанавливает позицию после фильтрации по
    `m_persistentSelection` — записи, а не номеру строки. Но текущую строку
    назначает и сам Qt: `QAbstractItemView::focusInEvent` при возврате фокуса
    ставит её через `moveCursor(MoveNext)` с `NoUpdate`, НЕ выделяя. Такую
    строку принимать за выбор нельзя — иначе следующий фильтр утащит вьюпорт
    к началу файла. Отсюда `m_inFocusIn` в `currentChanged` и проверка
    `isRowSelected` перед прокруткой к текущей строке в обработчике
    массового `dataChanged`. Любой новый код, который прокручивает к
    `currentIndex()`, обязан сначала убедиться, что строка выделена.
11. **У индексной вкладки два порядка строк.** Один файл — порядок файла
    (`row == line`), несколько — `lessRef` (время, как `LogEntry::operator<`).
    Режим определяется ЧИСЛОМ файлов (`identityAll()`), а не содержимым
    `m_allRefs`. Все бинарные поиски и слияния по `m_allRefs`/`m_visibleRefs`
    идут через `rowLess`, который выбирает порядок по режиму; всё, что
    ВСТАВЛЯЕТСЯ в слитый список (батч индексатора, результат фильтра по
    диапазону), сперва сортируется. `lessRef` напрямую — только для сортировки
    в порядок слитой вкладки.

## Как проверять изменения

Пользователь просил **не отлаживаться скриншотами**. Порядок предпочтений:

1. **Offscreen-харнес в `tests/`** — `qputenv("QT_QPA_PLATFORM","offscreen")` +
   `QApplication`, панель конструируется напрямую, контролы ищутся через
   `findChild<T*>(objectName)`, клики — `button->click()`, ожидание — цикл
   `QCoreApplication::processEvents` в предикате. Так проверяются даже
   `QFileSystemWatcher`, дебаунсы и таймеры (см. `tests/dirscanner_smoke`).
2. **Временный env-gated хук в `MainWindow`** (QTimer в конструкторе → выполнить
   действие → сдампить состояние в файл), если нужен живой оконный контекст.
3. Синтетические клики мышью — крайний случай: `SetCursorPos` у края экрана
   однажды свернул все окна пользователя, а `SendKeys` может молча не доходить
   до приложения.

Постоянные env-хуки в коде:

| Переменная | Что делает |
| --- | --- |
| `DENDRO_BASELINE_DUMP=<каталог>` | После загрузки первого файла прогоняет фиксированную серию фильтров, дампит `baseline.json` / `baseline_view.txt` и выходит. Работает через стабильный API модели, поэтому даёт байтовый базлайн при рефакторингах хранилища и сравним между бэкендами (на индексном `midLen` — оценка, из сравнения исключается). |
| `DENDRO_UI_TRACE=<файл>` | Хартбит 100 мс; разрывы между метками = фризы event loop. |
| `DENDRO_SLOW_EVENTS=<файл>` | Каждая доставка события на GUI-потоке дольше 100 мс: `ms;класс;тип`. Точнее, чем `DENDRO_UI_TRACE`, — сразу указывает на виновника. |

Тестовые логи генерируются `scripts/generate_test_log.py`, фикстуры кладутся в
`testdata/` (gitignored).

## Ловушки платформы и инструментов

- **MSVC**: смена `struct` → `class` меняет манглинг. Forward-декларации должны
  совпадать по ключевому слову, иначе `LNK2019` в неожиданном месте.
- **Qt 6 `QHash::erase`** делает backward-shift и инвалидирует чужие итераторы —
  вытеснение из кэша делать **до** вставки, а не после.
- **`QVector`**: в многопоточном коде `constLast()`, не `last()` — второй делает
  detach вне мьютекса.
- **Таблицы в `QTextBrowser`**: не задавать `width="100%"` текстовой колонке —
  соседние числовые ячейки схлопнутся в нулевую ширину и числа рассыплются в
  столбик по цифре. Числовым ячейкам — `white-space: nowrap`.
- **В тестовых exe `qWarning()` не доходит до stderr** (уходит в отладчик).
  Для временной трассировки — `fprintf(stderr, …) + fflush(stderr)`, ловить
  через `cmd /c "app.exe 2> file"`: PowerShell'ный `2>&1` заворачивает строки в
  `ErrorRecord`.
- **Пайпы тестировать через `cmd /c "gen | app -"`** — PowerShell-джоб портит
  байты в пайпе.
- **Переносы строк**: рабочее дерево CRLF (`core.autocrlf=true`, `.gitattributes`
  фиксирует только `*.bat`/`*.cmd`). Полная перезапись файла даёт LF — после
  такой правки нормализовать обратно в CRLF.
- Комментарии в коде смешанные, русский и английский. Писать в стиле того файла,
  который правишь.

## Состояние и известные слабые места

Поддержка больших логов доведена до рабочего состояния: 2 ГБ / 23,8 млн строк
индексируются за ~10–13 с, пик RAM ~663 МБ (резидентно тот же файл требовал
единицы гигабайт), худший фриз GUI ~117 мс. Цель — ~20 ГБ / 200 млн строк.

Что на индексном бэкенде осталось слабым:

- одно-файловая индексная вкладка вообще не сортирует (`row == line`) — это
  намеренный компромисс ради нулевой цены памяти, но тот же файл выше и ниже
  порога 512 МБ показывается в разном порядке. Закреплено в
  `testSingleFileOrdering`;
- слитая индексная вкладка **без фильтра делает reset модели на каждый батч**
  индексатора (`appendIndexedRows`, ветка `m_identityVisible && !identityAll()`),
  то есть во время загрузки нескольких больших файлов выделение и прокрутка
  сбрасываются на каждой порции. Резидентный путь вставляет сериями
  `beginInsertRows`;
- добавление второго файла в открытую вкладку с огромным файлом, строки
  которого НЕ упорядочены по времени, сортирует все его строки `lessRef` на
  GUI-потоке — O(N log N) с мьютексом индекса в каждом сравнении. На
  упорядоченном файле это одна проверка по записям, без сортировки;
- быстрый поиск синхронный в обе стороны — дисковый скан фризит GUI на
  гигантском файле без совпадений;
- `Save View As` пишет синхронно через `data()`, без стриминга и прогресса;
- **с включённым переносом строк навигация уводит текущую строку за экран**:
  высоты строк уточняются лениво, уже после прокрутки, и view не возвращает
  строку в видимую область — после Down / PageDown / End она оказывается ниже
  вьюпорта, а последняя строка недостижима прокруткой. Закреплено в
  `logview_state` (`checkWrapKnownDefect`), там же написано, что делать после
  починки;
- ручная GUI-проверка скролла, деталей и маркеров на 2–20 ГБ не делалась.
