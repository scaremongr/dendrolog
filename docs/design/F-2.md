# F-2. Сжатые файлы и архивы

Статус: принят 17 ноября 2026, действуют рекомендованные варианты (17 ноября 2026, для `0.4.0`). Задача `F-2` из `docs/roadmap.md`, релиз 0.7. Сверен с кодом 0.6.0 на ревизии 19 ноября 2026 — раздел «Что изменилось к 0.6.0»: он главнее номеров строк и пунктов «Как устроено сейчас», помеченных как устаревшие.

## Задача и границы

Файл от клиента открывается как есть: `app.log.gz` — вкладкой, архив с десятками логов — набором файлов в сканере каталога.

Входит:

- `.gz` с одним логом, включая многочастные (склеенные) gzip. Распознаётся по сигнатуре `1F 8B`, а не только по имени.
- `.zip`, `.tar`, `.tar.gz`, `.tgz` как набор файлов: содержимое показывается в Directory Scanner.
- `.gz` в дереве сканера рядом с обычными логами: счётчики, диапазон времени, фильтр по содержимому.
- Прогресс, отмена, проверка места на диске, уборка временных файлов, в том числе после падения.

Не входит:

- `.bz2`, `.xz`, `.zst`, `.7z`, `.rar`, архивы с паролем — понятное сообщение «формат не поддерживается».
- Архив внутри архива не раскрывается. `.gz` внутри архива остаётся файлом и открывается как обычный `.gz`.
- Чтение сжатого файла без распаковки на диск (см. «Отвергнутые варианты»).
- Кэш распакованных копий между запусками.
- Запись и пересжатие.

## Что изменилось к 0.6.0

Номера строк в «Как устроено сейчас» — по коду 0.4.0. С тех пор этап 0.6 (R-1, R-4, R-5, R-8) и кодировки F-1 поменяли открытие файла, идентичность источника и сохранение состояния; ниже — что из этого меняет шаги F-2.

- **Выбор вкладки — уже один.** `MainWindow::tabForOpening` (R-5) заменил три копии; пустой считается только `LogViewWidget::isBlank`. Пункт PR 2 «один общий выбор вкладки вместо трёх копий» сделан — PR 2 только пользуется им.
- **Что куда идёт — `OpenRouting::plan`** (Q-6, R-5): файлы, первая папка — в Directory Scanner, `*.dlsession` — сессия; drag&drop, командная строка и второй экземпляр идут через него. Архив (`.zip`, `.tar`, `.tgz`, `.tar.gz`) — четвёртый исход плана (в сканер, как папка), `.gz` — файл. `plan` файлы не читает, поэтому архив от лога он отличает по имени, а сигнатура (gzip без имени `.gz`, tar внутри `.gz`) проверяется уже при открытии, как в «Архивы с набором файлов». Тест — `tests/open_routing`.
- **Недавние файлы.** Спул stdin туда больше не попадает (`RecentFiles::accepts`, `StdinSpooler::isSpoolFilePath`, Q-9) — пункт «Спул stdin туда тоже попадает» устарел. Временную копию распакованного файла добавлять в недавние нельзя тем же правилом: в недавние идёт путь источника (`LogSource::path`).
- **Слияние вкладок** — `LogViewWidget::addFilesFrom(other)`: переносит файлы с состоянием кодировки (выбор пользователя и решение автоматики) и закладки. `LogOpenRequest` из «Слияние вкладок» должен войти в этот путь, а не заменять его: приёмник получает и `SpoolItem`, и `FileEncoding`.
- **Открытие с состоянием.** `addLogFile(path, FileEncoding)` (F-1: `--encoding`, память файла) и нормализация пути с отсевом второго написания того же файла (`LogViewWidget::samePath`, R-1). Отсев дубликатов для сжатого файла — по источнику (`path` + `member`), как и было в дизайне.
- **Идентичность источника и сохранённое состояние (R-1, R-4, R-5) — новое для F-2.** Закладки, история, память файла, сессия, `last-session.json` и стек `Ctrl+Shift+T` сохраняют `SourceIdentity` (путь, размер, отпечатки начала и 4 КБ перед концом прочитанного) и `RecordId` (номер строки + отпечаток). Если для сжатого файла сохранить `filePath`, состояние привяжется к временной копии: после перезапуска её нет — источник `Missing`, закладки «ждут файл». Решение для PR 2: у сжатого источника `SourceIdentity::path` — путь архива (и имя члена архива), отпечатки — по распакованному содержимому, как сейчас (номер строки и отпечаток строки относятся к распакованному тексту, а он для того же архива один и тот же). Проверка такой идентичности (`check`/`checkAt`) без распаковки невозможна, поэтому до распаковки источник — «ожидает», а после — проверяется по копии обычным путём; `SessionFile::rebind` ищет файл архива. Ключ памяти файла (`FileMemoryStore`, нормализованный путь) — путь архива плюс член; поиск по содержимому для сжатого источника не делается до распаковки (дорого) — только по пути. Формат `documentstate` / `filememorystore` при этом получает необязательное поле «член архива» — версия формата не растёт, если поле необязательное. Закрепить тестом в `document_state`: `.gz` → закладка → закрыть → открыть → закладка на месте; сессия с `.gz`, перенесённая вместе с архивом.
- **Кодировка распакованного файла** определяется обычным правилом F-1 (`EncodingDetector::advance`) — распакованная копия для чтения обычный файл. Ручной выбор хранится в памяти файла по ключу источника (выше).
- **Протокол второго экземпляра** (`SingleInstance`) не имеет версии (известное ограничение F-1, шаг 4): если F-2 или F-7 поменяют то, что передаётся первому окну, старое окно примет новый аргумент за путь. Менять протокол — с версией.
- **Сканер.** Ротированные имена без сжатия (`app.log.1`, `app.log-20260101`) уже в дереве (Q-10), `.gz`, `.1.gz` правило Q-10 намеренно отсекает (`scannerNameMatches`) — PR 3 расширяет именно его. Счётчики (`LogParser::analyzeFileForStats`) читают сырые байты по кодовым единицам кодировки без `QTextStream` (Q-15, Q-18), фильтр по содержимому — `FileContentSearch::search(path, …)` в ядре (F-1, шаг 5) с определением кодировки; обоим PR 3 даёт вход `QIODevice`, а не путь. Последний пункт «Решений за автором» про ротированные имена закрыт Q-10.
- **Save View As** сравнивает идентичность файлов (`ViewExport`), как и было; защищать нужно и архив, и копию.
- **Где показывается путь.** Добавились: панель Bookmarks и Session Report (путь файла закладки и источника), индикатор кодировки (имя файла текущей строки), плашка памяти файла. Все они должны брать `displayPath()`.

## Решение

### Распаковка во временный файл

Сжатый источник целиком распаковывается на диск в фоне, после чего открывается обычным путём. Индекс, кэш текста, воркеры, `FileChangeDetector` и оба бэкенда не меняются: они видят простой файл с байтовыми смещениями.

### Источник и данные в `LogFile`

`filePath` остаётся путём, откуда читают, — как уже сделано для stdin. Добавляется описание того, что открыл пользователь:

```cpp
struct LogSource {
    enum class Kind { File, Archive, Stream };
    Kind    kind = Kind::File;
    QString path;    // лог или архив на диске; пусто у потока
    QString member;  // имя внутри zip/tar; пусто у .gz
    QString label;   // подпись потока: «stdin», командная строка (F-7)
};
```

- `LogFile::source` и `LogFile::spool` (`shared_ptr<SpoolItem>` — владелец временного файла).
- `displayPath()` — что показывать: `C:\logs\app.log.gz`, `bundle.zip › logs/app.log`.
- `orderKey()` — ключ порядка при равном времени: путь источника плюс имя внутри архива; для обычного файла равен `filePath`, поведение не меняется. Оба компаратора переходят на него одновременно.
- Правило в заголовке `logfile.h`: пользователю показывать `displayPath()`, на диск сохранять `source`, читать по `filePath`.

### Временные файлы

- **Где:** `QStandardPaths::CacheLocation` + `/spool/<pid>-<случайное>/`. Не `QDir::temp()`: на части Linux-систем `/tmp` лежит в оперативной памяти (предположение о типичных дистрибутивах, не проверялось).
- **Кто владеет:** `SpoolItem` удаляет свой файл или каталог, когда исчезает последний `LogFile`, который на него ссылается. Search Results делит записи с вкладкой, поэтому файл живёт, пока его кто-то может читать.
- **Удаление — не на GUI-потоке:** каталог на десятки гигабайт удаляется фоновой задачей.
- **После падения:** в каталоге экземпляра лежит `QLockFile`. При старте фоновая уборка удаляет каталоги, чью блокировку удалось взять (владелец мёртв). По документации Qt `QLockFile` распознаёт блокировку умершего процесса; закрепить тестом.
- **Windows:** файл, открытый воркером, не удалится — остаётся до уборки при следующем старте.

### Место на диске

- **До начала.** Нижняя оценка для gzip — большее из размера сжатого файла и поля ISIZE в конце (настоящий размер не меньше ISIZE: поле хранит его по модулю 4 ГБ). Для zip размеры точные, из оглавления. Если свободного места меньше оценки плюс резерв 512 МБ — отказ с цифрами, распаковка не начинается.
- **Во время.** Свободное место проверяется каждые 64 МБ записи; падение ниже резерва останавливает распаковку с ошибкой «не хватило места», частичный файл удаляется. Это же защищает от zip-бомбы.

### Вкладка

- `addLogFile(path)` по сигнатуре решает, что файл сжат, заводит `LogFile` с заранее выбранным временным путём и состояние `unpacking`. Вкладка сразу получает имя.
- Прогресс — по прочитанным сжатым байтам. Статус-бар: «Unpacking app.log.gz… 43 %» и кнопка отмены по образцу Cancel Save. Закрытие вкладки отменяет распаковку и ждёт воркер не дольше одного блока.
- По завершении запускается прежний код выбора бэкенда — уже по размеру распакованного файла.
- Ошибка (не gzip, обрыв, CRC, место, запись) — файл помечается незагруженным, причина показывается текстом.
- Конвертация вкладки в индексную пропускает файлы, которые ещё распаковываются.
- Отсев дубликатов сравнивает источники, а не временные пути.

### Перезагрузка и авто-обновление

- Тик авто-обновления сжатые источники пропускает: дозаписи у них не бывает, а молча перераспаковывать гигабайты из-за ротации нельзя.
- `F5`: если подпись архива изменилась — строки файла сбрасываются, архив распаковывается заново в тот же временный путь, файл загружается с нуля. Это тот же сценарий, что «файл переписан» у обычного лога.
- Архив исчез — строки остаются: распакованная копия самодостаточна. `F5` сообщает, что источник не найден.

### Что видит пользователь

| Место | Что показано |
| --- | --- |
| Имя вкладки, плашка файла | `app.log.gz`; для файла из архива — имя файла |
| Подсказка вкладки, Entry Details, «копировать путь» | `displayPath()` и размер распакованной копии |
| «Показать в проводнике» | архив |
| Недавние файлы | путь архива; повторное открытие распаковывает заново |
| Save View As | защищены и архив, и временная копия |
| Диалог открытия | в фильтр добавлены `*.gz *.zip *.tar *.tgz` |

### Слияние вкладок

`LogViewWidget` получает `addLogFile(const LogOpenRequest&)`: путь, `LogSource` и `SpoolItem`. `mergeTabs` передаёт запрос от существующего `LogFile`, приёмник делит ту же временную копию — без повторной распаковки и без удаления файла из-под читателя.

### Архивы с набором файлов

- Архив извлекается во временный каталог: только файлы, подходящие под расширения из настроек, и `.gz`. Затем каталог показывается в Directory Scanner как обычная папка с подписью «`bundle.zip`» и кнопкой возврата к прежнему корню.
- Так сканер, счётчики, фильтр по содержимому, открытие и слияние работают без изменений.
- Реестр «временный каталог → архив» даёт файлам оттуда `LogSource{Archive, архив, имя}`.
- Имена из архива обезвреживаются: `..`, абсолютные пути, буквы дисков, символические ссылки и зарезервированные имена Windows отбрасываются или заменяются; недопустимые символы — на `_`.
- `.gz` проверяется после первого распакованного блока: заголовок tar означает архив, иначе это одиночный лог.

### Сканер каталога

- В дерево попадают `.gz`, у которых в имени без `.gz` есть компонент из списка расширений: `app.log.gz`, `app.log.1.gz`.
- Счётчики и фильтр по содержимому читают `.gz` потоком, без записи на диск: `GzipDevice` — последовательный `QIODevice`, `analyzeFileForStats` и `ContentMatcher` принимают устройство вместо `QFile`.
- Прогресс фильтра считается в сжатых байтах. Дочитывание с якоря для `.gz` отключено: изменившийся файл анализируется заново.
- Колонка Size показывает размер на диске.

### Зависимость

Встроенный miniz в `third_party/miniz/`, отдельной статической целью, приватно слинкованной с `dendrolog_core`. По моим сведениям (проверить при реализации): лицензия MIT, есть inflate и чтение zip с zip64, заголовок gzip библиотека не разбирает — нужен свой разбор заголовка, CRC32 и многочастности, около сотни строк. tar читается своим кодом.

Упаковщикам ничего не добавляется: библиотека статическая, `windeployqt`, Inno Setup и AppImage не меняются. В `CMakeLists.txt` — `LANGUAGES C CXX`; в `README.md` и `LICENSE` — упоминание miniz.

### Что переиспользует F-7

`SpoolDir`/`SpoolItem` (место, время жизни, уборка после падения), `LogSource{Stream, label}` (имя вкладки, отсутствие в недавних файлах, запрет `F5`), `LogOpenRequest` (слияние вкладок). Спулер stdin стоит перевести на них же: уйдут частный случай в `updateTabLabel` и мёртвая запись в недавних файлах. Сам распаковщик F-7 не нужен: поток идёт существующим путём растущего файла.

## Отвергнутые варианты

| Вариант | Почему нет |
| --- | --- |
| Читать gzip без распаковки, с индексом по распакованным смещениям | Индексному бэкенду нужен произвольный доступ: кэш читает куски по 4 МБ, воркеры ходят вперёд и назад. ### PR 1. Ядро — 19 ноября 2026

Новые файлы ядра (`DENDROLOG_CORE_SOURCES`, без Qt Widgets): `src/gzipdevice.*`, `src/spooldir.*`, `src/sourceunpacker.*`; `src/logfile.*` — `LogSource`, `source()`/`setSource()`, `displayPath()`, `orderKey()`, `spool`. miniz 3.0.2 — `third_party/miniz/` (своя статическая цель, приватно у `dendrolog_core`), `LANGUAGES C CXX`, упоминание в `LICENSE` и `README.md`. Тест — новый `tests/unpack`. Пользователь пока ничего не видит: открытие `.gz` во вкладке — PR 2.

**Зависимость проверена.** Архив релиза `miniz-3.0.2.zip` (SHA-256 `ada38db0b703a56d3dd6d57bf84a9c5d664921d870d8fea4db153979fb5332c5`, версия, URL — `third_party/miniz/README.md`); лицензия MIT, как и предполагалось. В репозитории — только `miniz.c`, `miniz.h`, `LICENSE`, байт в байт (`-text` в `.gitattributes`, чтобы `core.autocrlf` их не трогал). Предположения раздела «Зависимость» подтвердились: заголовок gzip miniz не разбирает (свои ~150 строк: все флаги, FHCRC, склейка, хвост), inflate — `mz_inflate` в raw-режиме, CRC-32 — `mz_crc32`. Предупреждения чужого кода гасятся флагами цели (`-w`, `/W0`, `_CRT_SECURE_NO_WARNINGS`), `MINIZ_NO_ZLIB_COMPATIBLE_NAMES` убирает макросы `crc32`/`inflate`.

**Скорость (риск «Скорость» закрыт).** Лог генератора `scripts/generate_test_log.py --size 1G` (1 073 741 926 байт, 11,6 млн строк), `gzip -6` → 173 МБ. Облачная машина, 4 ядра, Release, `unpack --bench`, два прогона: только `GzipDevice` (inflate + CRC, без записи) — 6,06–6,09 с, **~168 МБ/с распакованного**; `SourceUnpacker` целиком (чтение, inflate, CRC, запись на диск, проверки места) — 6,42–6,63 с, **~155–160 МБ/с**. Для сравнения `gzip -dc` того же файла в `/dev/null` — 5,6 с: miniz медленнее zlib на ~8 %. Гигабайт распаковывается за ~6,5 с — того же порядка, что индексация (2 ГБ за 10–13 с), узким местом не выглядит; менять декодер за интерфейсом `GzipDevice` не нужно.

**Решения сверх документа:**

- **Компараторов три, а не два.** Ключ строки резидентного хранилища (R-1, сравнение записи с `RecordKey` в `residentlogstore.cpp`) — зеркало `LogEntry::operator<`; на `orderKey()` переведены все три одним коммитом, иначе `rowForKey` искал бы двоичным поиском в другом порядке. `logstore_equivalence` — без изменений результата. Ключ: у обычного файла и потока — `filePath` (ссылка, без выделений на сравнение), у `.gz` — путь архива, у члена zip/tar — путь архива + `\x01` + имя (члены одного архива идут подряд, сразу за ним).
- **`displayPath()`** не переводит разделители в нативные — как и `filePath` обычного файла, это делает место показа. Подпись пустого потока — `displayName`, не временный путь.
- **Блокировка — рядом с каталогом экземпляра** (`<root>/<pid>-<16 hex>.lock`), а не в нём, как было в «Временных файлах». Экземпляр сначала берёт блокировку, потом создаёт каталог; с блокировкой внутри между `mkdir` и `lock` чужой уборщик видел бы «каталог без живой блокировки» и удалял бы его. Каталог экземпляра без блокировки уборщик считает сиротой. Трогает он только имена вида `<цифры>-<16 hex>`: корень, заданный по ошибке на чужой каталог, ничего не потеряет.
- **`QLockFile` без устаревания по возрасту** (`setStaleLockTime(0)`): по умолчанию Qt считает брошенной блокировку старше 30 с, даже если владелец жив. Мёртвого владельца он распознаёт по PID (и на Linux дополнительно не удаляет файл под живым `flock`). Закреплено тестом: дочерний процесс, убитый `kill`, — его каталог убран; живой дочерний и свой — нет.
- **`SpoolItem` удаляет файл задачей в глобальном пуле** и держит `shared_ptr` на `SpoolDir`; последний элемент там же удаляет каталог экземпляра. Без `QCoreApplication` — синхронно. `SpoolDir::removeOrphans` синхронный: в фон его ставит вызывающий (PR 2, при старте). `SpoolDir::defaultRoot()` — `CacheLocation/spool`; ядро про `AppSettings` не знает, корень — параметр `create(root)`.
- **Нули после последнего потока gzip — не ошибка** (как у `gzip -d`: выравнивание блоков ленты), любой другой хвост — `TrailingGarbage`. Пустой файл и текст — `NotGzip`; обрыв в заголовке, данных или хвосте — `Truncated`.
- **gzip-«бомба» — правило документа, без отдельного предела.** Предела на размер распакованного или отношение сжатия нет: «Место на диске» уже решает это проверкой свободного места каждые 64 МБ против резерва 512 МБ. Тест: 48 МБ нулей (сжато в сотни раз) с честной ISIZE отклоняются до начала, с ложной ISIZE (как у потока больше 4 ГБ, где поле переполнилось) — останавливаются по ходу, не записав больше «диск − резерв + интервал», частичный файл удалён. Функция «сколько свободно» вернула −1 (неизвестно) — проверка пропускается, а не запрещает распаковку.
- **Одно задание на `SourceUnpacker`** (как `LogParser` на файл): второе при занятом воркере — отказ (`unpackGzip` → 0). Занятость — атомарный флаг, который воркер снимает сразу после отправки итога, а не queued-слот: после `cancel()` + `waitForFinished()` новое задание стартует немедленно (F5 в шаге 2). Чтобы запоздавший итог прежнего задания не приняли за новый, `unpackGzip` возвращает номер задания, он же — `Result::job`. Перед созданием целевого файла проверяются сигнатура (не-gzip не оставляет даже пустого файла) и «цель — не сам источник» (тот же путь или ссылка: иначе открытие на запись обнулило бы источник, а уборка после ошибки — удалила). Сообщения ошибок — английские, как интерфейс; в `Result` — и код (`Error`, `GzipDevice::Error`), и цифры места (`requiredBytes`, `availableBytes`).
- **Отмена не ждёт конца файла.** У `GzipDevice` есть флаг прерывания (`setAbortFlag`): он проверяется на каждом блоке источника (256 КБ сжатого), поэтому вход без вывода — гигабайты нулей в конце, миллионы пустых потоков, длинный FCOMMENT — не держит один `read()` до конца файла; распаковщик передаёт ему свой флаг отмены. CRC заголовка (FHCRC) считается на ходу, байты заголовка не копятся: FNAME и FCOMMENT ничем не ограничены. Устройство поверх чужого закрытого источника само его открывает и само закрывает; открытый вызывающим — читает с текущей позиции и оставляет открытым.
- **Воркеры — `QtConcurrent::run` в свой пул**, как у `LogParser`/`LogIndexer` (у `SpoolItem` — в глобальный), а не голый `QThreadPool::start(лямбда)`: такую передачу слой TSan (`tests/sanitizers/tsan_qt_sync.cpp`) не видит, и первый прогон под TSan дал 43 ложных отчёта. Слой не дополнялся: распаковщик передаёт данные только этим путём и сигналами из воркера. У цели `miniz` выключены AUTOMOC/UIC/RCC: иначе она получала пустой C++-файл moc, а сборка под TSan подключает в каждый C++-файл заголовок Qt, которого у цели нет.
- **`orderKey()` внутри вкладки обязан быть единственным** (правило — в комментарии `logfile.h`): при равных ключах бэкенды разрешают ничью по-разному (резидентный — по id записи, индексный — по номеру файла). Обычные файлы этого не нарушают — их вкладка отсеивает по пути; для сжатых шаг 2 отсеивает дубликаты по источнику, как и сказано в «Вкладке». Общий последний ключ «идентичность файла» для обоих бэкендов не вводился: у резидентного нет номера файла, а указатель между бэкендами не сравним.
- **При завершении приложения** (`QCoreApplication::closingDown()`) `SpoolItem` удаляет синхронно: пул мог уже отработать `waitForDone` и задачу не выполнить.

**Что знать шагам 2 и 3.** Шаг 2: `LogFile` создаётся по пути копии (`SpoolDir::createFile(имя без .gz)`), затем `setSource({Archive, путь .gz})` и `spool = item` — ДО передачи парсеру или хранилищу; `displayPath()` — во все места показа пути; `SourceUnpacker` — один на распаковываемый файл, результат — `finished(Result)`; `SpoolDir` и фоновый `removeOrphans` при старте — у окна. Шаг 3: `GzipDevice` — последовательный `QIODevice` по пути или по чужому устройству, прогресс — `compressedBytesRead()`, сигнатура — `GzipDevice::fileHasSignature`.

### PR 2. Вкладка и окно — 25 ноября 2026

`.gz` (по сигнатуре `1F 8B`, не по имени) открывается вкладкой отовсюду — диалог Open (в фильтре `*.gz`), бросок, командная строка, недавние, сканер, второй экземпляр: все идут в `LogViewWidget::addLogFile`. Там сжатый файл заводится `LogFile` по пути копии в `SpoolDir` (`app.log.gz` → `<spool>/<pid>-…/N-app.log`) с `source() = {Archive, путь .gz}`, `displayName` — имя архива, `spool` — `SpoolItem`; копию пишет `SourceUnpacker` (по одному на файл, ребёнок вкладки). По концу распаковки — обычный путь (`startLoad`: бэкенд по размеру копии). Пока идёт распаковка, вкладка `isLoading()`; сигналы `unpackingStarted/Progress/Finished`; окно показывает «Unpacking app.log.gz… 43 %» и кнопку **Cancel Unpacking** по активной вкладке. Ошибка — `fileParsingFailed`, причина — `loadFailureMessage` («Cannot open app.log.gz: …» с текстом `SourceUnpacker`). Места показа пути — `displayPath()` (подсказка вкладки, Copy Path, Entry Details, панель Bookmarks, заметка закладки, индикатор кодировки, Go to, легенда — уже была); Show in Folder — папка архива; подсказка вкладки — и размер копии. Save View As защищает архив и копию (`ViewExport::protectedPaths`). Уборка сирот — `SpoolDir::removeOrphans` при старте окна в `QtConcurrent::run`.

Идентичность сжатого источника (раздел «Что изменилось к 0.6.0»): `SourceIdentity` получил необязательные `compressed`, `member` и отпечатки самого архива (JSON `"compressed":true`, `"member"`, `"archive":{size,head,tail}`; версия формата 1 та же, `member` или `archive` без `compressed` — отказ). Путь — архив, `size/head/tail` — распакованного содержимого. `SourceIdentity::capture(const LogFile&)` снимает содержимое по копии, путь — источника. `RecordLocator` ключует ожидающие запросы по ключу источника (`RecordLocator::sourceKey`: путь архива [+ `\x01` + член]), содержимое сверяет `checkContentAt(копия)`; сброс строк (`fileReset`) — по пути чтения. Закладки сравнивают источник так же (`BookmarkStore::restore`). Тест — новый `tests/compressed_tabs` (оба бэкенда) и проверки в `record_identity`, `open_routing`, `mainwindow_smoke`.

**Решения сверх документа:**

- **Проверка сжатого источника без распаковки — по отпечаткам архива.** Документ предполагал состояние «ожидает до распаковки». Вместо него идентичность сжатого источника хранит и отпечатки самого `.gz` (те же два чтения по 4 КБ при снятии): `checkAt(путь)` — тот же архив → Valid, другой gzip → Changed, нет или не gzip → Missing; без отпечатков архива (не сняты) — «есть и gzip» → Valid. Содержимое — `checkContentAt(путь чтения)` по копии, когда она готова. На этом без изменений работают `applyState` (отчёт о пропавших и изменённых), `SessionFile::rebind` (сессия, перенесённая вместе с архивом, находит его по относительному пути, даже если по прежнему абсолютному лежит другой архив после ротации), «Locate File» отчёта сессии и решение «копия или перенос» памяти файла. Архив, сжатый заново с тем же содержимым, по отпечаткам архива — Changed (откроется, закладки найдутся по копии). switch-и по `SourceIdentity::State` во всех хранилищах остались прежними. Найдено ревью: первая версия (только «есть и gzip») принимала любой gzip по пути.
- **Память файла — после распаковки, а не до.** Документ предлагал искать память `.gz` только по пути до распаковки. Ищется после: `FileMemoryStore::open(путь архива, путь копии)` — ключ по архиву, содержимое по копии во всех трёх случаях (по пути Valid / переписан → отсоединение / по содержимому). Поиск по содержимому с готовой копией стоит те же два чтения по 4 КБ, а ротация `app.log.1.gz → app.log.2.gz` иначе нашла бы по пути чужую память. Следствие: лог, сжатый заново (другие байты архива, то же содержимое), и лог, распакованный пользователем (`app.log.gz` → `app.log`), находят свою память по содержимому — `FileMemory::relocate(путь, compressed)` переносит её в обе стороны. Флаги вызова `addLogFile` (снимок, перенос вкладки) распаковка хранит и восстанавливает перед памятью (`ArchiveState`).
- **Отмена — файл остаётся незагруженным** с причиной «unpacking was cancelled», F5 пробует снова (как ошибка); из вкладки он не убирается — простое обратимое.
- **Время копии — время архива** (`QFile::setFileTime`): опорная дата года syslog (`LineClassifier::yearReferenceForFile`) — когда лог писали, а не когда распаковали.
- **F5:** архив пропал — сообщение, строки остаются; не изменился (размер и mtime архива как при распаковке) — ничего; изменился — строки сбрасываются ДО распаковки в тот же путь (индексный бэкенд читает текст копии с диска), затем полная перезагрузка. Неудачная или отменённая распаковка по F5 повторяется всегда. Тик авто-обновления сжатые файлы пропускает целиком, и вкладка с одним `.gz` не конвертируется по порогу на тике (копия не растёт).
- **Конвертация в индексную** пропускает файлы, чья загрузка ещё не началась (распаковка идёт, сорвалась или ждёт памяти, `isArchivePending`); такой файл грузит конец его распаковки — уже в индексную вкладку.
- **Снимок посреди распаковки** не снимает идентичность с недописанной копии (`captureState`, `isArchivePending` — и при перераспаковке по F5): берётся прежняя (снятая перед F5) или та, с которой файл открыт из снимка (`applyState`); файл, открытый впервые и ещё не распакованный, в снимок не попадает — помнить о нём нечего. `--encoding` для такого файла запоминается до загрузки копии, недописанная копия не перечитывается.
- **Скрытый файл снимка (U-23), который сжат,** скрывается, когда начинается загрузка его копии (`m_hiddenArchiveSources`): путь копии при `applyState` ещё неизвестен.
- **Слияние вкладок** (`addFilesFrom`): распакованный файл переезжает новым `LogFile` с тем же `SpoolItem`, без повторной распаковки; ещё распаковывающийся — распаковывается в приёмнике заново. `LogOpenRequest` из «Слияния вкладок» не понадобился — хватило `addFilesFrom`.
- **Каталог экземпляра один на процесс и корень** (слабая ссылка в `LogViewWidget`): вкладки делят каталог и блокировку; корень — `AppSettings::spoolRoot()` (кэш приложения и в portable-режиме; при `overrideConfigDirForTesting` — `<configDir>/spool`), у вкладки — `setSpoolRoot` для тестов.
- **Деструктор вкладки** отменяет и ждёт распаковщики ДО освобождения файлов: иначе `SpoolItem` удалял бы копию, пока воркер в неё пишет.
- **Тест — отдельный `tests/compressed_tabs`**, а не дописки в `logview_lifecycle` (~на критическом пути параллельного прогона), `document_state` и `viewexport`: сценарии F-2 делят фикстуры (gzip из `tests/common/gzipbytes.h` — `qCompress` + свой заголовок, тестам виджетов не нужен miniz) и идут параллельно с остальными, ~5 с.

- **Серые закладки после F5:** `BookmarkStore::invalidateFile` узнаёт файл по пути чтения, а ждущая закладка знает путь архива — перераспаковка зовёт `BookmarkStore::recheckSource(ключ источника)`.
- **Строка состояния** показывает распаковку только активной вкладки; смена вкладки и закрытие убирают прогресс и кнопку **Cancel Unpacking**, переключение на распаковывающуюся вкладку показывает кнопку, а процент — со следующего события прогресса.

**Осталось:** ключ памяти файла с членом архива (`path` + `member`) — шаг 4 (zip).

### PR 3. Сканер — 25 ноября 2026

`.gz` в дереве Directory Scanner, счётчики (`LogParser::analyzeFileForStats`) и фильтр по содержимому (`FileContentSearch::search`) читают его потоком через `GzipDevice`, без записи на диск. Затронуты `src/directoryscanner.*` (правило имён), `src/logparser.cpp`, `src/filecontentsearch.*`, одна строка `src/textencoding.cpp`; тест — `tests/dirscanner_smoke` (+ `tests/common/gzipwriter.h`, сжатие фикстур через miniz). Критерий: счётчики `.gz` и колонки дерева (Entries, From, To, W/E/F) равны несжатому близнецу — многострочные записи, CRLF, оборванный хвост, BOM UTF-8, UTF-16 LE/BE, cp1251, syslog, пустой, склеенные потоки, 3 МБ в четырёх потоках; фильтр отвечает как близнец на всех запросах `cyrillicProbes` в семи кодировках и четырёх размерах блока, в сценариях предварительного решения (в том числе с перечитыванием); прогресс доходит ровно до размера файла на диске; отмена посреди файла. До реализации тест давал 667 отказов.

**Решения сверх документа:**

- **Читать как `.gz` — по сигнатуре, показывать в дереве — по имени.** `analyzeFileForStats` и `FileContentSearch::search` узнают сжатый файл по `1F 8B` (`QFile::peek`, без второго открытия) — так же, как вкладка узнает его при открытии (PR 2); файл `app.log.gz` с обычным текстом читается как текст, ротация `app.log.1`, сжатая без смены имени, — распаковывается. В дерево `.gz` попадает, если имя без последнего `.gz` проходит правило Q-10 (`scannerNameMatches`): `app.log.gz`, `app.log.1.gz`, `app.log-20260101.gz`; `app.log.bak.gz`, `app.log.gz.1`, `app.tgz` — нет (`.tgz` — архив, PR 5). Если пользователь сам внёс `gz` в список расширений, `.gz` не снимается — работает прежнее правило.
- **`.gz` с якоря не дочитывается.** `analyzeFileForStats` отдаёт у потока `next.offset = 0`, поэтому сканер якоря не снимает и изменившийся файл разбирает заново (дописанный поток `cat more.gz >> app.log.gz` — тоже, закреплено тестом). Запрос продолжения с середины для `.gz` — `parseSuccess = false`, и сканер переходит на полный разбор, а не складывает цифры.
- **Повреждённый архив.** Счётчики — «Parse Failed» (обрыв, CRC, мусор): вкладка такой архив не откроет (распаковщик удаляет результат при любой ошибке), полсчёта вводили бы в заблуждение. Фильтр по содержимому: `readable = false`, а находка до места ошибки остаётся находкой — поиск, нашедший строку, до ошибки просто не дочитывает (оборванный архив, который ещё пишется, полезно находить).
- **Окно решения о кодировке у потока.** `EncodingDetector::advance` дочитывает окно 64 КБ, не уместившееся в порцию, вторым дескриптором по пути — у `.gz` там сжатые байты. Правило не менялось: пустой путь теперь значит «окно только из порции» (без попытки открыть файл), а поиск по `.gz`, пока кодировка не решена, дочитывает блок вперёд до 64 КБ за первым байтом ≥ 0x80 (`Reader::extend`). Окно получается то же, что у файла; остаток порции за окном идёт в свидетельство сразу, а не следующим блоком, — от порций итог не зависит (свидетельство сжато, тест `textencoding`), и ответ сравнивается с близнецом на четырёх размерах блока.
- **Перечитывание после пересмотра** (предварительные строки не влезли в 16 МБ) у потока — заново с начала и пропуск до нужного места; прогресс при этом не растёт (считаются сжатые байты, прочитанные впервые).
- **Прогресс — сжатые байты** (`compressedBytesRead`), итог файла (`bytesRead`) — тоже: сканер доливает до размера на диске, как и раньше. Флаг отмены передан `GzipDevice::setAbortFlag`: вход без вывода не держит блок. Тестовый крючок `afterBlock` получает смещение в распакованном потоке.
- **Предел строки в счётчиках и отмена (по ревью).** Маленький `.gz` из одних нулей распаковывается в гигабайты без `'\n'`, а попадает в разбор просто потому, что лежит в папке. `analyzeFileForStats` считает строку длиннее `kMaxStatsLineBytes` (4 МБ) по голове этой длины (метка и уровень — в начале строки; остаток только ищет её конец), и поиск `'\n'` продолжается с конца прочитанного, а не с начала строки — прежде длинная строка перечитывалась на каждый мегабайт (это было и у обычных файлов). Счётчики принимают флаг отмены (`cancelled`, он же — `GzipDevice::setAbortFlag`); сканер поднимает его новым `scan()` и в деструкторе, так что брошенный разбор большого архива не держит поток пула и выход из программы. Прерванный разбор — `parseSuccess = false`, его итог сканер отбрасывает (дерева, для которого он шёл, уже нет).
- **Расширение `gz` или `log.gz` в настройках** работает как прежде: сначала проверяется полное имя, затем имя без `.gz`.
- **Год syslog у `.gz`** — по mtime самого `.gz` (`yearReferenceForFile(filePath)`), как у любого файла сканера. **Для PR 2:** вкладка читает распакованную копию, mtime которой — время распаковки; опорную дату для `.gz` вкладке брать у источника (`LogSource::path`), иначе метки syslog без года у сканера и вкладки могут разойтись на годе (архив прошлого года, открытый в январе).
- **Открытие `.gz` из сканера во вкладку — PR 2.** Сканер передаёт путь окну как раньше; до PR 2 вкладка покажет сжатые байты как текст.
- **Цена.** Отдельно не замерялась: разбор `.gz` упирается в `GzipDevice` (~168 МБ/с распакованного, замер PR 1), для сравнения — несжатый файл сканер читает со скоростью диска. Риск «Сканер» (папка с десятками больших `.gz` грузит процессор) остаётся: счётчики идут в пуле с прежним пределом параллельности.

- **Реестр — один на процесс** (`ArchiveRegistry::instance()`, GUI-поток), а не у панели: путь из каталога извлечения приходит во вкладку любой дорогой (двойной щелчок, Open с выбором, бросок файла из дерева), и `addLogFile` узнаёт его сам. Запись держит `SpoolItem` каталога; посторонний файл в каталоге (не из списка извлечённых) членом не считается.
- **Член — по имени, как записано в архиве** (`/`-разделители), в `LogSource::member`, `SourceIdentity::member` и ключе памяти (`keyFor`: нормализованный путь архива, `\x01`, имя — у каждого лога архива своя память). Имена без флага UTF-8: корректный UTF-8 — UTF-8, иначе IBM866 (OEM-кодировка русской Windows, «Сжатая ZIP-папка»). Правило без локали: по сохранённому имени член ищется снова; западное имя в CP437 покажется кириллицей, но извлечётся.
- **Отбор членов** — правило имён сканера (`scannerNameMatches` по имени файла, расширения из настроек — `DirectoryScanner::effectiveExtensions`), поэтому `.gz` логов (`app.log.1.gz`) тоже извлекаются и в каталоге остаются `.gz` (сканер читает их потоком, PR 3); вкладка такого члена получает текст — `unpackZipMember` распаковывает член-gzip дальше.
- **Опасные имена.** Отбрасываются: `..`, абсолютные пути (`/`, `\\`), буквы дисков (`C:`), символические ссылки (Unix-атрибуты), каталог-член; заменяются: `<>:"|?*` и управляющие — `_`, хвостовые точки и пробелы — убираются, зарезервированные имена Windows — префикс `_`. Повтор пути (регистр, хвостовая точка) — суффикс `~N`; файл, чьё имя занято каталогом другого члена, — пропуск. Вторая линия — путь после `cleanPath` обязан начинаться с каталога извлечения. Пропущенные и члены с паролем считаются, панель говорит о них строкой статуса.
- **Целостность** — своя: длина и CRC-32 по выданным байтам (итератор miniz у хранимых членов CRC не сверяет); член, разворачивающийся больше заявленного, — ошибка (miniz останавливает inflate). Любая ошибка члена — ошибка всего извлечения, каталог удаляется целиком: полархива в сканере вводил бы в заблуждение (как «Parse Failed» у битого `.gz`).
- **Место.** До начала — сумма размеров ОТОБРАННЫХ членов из оглавления плюс резерв 512 МБ (размеры оглавления точные; ложный размер ловит проверка по ходу и предел miniz); у одного члена — его размер, у члена-gzip перед распаковкой — ещё и оценка gzip. Прогресс zip — распакованные байты из суммы размеров.
- **Подпись и возврат.** Подпись пути — имя архива (подсказка — путь архива и что файлы временные), временный путь не показывается. «Назад» — к папке, показанной до ПЕРВОГО архива (архив поверх архива заменяет его, «назад» ведёт к той же папке; папки не было — дерево очищается). Скан папки, другой архив и «назад» отпускают каталог (удаляется в фоне). Пока идёт извлечение, «назад» его отменяет — иначе первое извлечение большого архива нечем остановить. Ошибка архива оставляет показанное.
- **Маршрутизация.** `OpenRouting::plan` узнаёт архив по имени (`.zip` в любом регистре); каталоги и архивы делят один корень сканера — первый по порядку передачи, остальные названы пропущенными. zip под другим именем ловит `MainWindow::openRecentFile` по сигнатуре (через него идут недавние, командная строка, бросок и второй экземпляр), диалог Open — тем же правилом. Сам zip во вкладке (`addLogFile` напрямую) не читается как текст — сообщение «откройте в Directory Scanner».
- **Недавние** — архив, а не файл из каталога извлечения: `RecentFiles::accepts` такие пути не берёт (как спул stdin), окно кладёт вместо них архив. Повторное открытие архива из недавних — снова сканер. Протокол второго экземпляра не менялся: передаются те же пути.
- **Строка статуса окна** получила `objectName` `statusMessageLabel` — оконный тест проверяет сообщение о битом архиве.

**Ревью (`/code-review high` по диффу шага).** Восемь находок, все исправлены: панель не проверяла, что каталог извлечения создан (`createDirectory` → nullptr, падение при нехватке места в спуле); член с повторяющимся именем открывался бы первым — теперь извлекается только первый, второй считается пропущенным (`unpack`); отмена извлечения ждала на GUI-потоке, пока воркер удалит извлечённое (гигабайты), — теперь распаковщик отцепляется и удаляет себя по итогу, следующее извлечение берёт новый (`dirscanner_smoke`: архив поверх идущего извлечения); `unpackZip` не удалял каталог при ошибке оглавления и `mkpath`; несколько zip в Open — остальные молча терялись (теперь строка статуса, как у броска); Save View As предлагал `*.gz`/`*.zip` (текст под именем `.zip` потом открывался бы как архив) — фильтр сохранения без них; прогресс члена-gzip шёл до 100 % и с нуля — вторая стадия шкалу не трогает; подпись прогресса — `.arg` одним вызовом.

**Осталось:** tar (`.tar`, `.tar.gz`, `.tgz`) — шаг 5.
