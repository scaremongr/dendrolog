# F-2. Сжатые файлы и архивы

Статус: черновик (17 ноября 2026, для `0.4.0`). Задача `F-2` из `docs/roadmap.md`, релиз 0.6.

## Задача и границы

Файл от клиента открывается как есть: `app.log.gz` — вкладкой, архив с десятками логов — набором файлов в сканере каталога.

Входит:

- `.gz` с одним логом, включая многочастные (склеенные) gzip. Распознаётся по сигнатуре `1F 8B`, а не только по имени.
- `.zip`, `.tar`, `.tar.gz`, `.tgz` как набор файлов: содержимое показывается в Directory Scanner.
- `.gz` в дереве сканера рядом с обычными логами: счётчики, диапазон времени, фильтр по содержимому.
- Прогресс, отмена, проверка места на диске, уборка временных файлов, в том числе после падения.

Не входит:

- `.bz2`, `.xz`, `.zst`, `.7z`, `.rar`, архивы с паролем — понятное сообщение «формат не поддерживается».
- Архив внутри архива не раскрывается. `.gz` внутри архива остаётся файлом и открывается как обычный `.gz`.
- Чтение сжатого файла без распаковки на диск (см. «Отвергнутые варианты»).
- Кэш распакованных копий между запусками.
- Запись и пересжатие.

## Как устроено сейчас

- **Образец — спулер stdin.** `StdinSpooler` пишет поток в `QDir::temp()/DendroLog-stdin-<pid>.log` (`src/stdinspooler.cpp:36-48`), вкладка открывает этот файл как растущий лог, деструктор файл удаляет (`:32-33`). После падения файл остаётся: уборки осиротевших файлов нет.
- **`LogFile::filePath` — и ключ, и путь чтения.** Структура хранит один путь (`src/logfile.h:10-28`), конструктор берёт из него имя, размер и mtime (`src/logfile.cpp:4-11`). По нему читают парсер (`src/logparser.cpp:77`), индексатор (`src/logindexer.cpp:72`), кэш текста и воркеры (`src/indexedlogstore.cpp:218`, `:549-554`). По нему же ключуется состояние дочитывания (`src/logviewwidget.h:156-181`), отсев дубликатов (`src/logviewwidget.cpp:119-122`) и порядок строк с равным временем (`src/logentry.h:94-95`, `src/indexedlogstore.cpp:511-515`).
- **Бэкенд выбирается по размеру файла на диске** в `LogViewWidget::addLogFile` (`src/logviewwidget.cpp:130-132`). Конвертация вкладки в индексную стирает состояния всех файлов и перезапускает их загрузку (`:135-145`).
- **Перезагрузка смотрит на тот же путь.** `reloadChangedFiles` сравнивает подпись «размер + mtime» и якорь `FileChangeDetector` файла `filePath` (`src/logviewwidget.cpp:491`, `:516`); исчезнувший файл — строки сбрасываются (`:493-503`).
- **Путь показывается пользователю в четырёх местах:** подсказка вкладки (`src/mainwindow.cpp:2342-2355`), Entry Details (`src/entrydetailspanel.cpp:624`), «показать в проводнике» и «копировать путь» (`src/mainwindow.cpp:2433-2460`). Для stdin есть частный случай по совпадению пути со спулом (`:2335-2341`).
- **Недавние файлы получают тот путь, что передан в `openRecentFile`** (`src/mainwindow.cpp:3634-3638`). Спул stdin туда тоже попадает (`:3584`) и после выхода становится мёртвой записью.
- **Слияние вкладок передаёт пути, а не объекты:** `mergeTabs` и `mergeAllTabsInto` заново вызывают `addLogFile(lf->filePath)` и закрывают источник (`src/mainwindow.cpp:2379-2389`, `:2410-2421`).
- **Выбор вкладки для новых файлов написан трижды:** `on_actionOpen_triggered` (`src/mainwindow.cpp:2502-2550`), `onOpenSelectedDirectoryFiles` (`:3436-3476`), `openRecentFile` (`:3601-3638`). Drag&drop и командная строка идут через третий (`:651-665`, `:3561-3568`) и берут только обычные файлы.
- **Save View As защищает `filePath` всех вкладок** (`src/mainwindow.cpp:2578-2588`), сравнение — по идентичности файла (`src/viewexport.cpp:33-74`).
- **Сканер отбирает файлы по последнему суффиксу** (`src/directoryscanner.cpp:799`, `:1375-1381`): `app.log.gz` и `app.log.1` в дерево не попадают. Счётчики считает `LogParser::analyzeFileForStats` через `QFile` и `QTextStream` (`src/logparser.cpp:209-227`), фильтр по содержимому читает `QFile` блоками (`src/directoryscanner.cpp:949-975`, `:1028-1050`). Дозапись дочитывается с якоря (`:529-553`).
- **Сборка:** проект объявлен как `LANGUAGES CXX` (`CMakeLists.txt:3`), сторонних библиотек кроме Qt нет (`:14`), каталога `third_party/` нет. Упаковка — `windeployqt` + Inno Setup и `linuxdeploy` (`.github/workflows/build.yml`).
- **Кэш текста не держит файл открытым** между чтениями (`src/textchunkcache.cpp:57-63`); воркеры держат его открытым на время скана (`src/sequentiallinereader.h:20-27`).

## Решение

### Распаковка во временный файл

Сжатый источник целиком распаковывается на диск в фоне, после чего открывается обычным путём. Индекс, кэш текста, воркеры, `FileChangeDetector` и оба бэкенда не меняются: они видят простой файл с байтовыми смещениями.

### Источник и данные в `LogFile`

`filePath` остаётся путём, откуда читают, — как уже сделано для stdin. Добавляется описание того, что открыл пользователь:

```cpp
struct LogSource {
    enum class Kind { File, Archive, Stream };
    Kind    kind = Kind::File;
    QString path;    // лог или архив на диске; пусто у потока
    QString member;  // имя внутри zip/tar; пусто у .gz
    QString label;   // подпись потока: «stdin», командная строка (F-7)
};
```

- `LogFile::source` и `LogFile::spool` (`shared_ptr<SpoolItem>` — владелец временного файла).
- `displayPath()` — что показывать: `C:\logs\app.log.gz`, `bundle.zip › logs/app.log`.
- `orderKey()` — ключ порядка при равном времени: путь источника плюс имя внутри архива; для обычного файла равен `filePath`, поведение не меняется. Оба компаратора переходят на него одновременно.
- Правило в заголовке `logfile.h`: пользователю показывать `displayPath()`, на диск сохранять `source`, читать по `filePath`.

### Временные файлы

- **Где:** `QStandardPaths::CacheLocation` + `/spool/<pid>-<случайное>/`. Не `QDir::temp()`: на части Linux-систем `/tmp` лежит в оперативной памяти (предположение о типичных дистрибутивах, не проверялось).
- **Кто владеет:** `SpoolItem` удаляет свой файл или каталог, когда исчезает последний `LogFile`, который на него ссылается. Search Results делит записи с вкладкой, поэтому файл живёт, пока его кто-то может читать.
- **Удаление — не на GUI-потоке:** каталог на десятки гигабайт удаляется фоновой задачей.
- **После падения:** в каталоге экземпляра лежит `QLockFile`. При старте фоновая уборка удаляет каталоги, чью блокировку удалось взять (владелец мёртв). По документации Qt `QLockFile` распознаёт блокировку умершего процесса; закрепить тестом.
- **Windows:** файл, открытый воркером, не удалится — остаётся до уборки при следующем старте.

### Место на диске

- **До начала.** Нижняя оценка для gzip — большее из размера сжатого файла и поля ISIZE в конце (настоящий размер не меньше ISIZE: поле хранит его по модулю 4 ГБ). Для zip размеры точные, из оглавления. Если свободного места меньше оценки плюс резерв 512 МБ — отказ с цифрами, распаковка не начинается.
- **Во время.** Свободное место проверяется каждые 64 МБ записи; падение ниже резерва останавливает распаковку с ошибкой «не хватило места», частичный файл удаляется. Это же защищает от zip-бомбы.

### Вкладка

- `addLogFile(path)` по сигнатуре решает, что файл сжат, заводит `LogFile` с заранее выбранным временным путём и состояние `unpacking`. Вкладка сразу получает имя.
- Прогресс — по прочитанным сжатым байтам. Статус-бар: «Unpacking app.log.gz… 43 %» и кнопка отмены по образцу Cancel Save. Закрытие вкладки отменяет распаковку и ждёт воркер не дольше одного блока.
- По завершении запускается прежний код выбора бэкенда — уже по размеру распакованного файла.
- Ошибка (не gzip, обрыв, CRC, место, запись) — файл помечается незагруженным, причина показывается текстом.
- Конвертация вкладки в индексную пропускает файлы, которые ещё распаковываются.
- Отсев дубликатов сравнивает источники, а не временные пути.

### Перезагрузка и авто-обновление

- Тик авто-обновления сжатые источники пропускает: дозаписи у них не бывает, а молча перераспаковывать гигабайты из-за ротации нельзя.
- `F5`: если подпись архива изменилась — строки файла сбрасываются, архив распаковывается заново в тот же временный путь, файл загружается с нуля. Это тот же сценарий, что «файл переписан» у обычного лога.
- Архив исчез — строки остаются: распакованная копия самодостаточна. `F5` сообщает, что источник не найден.

### Что видит пользователь

| Место | Что показано |
| --- | --- |
| Имя вкладки, плашка файла | `app.log.gz`; для файла из архива — имя файла |
| Подсказка вкладки, Entry Details, «копировать путь» | `displayPath()` и размер распакованной копии |
| «Показать в проводнике» | архив |
| Недавние файлы | путь архива; повторное открытие распаковывает заново |
| Save View As | защищены и архив, и временная копия |
| Диалог открытия | в фильтр добавлены `*.gz *.zip *.tar *.tgz` |

### Слияние вкладок

`LogViewWidget` получает `addLogFile(const LogOpenRequest&)`: путь, `LogSource` и `SpoolItem`. `mergeTabs` передаёт запрос от существующего `LogFile`, приёмник делит ту же временную копию — без повторной распаковки и без удаления файла из-под читателя.

### Архивы с набором файлов

- Архив извлекается во временный каталог: только файлы, подходящие под расширения из настроек, и `.gz`. Затем каталог показывается в Directory Scanner как обычная папка с подписью «`bundle.zip`» и кнопкой возврата к прежнему корню.
- Так сканер, счётчики, фильтр по содержимому, открытие и слияние работают без изменений.
- Реестр «временный каталог → архив» даёт файлам оттуда `LogSource{Archive, архив, имя}`.
- Имена из архива обезвреживаются: `..`, абсолютные пути, буквы дисков, символические ссылки и зарезервированные имена Windows отбрасываются или заменяются; недопустимые символы — на `_`.
- `.gz` проверяется после первого распакованного блока: заголовок tar означает архив, иначе это одиночный лог.

### Сканер каталога

- В дерево попадают `.gz`, у которых в имени без `.gz` есть компонент из списка расширений: `app.log.gz`, `app.log.1.gz`.
- Счётчики и фильтр по содержимому читают `.gz` потоком, без записи на диск: `GzipDevice` — последовательный `QIODevice`, `analyzeFileForStats` и `ContentMatcher` принимают устройство вместо `QFile`.
- Прогресс фильтра считается в сжатых байтах. Дочитывание с якоря для `.gz` отключено: изменившийся файл анализируется заново.
- Колонка Size показывает размер на диске.

### Зависимость

Встроенный miniz в `third_party/miniz/`, отдельной статической целью, приватно слинкованной с `dendrolog_core`. По моим сведениям (проверить при реализации): лицензия MIT, есть inflate и чтение zip с zip64, заголовок gzip библиотека не разбирает — нужен свой разбор заголовка, CRC32 и многочастности, около сотни строк. tar читается своим кодом.

Упаковщикам ничего не добавляется: библиотека статическая, `windeployqt`, Inno Setup и AppImage не меняются. В `CMakeLists.txt` — `LANGUAGES C CXX`; в `README.md` и `LICENSE` — упоминание miniz.

### Что переиспользует F-7

`SpoolDir`/`SpoolItem` (место, время жизни, уборка после падения), `LogSource{Stream, label}` (имя вкладки, отсутствие в недавних файлах, запрет `F5`), `LogOpenRequest` (слияние вкладок). Спулер stdin стоит перевести на них же: уйдут частный случай в `updateTabLabel` и мёртвая запись в недавних файлах. Сам распаковщик F-7 не нужен: поток идёт существующим путём растущего файла.

## Отвергнутые варианты

| Вариант | Почему нет |
| --- | --- |
| Читать gzip без распаковки, с индексом по распакованным смещениям | Индексному бэкенду нужен произвольный доступ: кэш читает куски по 4 МБ, воркеры ходят вперёд и назад. В gzip это требует контрольных точек с 32 КБ словаря на каждую и распаковки от точки на каждый промах. Меняются `TextChunkCache`, `SequentialLineReader`, `FileChangeDetector` — самый горячий и самый проверенный код. Выигрыш — только место на диске. Вернуться, если у пользователей архивы больше свободного диска |
| Распаковать в память | Ограничено оперативной памятью, не работает на индексном бэкенде |
| Показывать строки по мере распаковки (временный файл как растущий лог) | Строки после первой порции получили бы пометку «новые», переход порога посреди распаковки переиндексирует файл, два прогресса накладываются. Возможная оптимизация после замеров |
| Системный zlib | На Windows его нет: нужен vcpkg или своя сборка, плюс DLL в установщике. zip всё равно пришлось бы писать отдельно |
| Приватный zlib из Qt | Приватный API без гарантий; в сборках Qt для Linux используется системный zlib, так что понадобились бы две ветки (предположение, не проверялось) |
| libarchive | Покрывает все форматы, но тяжёлая зависимость на обеих платформах. Рассмотреть, если понадобятся `.xz`/`.zst` |
| Внешние `gzip`/`tar` через `QProcess` | Зависит от окружения пользователя |
| `qUncompress`, `QZipReader` | Первый не читает gzip и работает в памяти; второй — приватный API и отдаёт файл целиком в память |
| Раскрывать архив узлом в дереве сканера | Сканер везде ключуется путями на диске (`m_itemMap`, `m_dirMap`, `reconcileLevel`); виртуальный узел — большая переделка. Можно позже |
| Поменять смысл `filePath` на «путь источника» | Меняет около двадцати мест чтения в обоих бэкендах; ошибка там — мусор вместо текста. При выбранном варианте ошибка косметическая: показан временный путь |

## Проверки

- **`tests/unpack` (новый, только ядро).** Фикстуры настоящего gzip зашиты в исходник теста массивами байт: рабочее дерево на Windows с `core.autocrlf`, двоичные файлы в репозитории рискованны. Случаи: один поток, склеенные потоки, заголовок с именем файла, пустой файл, обрыв посередине, неверный CRC, не gzip. Большие входы генерирует сам тест через сжатие miniz.
- **Место на диске** проверяется подменой функции «сколько свободно», без заполнения диска — как ошибки записи в `tests/viewexport`.
- **`logview_lifecycle`.** `.gz` ниже и выше порога (`indexedThreshold = 0`); битый архив и повтор по `F5` после исправления; конвертация вкладки, пока второй файл распаковывается; слияние вкладок и закрытие источника; `F5` при изменённом и при пропавшем архиве; авто-обновление не трогает `.gz`.
- **Корень `SpoolDir` в тестах задаётся явно** (`QTemporaryDir`), настоящий кэш пользователя тесты не трогают.
- Ручная проверка на Windows: архив на несколько гигабайт, отмена, закрытие вкладки, перезапуск после принудительного завершения.

## Риски и затронутые инварианты CLAUDE.md

- **Инвариант 5 (байты, а не символы)** сохраняется: читатели работают с распакованным файлом.
- **Инвариант 3 (обработка батча O(1))** и правило «воркеры получают снапшоты»: распаковщик получает только пути, результат приходит queued-сигналом; деструктор ждёт воркер, как у `LogParser` и `LogIndexer`.
- **Порядок строк (инвариант 11 и `LogEntry::operator<`).** Переход на `orderKey()` обязан пройти в обоих компараторах одним PR; страхует `logstore_equivalence`.
- **Один бэкенд на вкладку.** Конвертация при незавершённой распаковке — новый путь; без защиты индексатор прочитал бы недописанный файл.
- **Ядро без виджетов.** `AppSettings` лежит в `dendrolog_widgets`, поэтому список расширений и корень спула передаются в ядро параметрами.
- **Два пути в `LogFile`.** Новый код может показать временный путь. Смягчение: аксессоры, комментарий в заголовке, строка в карте модулей `CLAUDE.md`.
- **Место на диске.** Распакованная копия живёт, пока открыта вкладка; размер виден в подсказке.
- **Portable-режим.** Временные файлы пишутся вне каталога exe — как уже делает спул stdin.
- **Скорость.** Оценок нет: распаковка miniz не замерялась. Если окажется узким местом, декодер меняется за интерфейсом `GzipDevice`.
- **Сканер.** Папка с десятками больших `.gz` нагрузит процессор сильнее, чем сейчас, когда они пропускаются.

## Решения за автором

Если автор не возразил, принимается рекомендованный вариант.

| Вопрос | Рекомендация |
| --- | --- |
| Включать ли `.tar.gz` в 0.6 | Да, последним PR: архивы поддержки с Linux почти всегда в этом формате |
| `.bz2`, `.xz`, `.zst` | Нет; вернуться по запросам, тогда рассмотреть libarchive |
| Библиотека | Встроенный miniz |
| Где временные файлы | Каталог кэша приложения, без настройки в первой версии |
| Авто-обновление и сжатые файлы | Тик их пропускает; `F5` перераспаковывает изменившийся архив |
| Считать ли счётчики `.gz` в сканере автоматически | Да, как для обычных файлов |
| Архив в сканере | Отдельным корнем с возвратом, а не узлом в дереве |
| Ротированные имена без сжатия (`app.log.1`) | Отдельная задача; в F-2 правило компонентов действует только для `.gz` |
