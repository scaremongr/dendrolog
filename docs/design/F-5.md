# F-5. Схема на вкладку, затем на файл

Статус: спроектирован 19 ноября 2026, действуют рекомендованные варианты (автор передал продуктовые решения исполнителям). Задача `F-5` из `docs/roadmap.md`, релиз 0.7. Код читался на `06aa5eb` (0.6.0). Опирается на M-2 (каталог схем и панель Log Fields — из окна в контроллер `fieldschemacontroller`, делается до шага 1) и на `docs/design/F-4.md` (ключевые схемы: вид схемы, поэтому на файл он становится вместе со схемой).

## Задача и границы

Сейчас схема полей одна на окно: выбрал «nginx access» для одной вкладки — Spring-лог в соседней потерял колонки. Слитая вкладка из лога приложения и access-лога не может разобрать оба. Нужно, чтобы вкладки не мешали друг другу, а файлы слитой вкладки разбирались каждый своей схемой.

Входит:

- схема, извлечение полей («Filter blocks») и выбор колонок — на вкладку; схема по умолчанию для новых вкладок;
- схема на файл внутри вкладки; колонки слитой вкладки — объединение по имени;
- хранение: сессия, `last-session.json`, стек `Ctrl+Shift+T`, память файла; чтение старых файлов;
- все потребители полей: парсер, индексатор, индексный стор, фильтр-воркеры, переизвлечение, Save View As, Search Results, Entry Details.

Не входит: автоматическое предложение схемы при открытии (F-6 — после этой задачи, на файл), новые виды схем (F-4), схема в сканере каталога.

## Как устроено сейчас

- **Физически схема уже на вкладку.** У каждой `LogViewWidget` свои `LogParser` (два: загрузка и дочитывание), `LogIndexer` и индексный стор со своей копией `LogPattern` (`setParserPattern`, `src/logviewwidget.cpp:233-243`; `IndexedLogStore::m_fieldPattern`, `src/indexedlogstore.h:226`). Флаг извлечения — тоже на вкладку (`setExtractionEnabled`, `:245-253`). Правила вкладка привязывает к своим полям сама (`parserFieldNames`, `:99`, `:1571`).
- **Одинаковыми их держит окно.** `MainWindow::m_conversionPattern` — одна схема; `onPatternComboChanged` → `applyPatternToAllViews` (`src/mainwindow.cpp:1621`, `:1724`) ставит её ВСЕМ вкладкам, переизвлекает поля всех резидентных записей (до 4000 — синхронно, больше — один `FieldReextraction` на все вкладки) после остановки фильтров всех вкладок, Search Results и Save View As (инвариант 4). Новая вкладка получает схему окна (`createLogViewWidget`, `:1865`), флаг и колонки окна (`:1897-1902`).
- **Log Fields — глобальная панель.** Чекбоксы колонок строятся по схеме окна (`rebuildFieldVisibilityControls`), выбор ставится всем моделям (`applyFieldVisibilityToAllViews`, `:1601`). Модель хранит выбор у себя (`LogModel::setFieldDisplaySelection` — индексы колонок).
- **Привязка правил — к схеме окна:** Text Filters Apply (`applyTextFiltersToActiveView`, `:3596-3597`) и запрос Search берут `LogPattern(m_conversionPattern).fieldNames()`.
- **Хранение.** ini `[View]`: `conversionPattern`, `fieldFilterEnabled`, `fieldVisibleNames` (`:1158-1164`). `SessionState` — одна схема (`schemaName`, `schema` — определение), `fieldExtraction`, `visibleFields` (`src/documentstate.h:150-153`); при открытии окно ставит схему ДО вкладок, `SessionController::chooseSchema` находит совпадающую по определению или добавляет «(from session)». `TabState` и память файла схему не хранят (`docs/release-checklist-0.6.0.md`: «до F-5»). Читатели `ViewState`, `TabState`, `TabSource`, `FileMemory` и `SessionState` игнорируют неизвестные ключи; `SessionState` с версией не 1 отвергается.
- **Поля — индексы схемы.** `LogEntryFields::spans[i]` — колонка `i` схемы; `formatDisplayText` и `FilterRuleSet` (`m_boundFieldIndexes`) работают индексами, имя → индекс разрешает `bindFields`. Строка без колонки правила — «не содержит»; колонки нет в схеме — правило нейтрально (`fieldMissing`).
- **Схема при загрузке, а не при показе.** Резидентные записи несут спаны с момента разбора, индексный стор извлекает по требованию своей копией. Граница записи (при включённом извлечении) и, после F-4, метка и уровень из ключей решаются при загрузке.

## Решение

### Владелец и одно значение на файл

Схема на файл повторяет путь, проверенный F-1 для кодировки:

| | Резидентная вкладка | Индексная вкладка |
| --- | --- | --- |
| Где живёт схема файла | `LogViewWidget::m_fileSchemas` (путь → схема), как `m_fileEncodings` | в `IndexedLogStore`, в записи файла рядом с декодером |
| Кто читает | парсер получает схему файла на старте прохода (загрузка, дочитывание, перечитывание) | `entryAt`, снапшоты, фильтр-воркер, поисковая база — копией, как декодер |
| Переход порога | состояние уходит в стор | обратно — во вкладку |

Схема на `LogFile` (общем для записей и потоков) отвергнута: структура разделяется между потоками без синхронизации, мутация в ней — гонка.

Значение — `FileSchema`: `LogPattern` файла и таблица «колонка схемы → колонка вкладки». Тип живёт в ядре (`src/fieldlayout.h`) вместе с раскладкой вкладки:

```cpp
struct FieldLayout {               // колонки вкладки
    QStringList columns;           // объединение по имени, только растёт
    FileSchema  schemaFor(const LogPattern& p);   // добавляет недостающие колонки в конец
};
struct FileSchema {
    LogPattern   pattern;
    QVector<int> columnOf;         // индекс поля схемы → индекс колонки вкладки
    QBitArray    hasColumn;        // какие колонки вкладки есть у этой схемы
};
```

### Поля — сразу в пространстве колонок вкладки

Парсер, индексный стор и переизвлечение кладут спаны не по индексу схемы, а по `columnOf`: поле `Level` файла nginx и поле `Level` файла Spring — одна колонка вкладки. Дальше НИЧЕГО не меняется: фильтр, `formatDisplayText`, Save View As, Search Results, Entry Details работают индексами колонок вкладки, как сейчас индексами единственной схемы. У вкладки с одной схемой `columnOf` тождественен — поведение байт в байт прежнее.

Колонки только добавляются (новая схема файла дописывает свои имена в конец), поэтому индексы уже разобранных записей не устаревают. Пересборка раскладки — только при смене схемы пользователем: тогда колонки строятся заново и поля вкладки переизвлекаются, как сейчас при смене схемы окна.

Два правила для слитой вкладки:

- **Строка, в схеме которой нет ни одной выбранной колонки, показывается сырым текстом** (`formatDisplayText` получает `hasColumn` файла). Без этого выбор «Timestamp Level Message» оставил бы пустыми все строки файла со схемой без этих колонок. Строка, схема которой колонку имеет, но строка её не заполнила, остаётся пустой, как сейчас.
- **Правило фильтра по колонке, которой нет у схемы файла, на строках этого файла даёт «не содержит»** — та же семантика, что у продолжения многострочной записи. `Include Level contains ERROR` во вкладке Spring + nginx оставляет только ошибки Spring. Нейтральным (`fieldMissing`) правило остаётся, только если колонки нет во всей вкладке.

### Что видит пользователь

| Место | Поведение |
| --- | --- |
| Комбобокс схемы (док Log Fields) | Схема активной вкладки; при смене вкладки — её схема. Выбор меняет только активную вкладку |
| «Applies to» (под комбобоксом, только у вкладки из нескольких файлов, шаг 3) | «All files» или файл вкладки. Комбобокс показывает схему выбранной цели; у «All files» при разных схемах — «(mixed)» |
| «Filter blocks» и чекбоксы колонок | Вкладки; колонки — объединение схем её файлов |
| Новая вкладка | Схема по умолчанию — последняя выбранная пользователем в комбобоксе (ключ ini `[View] conversionPattern`, смысл «по умолчанию»), флаг и колонки — тоже последние |
| «Apply Schema to All Tabs» (меню дока Log Fields и меню View) | Прежнее поведение одним действием |
| Файл, добавленный в открытую вкладку | Схема вкладки (до шага 3 — она же для всех файлов); с шага 3 — схема из памяти файла, если есть, иначе схема вкладки |
| Объединение вкладок (`addFilesFrom`) | Файлы приносят свои схемы (как кодировку); колонки приёмника растут |
| Search Results | Колонки и привязка правил — от вкладки-источника |
| Entry Details | Имена колонок вкладки; значения — поля строки |

### Смена схемы: инвариант 4 на одну вкладку

`applyPatternToAllViews` становится `applySchema(tab, target)` в контроллере M-2: остановить фоновые фильтры и Save View As (как сейчас — у всех: дёшево и не требует знать, кто читает записи этой вкладки), Search Results, если его источник — эта вкладка; переизвлечь поля записей только затронутых файлов; `reapplyFilterIfStale`. `FieldReextraction` получает схему на запись (`(entry, shared_ptr<const FileSchema>)`), а не одну на задание. Если меняется ключевая часть схемы (F-4, шаг 3), файл перечитывается тем же путём, что смена кодировки.

### Хранение

Версии форматов не растут: все новые ключи необязательные, читатели прежних версий их игнорируют.

- **`ViewState.fields`** — `{"schema":{"name","definition"},"extraction":true,"visibleFields":[…]}`: схема вкладки, флаг, колонки по именам. Пишется в `TabState` (сессия, `last-session.json`, `Ctrl+Shift+T`) и в память файла одно-файловой вкладки.
- **`TabSource.schema`** (шаг 3) — `{"name","definition"}`, только если схема файла отличается от схемы вкладки.
- **`SessionState.schema` верхнего уровня остаётся** — схема активной вкладки: её прочитает 0.6, и ею получают схему вкладки без `fields` (сессии 0.6). `visibleFields` и `fieldExtraction` верхнего уровня — так же.
- **Схема по определению:** при применении — `SessionController::chooseSchema` (совпадающая по определению, иначе добавить «(from session)»). Для памяти файла каталог не засоряется: нет совпадающего определения — вкладка берёт схему по умолчанию, строка статуса сообщает «Remembered schema X is not in the catalogue».
- **Память файла:** одно-файловая вкладка помнит схему вкладки (`ViewState.fields`), файл слитой вкладки — свою (`TabSource.schema`). Применяется сразу при открытии, как ручной выбор кодировки: схема — не фильтр, предлагать её плашкой незачем.
- Эталоны `tests/document_state/*.json` (версии 1) читаются без изменений; новые эталоны с `fields` и `schema` — рядом.

### Связи

- **M-2** — до шага 1: шаг 1 переписывает тот самый путь (`applyPatternToAllViews`, Log Fields, каталог схем), который M-2 выносит в `fieldschemacontroller`. Без M-2 шаг 1 растит `mainwindow.cpp`.
- **F-4** — ключевая схема — свойство `LogPattern`, поэтому на шаге 2 «схема на файл» даёт и «JSON-файл в слитой вкладке с обычным логом» без отдельной работы. Перечитывание при смене ключевой части (F-4, шаг 3) после шага 1 касается одной вкладки, после шага 3 — одного файла.
- **F-6** — после шага 3: предложение «похоже на X — применить?» — на файл, отказ хранится в памяти файла рядом со схемой.
- **F-2** — схема сжатого файла хранится по ключу источника (путь архива + член) — тот же ключ памяти, что F-2 PR 2 вводит для закладок; шаг 3 идёт после F-2 PR 2 (оба трогают `documentstate`, `filememorystore`).

## Проверки

- **`logstore_equivalence`** — слитая вкладка с двумя схемами (одна — ключевая F-4, когда та готова): все конфигурации фильтров, правила по общей колонке, по колонке одного файла и по колонке, которой нет во вкладке; текст показа с выбором, задевающим только один файл (сырой текст у другого).
- **`document_state`** — эталоны версии 1 (`tab-state-v1.json`, `session-v1.json`, `file-memory-v1.json`, `session-windows.json`, `session-posix.json`) читаются, и результат — прежний; новые эталоны `session-schemas.json` (вкладки с разными схемами и файл со своей) с круговым проходом; схема, которой нет в каталоге: сессия добавляет «(from session)», память — схема по умолчанию и сообщение.
- **`mainwindow_smoke`** — сценарии из таблицы PR; свип меню с новым действием; смена схемы одной вкладки не трогает выдачу Search другой.
- **`logview_state`** — триггер «колонки» уже есть; добавить «смена схемы файла в слитой вкладке» (текущая запись и вьюпорт переживают переизвлечение).
- Одна схема на всё (как в 0.6) — побайтно прежний базлайн `DENDRO_BASELINE_DUMP` на обоих бэкендах.

## Риски и затронутые инварианты CLAUDE.md

- **Инвариант 7** меняется: «Fields — глобальный» → схема, извлечение и колонки — пер-вкладочные, у файла слитой вкладки — своя схема. Формулировка — в PR 1 и PR 3.
- **Инвариант 4** — сужается до вкладки, механизм прежний (`cancelPendingFilter(wait)` → мутация на GUI-потоке → `reapplyFilterIfStale`). Search Results делит записи с источником — останавливается вместе с ним.
- **Инвариант 3** — раскладка колонок растёт при подключении файла (один раз на файл), а не на батч; `columnOf` применяется в воркере.
- **Инвариант 11** — порядок строк не зависит от схемы, кроме метки из ключей (F-4), которая решается при загрузке; слияние идёт по моменту, как сейчас.
- **Хранилище** — PR 2 трогает оба бэкенда; параллельно с другой задачей хранилища не вести.
- **Совместимость форматов** — новые ключи необязательные, версии не растут; 0.6, открывший сессию 0.7, получит схему активной вкладки для всех вкладок и при пересохранении потеряет схемы вкладок (снимок 0.6 их не знает) — приемлемо.
- **Каталог схем** — схема из сессии с определением, которого нет в каталоге, добавляется «(from session)» на каждую такую вкладку; одинаковые определения сводятся к одной записи.
- **MSVC** — `FileSchema` и `FieldLayout` объявлять `struct` везде, forward-декларации совпадают.
- **Цена** — `FileSchema` копируется в воркер, как `LogPattern` сейчас (регексы Qt разделяемые); на строку добавляется перенос спанов через `columnOf` — копия вектора из единиц элементов.

### PR 1 — схема на вкладку (26 ноября 2026)

Сделано по таблице PR. Решения исполнителя (рекомендованные варианты «Решений за автором» приняты как есть):

- **Тип состояния** — `FieldSettings` в `src/documentstate.h` (ядро): имя схемы в каталоге, определение, «Filter blocks», колонки по именам. Он же — `ViewState.fields` на диске; `FieldLayout` / `FileSchema` — PR 2. Вкладка держит его сама (`LogViewWidget::fieldSettings` / `setFieldSettings`: схема — у парсера, имя, флаг и колонки — рядом); `setFieldSettings` только ставит схему парсерам и стору, переизвлечение и показ колонок — у контроллера.
- **Док** — `FieldSchemaController::setCurrentView` (окно зовёт из `connectToLogView`, без вкладок — `nullptr`): геттеры `activeSchema`, `fieldNames`, `visibleFieldNames`… описывают вкладку дока, без неё — схему по умолчанию. `applyToAllViews` и `applySessionSchema` M-2 заменены на `applyToView(view, settings)` и `resolveSaved`.
- **Схема по умолчанию** — последний выбор в доке на любой вкладке, вместе с флагом и колонками (ключи ini прежние: `conversionPattern`, `fieldFilterEnabled`, `fieldVisibleNames`); переключение вкладок её не меняет.
- **Пункт каталога** — по определению: то же имя и определение, иначе первый с тем же определением; имя хранится, чтобы две записи с одной схемой не путались.
- **Те же схема и флаг** (смена только колонок, «Apply to All Tabs» на вкладку с той же схемой, «Use Selected» с прежней схемой) — без переизвлечения и без остановки читателей.
- **Инвариант 4 на вкладку**: останавливаются фильтр этой вкладки, выдача Search, если её источник — эта вкладка (или вкладка активна), и фоновый Save View As — как раньше, у любой вкладки (задание не знает своей вкладки; задача S-20). `FieldReextraction` — свой на вкладку (`m_jobs`), вкладка закрыта посреди расчёта — расчёт отменяется; полоса прогресса окна прячется, когда не идёт ни один.
- **«Apply Schema to All Tabs»** — `QAction` в меню View и кнопка **All Tabs** рядом с **Manage…** (у дока Log Fields нет своего меню); схема, флаг и колонки дока на все вкладки.
- **Сохранённое состояние**: `captureState` пишет `fields` всегда (и «без схемы» — снимок возвращает именно её, а не схему по умолчанию). `applyState` до фильтров шлёт `savedFieldSettingsFound(fields, fromMemory)`, контроллер (подписан в `configureView`) синхронно ищет схему в каталоге и ставит её вкладке. Сессия: вкладка без `fields` (0.6) получает схему верхнего уровня (`SessionState::topLevelFields`), сессия без схемы — схему по умолчанию; открытие сессии больше не меняет ни открытые вкладки, ни схему по умолчанию; верхний уровень при записи — активная вкладка (как прежде через `WindowSettings`). Одинаковые определения не из каталога сводятся к одной записи «(from session)».
- **Память файла**: схема одно-файловой вкладки — в `ViewState.fields` её памяти; применяется сразу (не плашкой); нет в каталоге — схема по умолчанию и `statusMessage` «Remembered schema X is not in the catalogue»; файл, добавленный вторым, схемы не несёт (PR 3).
- **Тулбар Filters**: подсказка кнопки Fields — «(this tab)».
- **Читатели вне вкладки** (выдача Search, Save View As) останавливаются, только если у вкладки есть резидентные записи, поля которых меняются: схема новой вкладки из снимка (до загрузки) и индексной вкладки чужой экспорт не отменяет; выдачу Search активной вкладки окно по `schemaApplied` повторяет (панель на виду) или сбрасывает.
- **Пустой выбор колонок в снимке** — «все колонки» (как у ini и сессии 0.6); живой выбор «снять все» действует до закрытия вкладки.
- **Известное до PR 3**: объединение вкладок с разными схемами (`addFilesFrom`) читает файлы присоединяемой вкладки схемой вкладки-приёмника — схема на файл появится в PR 3.
- **Тесты**: `field_schema` (вкладки, инвариант 4 на вкладку, `resolveSaved`), `document_state` (эталон `session-schemas.json`, `ViewState.fields`, сессия с разными схемами, 0.6, «(from session)», `Ctrl+Shift+T`, память файла — оба бэкенда), `mainwindow_smoke` (сценарий «schema per tab»; схема фикстур кладётся в каталог до окна).

### PR 2 — ядро схемы на файл (26 ноября 2026)

Сделано по таблице PR, пользователю не видно ничего: вкладка по-прежнему читает все файлы одной схемой, но слитую вкладку из файлов с разными схемами ядро уже разбирает на обоих бэкендах (API вкладки ещё нет — это PR 3; проверено тестами, собирающими документ напрямую). Решения исполнителя:

- **Типы** — `src/fieldlayout.*` (ядро): `FieldLayout` (колонки вкладки, `schemaFor(pattern)` дописывает недостающие имена в конец), `FileSchema` (`pattern`, `columnOf`, `hasColumn`, `identity`; `toLayout` / `extractFields` — поля сразу в колонках вкладки) и `FileSchemaSet` (схемы файлов вкладки: по пути + общая, `fallback`). Все три — `struct`. Повторяющееся имя внутри одной схемы — k-е поле с именем N ↔ k-я колонка с этим именем: схема со своими дублями тождественна сама себе.
- **«Без схемы» = `nullptr`.** Флаг извлечения больше не живёт рядом со схемой у парсера, индексатора и стора: вкладка кладёт в модель схему файла, только пока «Filter blocks» включён и у схемы есть колонки (`LogViewWidget::applySchemaToModel`), иначе `nullptr`. Одно понятие вместо пары «схема + флаг» на каждом читателе.
- **Владелец схем файлов во вкладке — `LogModel`** (`setFileSchemas`, `setFileSchema`, `fileSchemaFor`), а не стор: показ (`formatDisplayText` с `FileSchema`, `displayTextLength`) нужен обоим бэкендам, модель переживает конверсию бэкенда, поисковая модель копирует набор у источника (`searchVisible`, `appendSearchRows`). `IndexedLogStore` держит копию указателя в записи файла рядом с декодером (`attachFile`, `refreshFileSchemas` — модель зовёт при смене) и отдаёт её снапшоту, фильтр-воркеру и поисковой базе. `ResidentLogStore` не менялся: поля его записей разобраны при загрузке. `m_fileSchemas` вкладки (путь → схема) из таблицы «Решения» — PR 3; в PR 2 вкладка ставит модели одну общую схему (`fallback`).
- **Схема — параметр прохода**: `LogParser::startParsing` / `startParsingFrom` и `LogIndexer::startIndexing` / `startIndexingFrom` принимают `FileSchemaPtr` (лямбда воркера держит её до конца прохода); `setPattern`, `setExtractionEnabled`, `pattern()` и члены схемы у обоих удалены. `analyzeFileForStats` получил ключевую схему параметром (сканер её не задаёт, как раньше). Вкладка берёт схему файла у своей модели на старте каждого прохода (`passSchema`: загрузка, дочитывание, перечитывание, полная перезагрузка, конверсия, откат UTF-16).
- **Показ слитой вкладки**: строка, у схемы файла которой нет ни одной выбранной колонки, — сырым текстом (view, Save View As текстом — схема строки по `LogEntryMeta::sourceFile`). Таблица Save View As (CSV / JSON Lines) уже клала сырой текст в Message строке без этой колонки — не менялась.
- **Фильтр** не менялся: поля в колонках вкладки, правило по колонке, которой нет у схемы файла, на его строках — «не содержит» (спана нет), по колонке, которой нет во вкладке, — нейтрально (`bindFields` по колонкам вкладки).
- **`FieldReextraction`** — `(entries, FileSchemaSet)`: схема на запись по её файлу (сырой указатель в задании, набор живёт в задании); у файла без схемы поля снимаются. Синхронный путь контроллера (до 4000 записей) — то же правило.
- **Тесты**: `logstore_equivalence` — `testMixedSchemas` (регексная Timestamp/Worker/Level/Message и JSON Lines Timestamp/Level/Message/Thread, оба порядка файлов, оба сценария подключения, 36 общих конфигураций и 8 своих, заданные значения показа и правил, Message и моменты ключевого файла); одно-файловые и прочие фикстуры проверяют, что колонки вкладки = колонки схемы. `field_reextraction` — слитая вкладка из трёх файлов (две схемы и без схемы). Обвязка `testdocuments.h` — `fileSchema(doc, path, schema)` и `Document::layout`. Тест «до реализации» проверен мутациями: без правила сырого текста — 96 расхождений, без переноса колонок в фильтр-воркере — 264.
- **Базлайн** `DENDRO_BASELINE_DUMP` (регексная схема Timestamp/Level/Thread/Message на 60 тыс. строк и JSON Lines на 30 тыс., показаны выбранные колонки) — побайтно прежний на обоих бэкендах.
- **Цена** — не хуже: облачная машина, 4 ядра, Release, 2 млн строк из генератора (текст и `--format jsonl`), `lineindex_smoke --bench` / `--bench-resident` с регексной схемой (Timestamp, Level, Thread, Message) и `jsonl`, медиана 7 прогонов, «до» и «после» подряд в одном окне. Индексатор: регексная 1,962 → 1,969 с, JSON Lines 0,593 → 0,569 с; резидентный парсер: регексная 6,103 → 6,059 с, JSON Lines 2,527 → 2,415 с (разброс прогонов ±10 %). У одной схемы перенос колонок тождественен и не выполняется (`identity`); схема прохода — указатель вместо копии `LogPattern` на старте.

### PR 3 — схема файла во вкладке, окне и сохранённом состоянии (26 ноября 2026)

Сделано по таблице PR; F-5 закрыта. Слитая вкладка разбирает каждый файл своей схемой: «Applies to» в доке Log Fields (только у вкладки из нескольких файлов) — **All files** или файл вкладки; при разных схемах у **All files** комбобокс показывает «(mixed)». Решения исполнителя (рекомендованные варианты «Решений за автором» приняты как есть):

- **Значение схемы файла — `FieldSettings`** (значат только имя и определение), отдельного типа нет: его же ищет в каталоге `FieldSchemaController::resolveSaved`. Своя схема хранится, только пока отличается от схемы вкладки (`LogViewWidget::m_fileSchemas`, ключ — `filePath`, как у `m_fileEncodings`); схема, равная схеме вкладки, своей не становится. Пустое определение — файл без схемы во вкладке со схемой.
- **API вкладки**: `fileSchema(file)` (своя или вкладки), `fileSchemas()`, `setFileSchema(file, схема)`, `setFieldSettings(settings, files)` — схема вкладки и свои схемы разом (однопараметрный оставляет свои), `addLogFile(path, FileEncoding, схема)`. Схема источника, который ещё откроется (снимок, память, объединение), ждёт его по `RecordLocator::sourceKey` (`setPendingFileSchema`) и ставится, когда файл появляется во вкладке (`adoptPendingSchema`) — до первого прохода, поэтому файл сразу читается своей схемой.
- **Раскладка колонок**: схема вкладки, затем свои схемы файлов в порядке файлов вкладки (`rebuildFieldLayout`; одно определение — один `FileSchemaPtr`). Файл со своей схемой, добавленный во вкладку, раскладку только растит — поля загруженных записей не трогаются, переизвлечения нет; вкладка сигналит `fieldLayoutGrown`, контроллер ставит показ колонок и перепривязывает правила. Любая смена схемы пользователем строит раскладку заново и переизвлекает поля, как раньше. Новые колонки показываются, если были показаны все прежние (у смены схемы вкладки — прежнее правило `keptColumns`).
- **Док**: цель «Applies to» — `FieldSchemaController::setTargetFile` (пусто — все файлы), смена вкладки дока возвращает «все файлы». Цель — файл: комбобокс показывает и меняет его схему (`applyToFile` → `applyToView(view, settings, files)`); выбор схемы файла схемой по умолчанию не становится. «Filter blocks» и колонки — вкладки и при цели «файл». Цель — все файлы: выбор схемы снимает свои схемы файлов; «Apply Schema to All Tabs» — тоже (схема дока на все вкладки и все их файлы). «(mixed)» — текст-заглушка комбобокса при индексе -1 (`isMixed`, `activeIndex` = -1).
- **Перечитывание — на файл**: подпись чтения (`readingSignature`) считается по схеме файла; сеттеры снимают подписи всех файлов и позицию до смены (`beginSchemaChange`) и перечитывают только файлы с изменившейся подписью (`endSchemaChange`). Позиция перечитывания ставится, только если её файл перечитывается; строки остальных файлов на месте (резидентные записи — те же объекты), вид держит якорь.
- **Сохранённое состояние**: `TabSource.schema` — объект `{"name","definition"}` или `null` (файл без схемы); пишется, только если у файла своя схема; битое значение — отказ (как у остальных полей). Снимок из одного источника со своей схемой (сессия, `Ctrl+Shift+T`) — эта схема становится схемой вкладки. Применение: `applyState` после схемы вкладки шлёт `savedFileSchemaFound` на каждый источник со своей схемой, контроллер ищет её в каталоге (сессия добавляет «(from session)», память — нет: файл остаётся со схемой вкладки, строка статуса сообщает) и ставит `setPendingFileSchema` (файл ещё не открыт) или `applyToFile`.
- **Память файла**: файл слитой вкладки помнит схему файла (свою или вкладки — какой читался), одно-файловая вкладка — схему вкладки в `ViewState.fields` (своя схема единственного файла сворачивается туда). Файл, добавленный во вкладку вторым, получает схему из памяти (`TabSource.schema`, иначе `ViewState.fields` памяти одно-файловой вкладки; «без схемы» не навязывается); открытый первым из памяти слитой вкладки — она становится схемой вкладки. Ключ «schema» в JSON памяти теперь значимый: проверка «лишние ключи не мешают» в `document_state` переведена на другой ключ.
- **Объединение вкладок** (`addFilesFrom`): схема файла в источнике (своя или его вкладки) становится своей здесь, если отличается от схемы приёмника. Известное ограничение PR 1 («объединение читает файлы схемой приёмника») снято.
- **Переход порога**: схемы файлов у вкладки и у модели (`LogModel::fileSchemas`) — конверсия их не трогает; проверено и большим файлом, добавленным в резидентную слитую вкладку (вкладка перечитывается индексатором целиком).
- **Ревью (`/code-review high` по диффу шага), исправлено до пуша**: файл, указанный в отчёте сессии («Locate File…»), не получал свою схему — ждущая схема переезжает на новый путь (`addRelocatedSource`); смена схемы второго файла посреди перечитывания первого теряла позицию первого — позиция перечитывания сбрасывается, только если её файл перечитывается снова; выбор колонок сессии терял колонки, которые есть только у схем файлов, — выбор снимка помнится до того, как ждущие схемы разобраны (`m_stateVisibleFields`); схема из памяти сжатого файла (он уже во вкладке, но без строк) запускала переизвлечение всей вкладки и останавливала чужой Save View As — файл без строк только растит раскладку (`fileHasRows`); при «Applies to» → файл верхний уровень сессии и «Apply Schema to All Tabs» брали схему файла — теперь схему вкладки (`activeSchema` — вкладки, `shownSchema` — комбобокса, для редактора); явная схема `addLogFile` главнее памяти; одинаковые имена файлов в «Applies to» — с папкой. Сверх ревью: на резидентной вкладке reset перечитанного файла возвращал вид к ЗАПИСИ текущей строки другого файла (начало многострочной записи), а не к строке — позиция держится на время перечитываний (`m_heldPosition`) и после такого reset запрашивается у локатора заново. Сама семантика восстановления после reset — в `LogListView` (задача S-24).
- **Не сделано (по-прежнему)**: S-21 (двойная работа при перечитывании резидентного файла) — смена ключевой схемы одного файла переизвлекает поля всей вкладки до перечитывания этого файла; S-20 (Save View As другой вкладки).
- **Тесты**: `logview_lifecycle` — `checkFileSchemas` (оба бэкенда: своя схема JSON Lines перечитывает только этот файл, записи регексного — те же объекты, вкладка = открытая сразу с этими схемами, колонки — объединение, закладки в обоих файлах, текущая строка и её место на экране на ASCII-фикстуре; регексная → регексная у файла — без перечитывания; объединение вкладок), `checkFileSchemaThreshold`; `document_state` — эталон `session-file-schemas.json`, прежние эталоны без схем файлов, `checkSessionFileSchemas` (оба бэкенда: «Applies to» и «(mixed)» в контроллере, сессия, «(from session)», память файла второго и первого файла); `mainwindow_smoke` — `scenarioFileSchemas`.

## Чего не делаем

- Автоматический выбор схемы при открытии (F-6 — предложение, после этой задачи).
- Схема по маске имени файла (`*.jsonl` → JSON Lines) — вернуться после F-6, если предложения окажется мало.
- Разные колонки для разных файлов в одном view (колонка показывается у всех файлов, где она есть).
- Удаление колонок из раскладки вкладки при закрытии файла — колонки только растут до смены схемы пользователем.
- Схема в сканере каталога и в фильтре сканера по содержимому.
