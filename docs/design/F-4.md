# F-4. JSON Lines и logfmt как источник полей

Статус: спроектирован 19 ноября 2026, действуют рекомендованные варианты (автор передал продуктовые решения исполнителям). Задача `F-4` из `docs/roadmap.md`, релиз 0.7. Код читался на `06aa5eb` (0.6.0). Связана с `docs/design/F-5.md` (схема на вкладку и на файл): вид схемы — свойство схемы, а не вкладки, поэтому на файл он становится сам, когда F-5 делает схему пофайловой.

## Задача и границы

Лог в JSON Lines (`{"ts":"…","level":"info","msg":"…",…}` — по объекту на строку) или в logfmt (`ts=… level=info msg="…" user=42`) сейчас разбирается эвристикой «где в строке метка и слово уровня»: эпоха числом (`"time":1700000000123`) и числовой уровень pino (`"level":30`) не видны, метку может взять не тот ключ, а поля регексной схемой не извлечь — значения в кавычках с экранированием и ключи в любом порядке. Нужно, чтобы время, уровень и сообщение брались из ключей, поля были доступны фильтрам и колонкам, и оба бэкенда давали одно и то же.

Входит:

- новый вид схемы «по ключам» с двумя форматами строки: JSON-объект и logfmt;
- время, уровень и граница записи из ключей на обоих бэкендах, при загрузке и дозаписи;
- поля со значениями в экранированной форме (JSON `\"`, `\n`, `\uXXXX`; logfmt `\"`, `\\`) — фильтр и Entry Details видят раскодированное значение;
- хранение в `patterns/*.json` с прямой совместимостью: 0.6 читает каталог с новой схемой и не теряет её;
- встроенные схемы «JSON Lines» и «logfmt», редактор, автоопределение формата по образцу.

## Как устроено сейчас

- **Метка и уровень — без схемы.** Индексатор на каждую строку зовёт `detectTimestampMs` и `detectLogLevel` по сырому тексту (`src/logindexer.cpp:199-207`); схему спрашивает, только если строка не первична без неё, и только ради решения «первичная или продолжение» — спаны выбрасываются (`:208-217`). Парсер делает то же, но спаны оставляет в записи (`src/logparser.cpp:302-320`). Правило границы — `LineClassifier::isPrimaryLine(schemaMatched, …)` (F-12). Схема участвует, только когда включено извлечение полей («Filter blocks»): флаг `extraction` у обоих.
- **На JSONL эвристика работает наполовину.** ISO-метка ищется где угодно в строке (самая левая), но `{"ts":"2026-…"` — не ведущая метка (позиция 7), поэтому запись начинается, только если в строке нашлось и слово уровня. Слово ищется по всей строке: `"msg":"retry after error"` при `"level":30` даст ERROR. Эпоха числом меткой не считается — записи без метки уходят в конец слитой вкладки.
- **Поле — диапазон в тексте строки.** `FieldSpan` — (смещение, длина) в `QString` строки, без копирования (`src/logfield.h`); `LogEntryFields::get` отдаёт `QStringView`. Читателей значения пять: фильтр (`src/filterruleset.cpp:122-127`), текст строки view и Save View As (`LogModel::formatDisplayText`, `src/logmodel.cpp:603-629`, и длина `:656`), Entry Details (`src/entrydetailspanel.cpp:569`, `:682`). Экранированное значение подстрокой не является — его так не отдать.
- **Индексный бэкенд извлекает поля по требованию** той же `LogPattern::extractFields`: строка для показа (`src/indexedlogstore.cpp:707`), снапшот для экспорта (`:1262-1270`), поисковая база (`:1345`), фильтр-воркер (`:1478`) — схема копией в воркер.
- **Смена схемы меняет только поля.** `MainWindow::applyPatternToAllViews` (`src/mainwindow.cpp:1724`) переизвлекает поля резидентных записей (синхронно или `FieldReextraction`, инвариант 4) и отдаёт новую схему индексному стору. Метки, уровни и границы записей остаются с момента загрузки — на обоих бэкендах.
- **Формат схемы на диске** — `LogPattern::serializeDefinition`: `{"version":3,"type":"dynamic-block-schema","linePrefix":…,"blocks":[…]}` плюс `name` и метаданные (`src/schemastore.h`). Читатель отказывается от версии больше 3 и от неизвестного `kind` блока (`src/logpattern.cpp:411`, `:426`). Неизвестные ключи верхнего уровня `SchemaStore::parseEntry` хранит в `meta` и переписывает дословно (Q-17); список ключей формата — `isSchemaFormatKey` (`src/schemastore.cpp:87`).
- **Ловушка совместимости.** `SchemaStore::sync` удаляет из каталога каждый `*.json`, который не стал записью списка, в том числе тот, что не разобрался (`src/schemastore.cpp:338-342`). `sync` зовут после OK в редакторе схем и при открытии сессии с новой схемой (`src/mainwindow.cpp:1671`, `:4084`). Значит, схема с версией 4 или неизвестным видом блока в 0.6 молча удаляется при первой правке каталога.
- **Сканер каталога схему не использует вовсе** (`LogParser::analyzeFileForStats`, `src/logparser.cpp:466-470`) — счётчики и время файла по эвристике.

## Решение

### 1. Вид схемы, а не вид блока

`LogPattern` остаётся единственным типом схемы во всём коде и получает второй движок. Определение — `PatternDefinition` плюс необязательная часть `KeyedDefinition`:

```cpp
struct KeyedDefinition {
    enum class Format { JsonObject, Logfmt };
    enum class EpochUnit { Auto, Seconds, Millis, Micros, Nanos };
    enum class NumericLevels { Auto, Syslog, Python };
    Format        format = Format::JsonObject;
    QStringList   timeKeys    {"ts","time","timestamp","@timestamp","@t","t"};
    QStringList   levelKeys   {"level","lvl","severity","loglevel","levelname","log.level","@l"};
    QStringList   messageKeys {"msg","message","@m","@mt","event"};
    QStringList   extraColumns;          // ключи, ставшие колонками, в порядке колонок
    EpochUnit     epochUnit = EpochUnit::Auto;
    NumericLevels numericLevels = NumericLevels::Auto;
};
```

Когда `KeyedDefinition` есть, `matchLine` / `extractFields` / `fieldNames` идут через ключевой движок, а регексный каскад не строится. Колонки: `Timestamp`, `Level`, `Message`, затем `extraColumns` по именам ключей. Имена ролей совпадают с колонками встроенных регексных схем (Python logging, Spring Boot) — правило фильтра `Level contains ERROR` и выбор колонок по имени переносятся между схемами, а слитая вкладка F-5 объединяет колонки по имени.

Почему не новый вид блока: блок — позиционный кусок регекса, а у JSON-строки нет позиций, ключи идут в любом порядке. Почему не отдельный класс схемы: `LogPattern` копией уходит в `LogParser`, `LogIndexer`, `IndexedLogStore`, `FieldReextraction`, снапшоты и сессию — второй тип пришлось бы протащить во все эти места, а фасад не меняет ни одной сигнатуры.

Разбор строки — новый модуль ядра `keyedline.{h,cpp}`: токенизатор JSON-объекта и logfmt по `QStringView` без аллокаций. Отдаёт пары (диапазон ключа, диапазон значения, признак «строка в кавычках с экранированием»). Вложенный объект или массив пропускается счётом скобок с учётом строк, без рекурсии. Ключ с обратной косой сравнивается после раскодирования (редкий медленный путь). Повторный ключ — берётся первый. Ключ роли ищется сначала дословно (`log.level`), затем как путь во вложенные объекты (`log` → `level`). `null` — поле отсутствует.

### 2. Какая строка «распознана»

- **JSON:** строка начинается с `{` в позиции 0 и даёт хотя бы одну полную пару «ключ — значение» с ключом роли (время, уровень или сообщение). Разбор терпимый: оборванный объект (хвост растущего файла без `'\n'`, строка, обрезанная писателем на 16 КБ) отдаёт пары до обрыва.
- **logfmt:** с позиции 0 идут пары `key=value` (значение голое или в кавычках), и среди них есть ключ роли. `Caused by: x=1` не распознаётся: первый токен не пара.
- **Отступ в начале строки — не распознана.** Так тело многострочного JSON (`  "ts": …`) и текст исключения остаются продолжениями, как по F-12.

Распознанная строка — `schemaMatched = true` в `LineClassifier::isPrimaryLine`, то есть начинает запись (правило F-12 не меняется). Нераспознанная — как сегодня: эвристика классификатора по строке, затем «продолжение текущей записи». Мусор между записями (вывод `printStackTrace` в stdout между JSON-строками) уходит в запись перед ним, как стек-трейс. Правило построчное и смотрит только на ASCII-структуру (`{`, `"`, `=`, ASCII-ключи ролей), поэтому смена кодировки границ не двигает — в отличие от регексной схемы с не-ASCII литералами (известное ограничение F-1).

### 3. Время и уровень из ключей — политика одна

Политика времени живёт только в `LineClassifier`, поэтому значение ключа считает он же. Две новые функции:

- `LineClassifier::timestampFromValue(QStringView value, bool isNumber, EpochUnit, YearReference, qint64& ms)`. Строка — тот же ручной сканер, что у `detectTimestampMs`, по тексту значения (ISO с зоной, access, syslog с годом по mtime — всё как в строке). Число или строка из одних цифр с необязательной дробью — эпоха. Единица — из схемы или по величине при `Auto`: `< 1e11` — секунды (дробь — миллисекунды), `< 1e14` — мс, `< 1e17` — мкс, иначе нс. Усечение до мс, как у дроби строки. Отрицательная эпоха — метка до 1970 (F-13).
- `LineClassifier::levelFromValue(QStringView value, bool isNumber, NumericLevels, LogLevel&)`. Слово — `detectLogLevel` по значению (словарь `kLevelWords` один). Число при `Auto`: 0–7 — syslog (0–2 Fatal, 3 Error, 4 Warning, 5–6 Info, 7 Debug); 10 и больше — шкала pino / Bunyan по десяткам (10 Trace, 20 Debug, 30 Info, 40 Warning, 50 Error, 60+ Fatal). `Python` — 10 Debug, 20 Info, 30 Warning, 40 Error, 50 Fatal.

Ключа нет или значение не читается — метка и уровень ищутся по строке эвристикой, как сегодня: хуже, чем без схемы, не бывает. Нашёлся ключ — эвристика по строке для этой роли не зовётся (это и экономия: сканер метки — самая дорогая стадия `--bench-stages`).

Один вызов на строку для обоих путей загрузки: `LineClassifier::classifyKeyed(const LogPattern&, QStringView text, YearReference) → KeyedClassification {matched, hasTs, tsMs, hasLevel, level}`. Парсер и индексатор зовут его вместо пары детекторов, когда у схемы есть ключевая часть и включено извлечение; правило «одно место — оба бэкенда» держится тем же приёмом, что `isPrimaryLine`. Резидентный парсер строит `QDateTime` из мс тем же путём, что сейчас из `detectTimestamp` (сверить моменты закрепляет `logstore_equivalence`).

### 4. Экранированное значение

Диапазон поля указывает на значение в тексте строки без кавычек — в экранированной форме, как в файле. У `FieldSpan` появляется признак «экранировано» — старший бит `length` (длина поля меньше 2³¹), структура остаётся 8 байт, а резидентная запись не дорожает. Прямых читателей `length` вне `logfield.h` нет: `logpattern.cpp` пишет, остальные идут через `view`/`get`.

Читатели получают значение через новый `LogEntryFields::value(i, text) → QString`: без признака — копия view, с признаком — раскодированная строка (`KeyedLine::unescape`). `get` остаётся для неэкранированных путей, но пять читателей переходят так:

| Читатель | Что видит |
| --- | --- |
| Фильтр по полю (`FilterRuleSet::ruleContains`) | Раскодированное значение: `C:\temp` находится как `C:\temp`, кириллица из `\u0430…` — кириллицей. Аллокация — только для экранированных значений |
| Правило без поля, быстрый поиск, Find All, подсветка | Сырой текст строки, как в файле (не меняется) |
| Текст строки во view и Save View As (`formatDisplayText`) | Раскодированное значение, но управляющие символы (`\n`, `\t`, `\r`) остаются escape-последовательностью: строка view однострочная |
| Entry Details | Раскодированное целиком, с настоящими переводами строк |

Длинные значения ничем не ограничены (`int` смещение и длина, как у регексной схемы); строка в несколько мегабайт стоит столько же, сколько сейчас.

### 5. Хранение и совместимость

Ключевая часть пишется рядом с регексной, **версия формата остаётся 3**:

```json
{ "name": "JSON Lines", "description": "…", "version": 3, "type": "dynamic-block-schema",
  "linePrefix": "", "blocks": [ { "name": "Message", "kind": "remainder", … } ],
  "keyed": { "format": "json", "timeKeys": ["ts","time",…], "levelKeys": […],
             "messageKeys": […], "extraColumns": ["logger","trace_id"],
             "epochUnit": "auto", "numericLevels": "auto" } }
```

- **0.6 и раньше** не знают `keyed`: `parseEntry` кладёт его в `meta` и переписывает дословно, а схема читается как регексная из запасных `blocks` — одна колонка `Message` со всей строкой. Файл не удаляется (он разбирается) и не теряет ключевую часть при пересохранении. Если пользователь в 0.6 правит блоки, 0.7 их не использует — ключевая часть главнее.
- **Версия 4 отвергнута**: из-за удаления неразобранных файлов в `SchemaStore::sync` 0.6 стёр бы такую схему при первой правке каталога.
- **0.7:** `keyed` — ключ формата (`isSchemaFormatKey`), а не метаданные; каноническая строка схемы (`SchemaEntry::schema`, сессия, отпечаток манифеста встроенных схем) включает его. `blocks` ключевой схемы — всегда запасной `Message` (пишет `serializeDefinition`, читатель 0.7 их игнорирует).
- **Попутно, чтобы следующий формат не упёрся в ту же ловушку:** `sync` больше не удаляет файлы, которые не разобрал (только файлы, бывшие записями и выбывшие из списка). Тест — в `schema_store`.
- Сессия хранит схему каноническим определением — ключевая часть едет в ней сама; `SessionController::chooseSchema` сравнивает определения целиком.

### 6. Что видит пользователь

| Место | Что показано |
| --- | --- |
| Лог, «Filter blocks» выключен | Сырая строка, как сейчас |
| Лог, схема JSON Lines и «Filter blocks» включён | Выбранные колонки через пробел: `2026-11-18T10:00:00Z info Request failed` |
| Строка, которую схема не распознала (мусор, пустая, обрыв без ключей ролей) | Сырой текст (правило `formatDisplayText` «полей нет — сырая строка») |
| Log Fields | `Timestamp`, `Level`, `Message` + колонки из `extraColumns` |
| Entry Details | Колонки схемы, затем **все** ключи верхнего уровня строки (`LogPattern::keyValuePairs`), значения раскодированы; вложенный объект — его JSON-текст; блок pretty-print JSON — как сейчас |
| Фильтр по полю | По колонкам схемы; правило по ключу, которого нет в колонках, — «колонки нет в схеме» (`fieldMissing`, нейтрально), редактор схемы добавляет колонку в один щелчок |
| Save View As | Текст view (как сейчас); экспорт полей — F-9 |
| Вложенные объекты и массивы | Значение поля — их JSON-текст как есть; ключ роли достаётся по пути `log.level` |
| Многострочный (pretty-printed) JSON | Не JSONL: строки с отступом — продолжения, первая `{` — своя запись. Entry Details собирает запись и показывает её pretty-print — как сейчас |
| Порядок слитой вкладки | По моменту из ключа: эпоха числом больше не уводит записи в конец |

### 7. Редактор, встроенные схемы, автоопределение

- **Редактор** (`ConversionPatternDialog`): переключатель «Format: Blocks / JSON / logfmt» над цепочкой карточек. В режиме JSON/logfmt вместо цепочки — карточка `CardFrame` (инвариант 9) с полями: ключи времени, уровня, сообщения (списки через запятую, умолчания предзаполнены), единица эпохи, шкала числовых уровней, список колонок с кнопкой «Add keys from sample» (ключи, встреченные в образцах строк). Предпросмотр — та же таблица полей по образцам, через `matchLine`.
- **Встроенные:** `resources/patterns/json-lines.json` и `logfmt.json` по манифесту `BuiltinSchemas` (запасные `blocks` — `Message`). В `resources.qrc` и в списке теста `builtin_schemas`.
- **Автоопределение:** `PatternHeuristics::detectLineFormat(QStringView) → Blocks | Json | Logfmt` (единственное место правила «как выглядит строка JSON / logfmt») и `suggestKeyedSchema(sampleLines)` — формат и `extraColumns` из ключей, встреченных в большинстве образцов. Кнопка Auto-detect редактора на JSON-образце предлагает ключевую схему. F-6 зовёт то же `detectLineFormat` по первым строкам файла и предлагает встроенную «JSON Lines» / «logfmt».

### 8. Горячий путь и цена

- Ключевой разбор — один проход по строке без аллокаций и без регекса; классификатор метки зовётся по короткому значению, а не по строке. Ожидание (оценка, не замер): индексация JSONL с ключевой схемой не медленнее той же индексации без схемы; цель приёмки — **не хуже ×1,2** к прогону без схемы на том же файле.
- Замер: `lineindex_smoke --bench <file> <schema>` (режим уже принимает схему) против `--bench <file>`, и `--bench-resident` получает тот же необязательный аргумент схемы. Файлы — `scripts/generate_test_log.py --format jsonl|logfmt` (новый ключ: те же записи и доля многострочных, эпоха и числовой уровень по флагам), 2 млн строк. Цифры — в раздел «Сделано» шага 2.
- **Инвариант 1:** индексный бэкенд текст не материализует — поля по требованию тем же `extractFields`, как сейчас; `keyValuePairs` зовёт только Entry Details для одной записи.
- **Инвариант 3:** вся новая работа — в воркере парсера и индексатора; GUI-путь батча не меняется.
- Сканер каталога остаётся на эвристике (счётчики и время файла без схемы) — как у регексных схем сегодня.

## Что получается бесплатно, а что нет

- **Фильтры по полю, Search, Row Highlighters по полю, выбор колонок, Save View As** — бесплатно: колонки обычные, значения через `value()`.
- **Время из ключа** — бесплатно для таймлайна, Time Filter, Go to Time, статистики, порядка слитой вкладки: момент лежит там же, где сейчас (индекс и `LogEntry`).
- **F-9 (экспорт полей в CSV / JSON)** — колонки схемы с раскодированными значениями достаются бесплатно через `value()`. Не бесплатно: «все ключи строки» в JSON-экспорте (не только колонки) — F-9 зовёт `keyValuePairs` в своём воркере; решается в F-9.
- **Не бесплатно:** смена схемы на уже открытом файле — метки и границы из ключей требуют перечитать файл (шаг 3); статистика «топ сообщений» по-прежнему считает текст строки, а не поле `Message`.

## Отвергнутые варианты

| Вариант | Почему нет |
| --- | --- |

| Автоопределение формата при каждой загрузке без выбора схемы | Автоопределение живёт в редакторе и в F-6 (предложение), путь загрузки берёт выбранную схему (`CLAUDE.md`, «Открытие файла») |

## Проверки

- **Эталон — заданные значения, а не второй разборщик.** Корпус `keyed_schema` пишет ожидаемые поля и моменты руками; сравнение с `QJsonDocument` — только как дополнительная проба на случайных объектах (фаззинг: случайный объект → строка через `QJsonDocument` → наши поля равны его значениям).
- **Политика времени:** `timestampFromValue` на строке ISO обязана давать тот же момент, что `detectTimestampMs` на той же строке, — закрепить в `lineindex_smoke` рядом с регекс-эквивалентностью.
- **`logstore_equivalence`** — главный трос: фикстуры JSONL и logfmt во всех 33 конфигурациях фильтров плюс правила по полю (`Level`, `Message` с раскодированным значением).
- **Хвост:** объект, дописанный частями (обрыв посреди строки в кавычках, посреди `\u`-последовательности, посреди вложенного объекта), — на обоих бэкендах та же запись и поля, что у файла, записанного разом.
- **Совместимость:** файл схемы с `keyed`, прочитанный путём 0.6 (`deserializeDefinition` без знания `keyed` — имитация в тесте), даёт валидную регексную схему; пересохранение сохраняет `keyed` в метаданных.

## Риски и затронутые инварианты CLAUDE.md

- **Инвариант 1 и 3** — сохраняются (см. «Горячий путь»). Риск — `keyValuePairs` в чужом горячем пути; в заголовке пометить «только для одной записи».
- **Инвариант 4** — `FieldSpan` получает бит, но поля по-прежнему ставит только GUI-поток; `value()` — чтение.
- **Политика времени одна** — новые функции живут в `LineClassifier`; эпоха — новая форма, её правило по величине закрепляется тестом и описывается в справке.
- **Граница записи (F-12)** — правило не меняется, меняется только `schemaMatched`; строки с отступом — продолжения.
- **Формат на диске** — версия 3 намеренно; риск, что будущий формат снова поднимет версию, снимает правка `sync` в шаге 1, но только для версий ≥ 0.7.
- **Цена** — если ×1,2 не достигается, первым делом смотреть ключ с экранированием и путь `log.level`; регексный каскад здесь не участвует.
- **MSVC** — новые типы объявлять одним ключевым словом (`struct KeyedDefinition` везде); `FieldSpan` остаётся `struct`.
- **Неоднозначность числовых уровней** — Python 10/20/30 против pino 10/20/30 различаются только настройкой схемы; `Auto` выбирает pino, Python — явно в редакторе.

## Решения за автором

Если автор не возразил, принимается рекомендованный вариант.

| Вопрос | Рекомендация |
| --- | --- |
| Где живёт JSON | Вид схемы (`keyed` в `LogPattern`), не вид блока и не отдельный класс |
| Ключи по умолчанию | Время `ts`, `time`, `timestamp`, `@timestamp`, `@t`, `t`; уровень `level`, `lvl`, `severity`, `loglevel`, `levelname`, `log.level`, `@l`; сообщение `msg`, `message`, `@m`, `@mt`, `event` — правятся в схеме |
| Эпоха | Единица по величине (`Auto`), можно задать в схеме |
| Числовые уровни | `Auto`: 0–7 — syslog, от 10 — pino / Bunyan; Python — явной настройкой |
| Ключ роли есть, значение не читается | Эвристика по строке, как без схемы |
| Видимое изменение | Колонка `Message` и другие показывают раскодированный текст, а поиск по всей строке — сырой: `\"` в строке, `"` в поле |
| Остальные ключи | Не колонки по умолчанию; видны в Entry Details, колонкой — по кнопке в редакторе |
| Многострочный JSON | Не разбирается как JSON; строки ведут себя как сегодня |
| Действует ли ключевая схема при выключенном «Filter blocks» | Нет — как любая схема; F-6 включает флаг вместе с предложенной схемой |
| Смена ключевой схемы на открытом файле | Перечитывает файл с сохранением позиции (шаг 3) |

## Чего не делаем

- Многострочный (pretty-printed) JSON как одна запись — нужен разбор через строки и своё правило границы.
- JSON после текстового префикса (CRI / Docker: `2026-… stdout F {…}`, `INFO {"a":1}`) — позже блоком «JSON-объект» в регексной цепочке на том же `keyedline`.
- Колонки на каждый ключ файла автоматически и фильтр по произвольному ключу вне колонок.
- Поля, вычисленные из нескольких ключей (`@mt` с подстановкой свойств Serilog), уровень Serilog CLEF по умолчанию (отсутствующий `@l` = Information).
- Схема в сканере каталога (счётчики, время и фильтр по содержимому — по эвристике).
- Статистика «топ сообщений» по полю `Message`.
- Другие форматы ключ-значение (GELF, CEE `@cee:`, `key: value` YAML-подобные).
