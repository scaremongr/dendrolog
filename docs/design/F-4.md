# F-4. JSON Lines и logfmt как источник полей

Статус: спроектирован 19 ноября 2026, действуют рекомендованные варианты (автор передал продуктовые решения исполнителям). Задача `F-4` из `docs/roadmap.md`, релиз 0.7. Код читался на `06aa5eb` (0.6.0). Связана с `docs/design/F-5.md` (схема на вкладку и на файл): вид схемы — свойство схемы, а не вкладки, поэтому на файл он становится сам, когда F-5 делает схему пофайловой.

## Задача и границы

Лог в JSON Lines (`{"ts":"…","level":"info","msg":"…",…}` — по объекту на строку) или в logfmt (`ts=… level=info msg="…" user=42`) сейчас разбирается эвристикой «где в строке метка и слово уровня»: эпоха числом (`"time":1700000000123`) и числовой уровень pino (`"level":30`) не видны, метку может взять не тот ключ, а поля регексной схемой не извлечь — значения в кавычках с экранированием и ключи в любом порядке. Нужно, чтобы время, уровень и сообщение брались из ключей, поля были доступны фильтрам и колонкам, и оба бэкенда давали одно и то же.

Входит:

- новый вид схемы «по ключам» с двумя форматами строки: JSON-объект и logfmt;
- время, уровень и граница записи из ключей на обоих бэкендах, при загрузке и дозаписи;
- поля со значениями в экранированной форме (JSON `\"`, `\n`, `\uXXXX`; logfmt `\"`, `\\`) — фильтр и Entry Details видят раскодированное значение;
- хранение в `patterns/*.json` с прямой совместимостью: 0.6 читает каталог с новой схемой и не теряет её;
- встроенные схемы «JSON Lines» и «logfmt», редактор, автоопределение формата по образцу.

## Как устроено сейчас

- **Метка и уровень — без схемы.** Индексатор на каждую строку зовёт `detectTimestampMs` и `detectLogLevel` по сырому тексту (`src/logindexer.cpp:199-207`); схему спрашивает, только если строка не первична без неё, и только ради решения «первичная или продолжение» — спаны выбрасываются (`:208-217`). Парсер делает то же, но спаны оставляет в записи (`src/logparser.cpp:302-320`). Правило границы — `LineClassifier::isPrimaryLine(schemaMatched, …)` (F-12). Схема участвует, только когда включено извлечение полей («Filter blocks»): флаг `extraction` у обоих.
- **На JSONL эвристика работает наполовину.** ISO-метка ищется где угодно в строке (самая левая), но `{"ts":"2026-…"` — не ведущая метка (позиция 7), поэтому запись начинается, только если в строке нашлось и слово уровня. Слово ищется по всей строке: `"msg":"retry after error"` при `"level":30` даст ERROR. Эпоха числом меткой не считается — записи без метки уходят в конец слитой вкладки.
- **Поле — диапазон в тексте строки.** `FieldSpan` — (смещение, длина) в `QString` строки, без копирования (`src/logfield.h`); `LogEntryFields::get` отдаёт `QStringView`. Читателей значения пять: фильтр (`src/filterruleset.cpp:122-127`), текст строки view и Save View As (`LogModel::formatDisplayText`, `src/logmodel.cpp:603-629`, и длина `:656`), Entry Details (`src/entrydetailspanel.cpp:569`, `:682`). Экранированное значение подстрокой не является — его так не отдать.
- **Индексный бэкенд извлекает поля по требованию** той же `LogPattern::extractFields`: строка для показа (`src/indexedlogstore.cpp:707`), снапшот для экспорта (`:1262-1270`), поисковая база (`:1345`), фильтр-воркер (`:1478`) — схема копией в воркер.
- **Смена схемы меняет только поля.** `MainWindow::applyPatternToAllViews` (`src/mainwindow.cpp:1724`) переизвлекает поля резидентных записей (синхронно или `FieldReextraction`, инвариант 4) и отдаёт новую схему индексному стору. Метки, уровни и границы записей остаются с момента загрузки — на обоих бэкендах.
- **Формат схемы на диске** — `LogPattern::serializeDefinition`: `{"version":3,"type":"dynamic-block-schema","linePrefix":…,"blocks":[…]}` плюс `name` и метаданные (`src/schemastore.h`). Читатель отказывается от версии больше 3 и от неизвестного `kind` блока (`src/logpattern.cpp:411`, `:426`). Неизвестные ключи верхнего уровня `SchemaStore::parseEntry` хранит в `meta` и переписывает дословно (Q-17); список ключей формата — `isSchemaFormatKey` (`src/schemastore.cpp:87`).
- **Ловушка совместимости.** `SchemaStore::sync` удаляет из каталога каждый `*.json`, который не стал записью списка, в том числе тот, что не разобрался (`src/schemastore.cpp:338-342`). `sync` зовут после OK в редакторе схем и при открытии сессии с новой схемой (`src/mainwindow.cpp:1671`, `:4084`). Значит, схема с версией 4 или неизвестным видом блока в 0.6 молча удаляется при первой правке каталога.
- **Сканер каталога схему не использует вовсе** (`LogParser::analyzeFileForStats`, `src/logparser.cpp:466-470`) — счётчики и время файла по эвристике.

## Решение

### 1. Вид схемы, а не вид блока

`LogPattern` остаётся единственным типом схемы во всём коде и получает второй движок. Определение — `PatternDefinition` плюс необязательная часть `KeyedDefinition`:

```cpp
struct KeyedDefinition {
    enum class Format { JsonObject, Logfmt };
    enum class EpochUnit { Auto, Seconds, Millis, Micros, Nanos };
    enum class NumericLevels { Auto, Syslog, Python };
    Format        format = Format::JsonObject;
    QStringList   timeKeys    {"ts","time","timestamp","@timestamp","@t","t"};
    QStringList   levelKeys   {"level","lvl","severity","loglevel","levelname","log.level","@l"};
    QStringList   messageKeys {"msg","message","@m","@mt","event"};
    QStringList   extraColumns;          // ключи, ставшие колонками, в порядке колонок
    EpochUnit     epochUnit = EpochUnit::Auto;
    NumericLevels numericLevels = NumericLevels::Auto;
};
```

Когда `KeyedDefinition` есть, `matchLine` / `extractFields` / `fieldNames` идут через ключевой движок, а регексный каскад не строится. Колонки: `Timestamp`, `Level`, `Message`, затем `extraColumns` по именам ключей. Имена ролей совпадают с колонками встроенных регексных схем (Python logging, Spring Boot) — правило фильтра `Level contains ERROR` и выбор колонок по имени переносятся между схемами, а слитая вкладка F-5 объединяет колонки по имени.

Почему не новый вид блока: блок — позиционный кусок регекса, а у JSON-строки нет позиций, ключи идут в любом порядке. Почему не отдельный класс схемы: `LogPattern` копией уходит в `LogParser`, `LogIndexer`, `IndexedLogStore`, `FieldReextraction`, снапшоты и сессию — второй тип пришлось бы протащить во все эти места, а фасад не меняет ни одной сигнатуры.

Разбор строки — новый модуль ядра `keyedline.{h,cpp}`: токенизатор JSON-объекта и logfmt по `QStringView` без аллокаций. Отдаёт пары (диапазон ключа, диапазон значения, признак «строка в кавычках с экранированием»). Вложенный объект или массив пропускается счётом скобок с учётом строк, без рекурсии. Ключ с обратной косой сравнивается после раскодирования (редкий медленный путь). Повторный ключ — берётся первый. Ключ роли ищется сначала дословно (`log.level`), затем как путь во вложенные объекты (`log` → `level`). `null` — поле отсутствует.

### 2. Какая строка «распознана»

- **JSON:** строка начинается с `{` в позиции 0 и даёт хотя бы одну полную пару «ключ — значение» с ключом роли (время, уровень или сообщение). Разбор терпимый: оборванный объект (хвост растущего файла без `'\n'`, строка, обрезанная писателем на 16 КБ) отдаёт пары до обрыва.
- **logfmt:** с позиции 0 идут пары `key=value` (значение голое или в кавычках), и среди них есть ключ роли. `Caused by: x=1` не распознаётся: первый токен не пара.
- **Отступ в начале строки — не распознана.** Так тело многострочного JSON (`  "ts": …`) и текст исключения остаются продолжениями, как по F-12.

Распознанная строка — `schemaMatched = true` в `LineClassifier::isPrimaryLine`, то есть начинает запись (правило F-12 не меняется). Нераспознанная — как сегодня: эвристика классификатора по строке, затем «продолжение текущей записи». Мусор между записями (вывод `printStackTrace` в stdout между JSON-строками) уходит в запись перед ним, как стек-трейс. Правило построчное и смотрит только на ASCII-структуру (`{`, `"`, `=`, ASCII-ключи ролей), поэтому смена кодировки границ не двигает — в отличие от регексной схемы с не-ASCII литералами (известное ограничение F-1).

### 3. Время и уровень из ключей — политика одна

Политика времени живёт только в `LineClassifier`, поэтому значение ключа считает он же. Две новые функции:

- `LineClassifier::timestampFromValue(QStringView value, bool isNumber, EpochUnit, YearReference, qint64& ms)`. Строка — тот же ручной сканер, что у `detectTimestampMs`, по тексту значения (ISO с зоной, access, syslog с годом по mtime — всё как в строке). Число или строка из одних цифр с необязательной дробью — эпоха. Единица — из схемы или по величине при `Auto`: `< 1e11` — секунды (дробь — миллисекунды), `< 1e14` — мс, `< 1e17` — мкс, иначе нс. Усечение до мс, как у дроби строки. Отрицательная эпоха — метка до 1970 (F-13).
- `LineClassifier::levelFromValue(QStringView value, bool isNumber, NumericLevels, LogLevel&)`. Слово — `detectLogLevel` по значению (словарь `kLevelWords` один). Число при `Auto`: 0–7 — syslog (0–2 Fatal, 3 Error, 4 Warning, 5–6 Info, 7 Debug); 10 и больше — шкала pino / Bunyan по десяткам (10 Trace, 20 Debug, 30 Info, 40 Warning, 50 Error, 60+ Fatal). `Python` — 10 Debug, 20 Info, 30 Warning, 40 Error, 50 Fatal.

Ключа нет или значение не читается — метка и уровень ищутся по строке эвристикой, как сегодня: хуже, чем без схемы, не бывает. Нашёлся ключ — эвристика по строке для этой роли не зовётся (это и экономия: сканер метки — самая дорогая стадия `--bench-stages`).

Один вызов на строку для обоих путей загрузки: `LineClassifier::classifyKeyed(const LogPattern&, QStringView text, YearReference) → KeyedClassification {matched, hasTs, tsMs, hasLevel, level}`. Парсер и индексатор зовут его вместо пары детекторов, когда у схемы есть ключевая часть и включено извлечение; правило «одно место — оба бэкенда» держится тем же приёмом, что `isPrimaryLine`. Резидентный парсер строит `QDateTime` из мс тем же путём, что сейчас из `detectTimestamp` (сверить моменты закрепляет `logstore_equivalence`).

### 4. Экранированное значение

Диапазон поля указывает на значение в тексте строки без кавычек — в экранированной форме, как в файле. У `FieldSpan` появляется признак «экранировано» — старший бит `length` (длина поля меньше 2³¹), структура остаётся 8 байт, а резидентная запись не дорожает. Прямых читателей `length` вне `logfield.h` нет: `logpattern.cpp` пишет, остальные идут через `view`/`get`.

Читатели получают значение через новый `LogEntryFields::value(i, text) → QString`: без признака — копия view, с признаком — раскодированная строка (`KeyedLine::unescape`). `get` остаётся для неэкранированных путей, но пять читателей переходят так:

| Читатель | Что видит |
| --- | --- |
| Фильтр по полю (`FilterRuleSet::ruleContains`) | Раскодированное значение: `C:\temp` находится как `C:\temp`, кириллица из `\u0430…` — кириллицей. Аллокация — только для экранированных значений |
| Правило без поля, быстрый поиск, Find All, подсветка | Сырой текст строки, как в файле (не меняется) |
| Текст строки во view и Save View As (`formatDisplayText`) | Раскодированное значение, но управляющие символы (`\n`, `\t`, `\r`) остаются escape-последовательностью: строка view однострочная |
| Entry Details | Раскодированное целиком, с настоящими переводами строк |

Длинные значения ничем не ограничены (`int` смещение и длина, как у регексной схемы); строка в несколько мегабайт стоит столько же, сколько сейчас.

### 5. Хранение и совместимость

Ключевая часть пишется рядом с регексной, **версия формата остаётся 3**:

```json
{ "name": "JSON Lines", "description": "…", "version": 3, "type": "dynamic-block-schema",
  "linePrefix": "", "blocks": [ { "name": "Message", "kind": "remainder", … } ],
  "keyed": { "format": "json", "timeKeys": ["ts","time",…], "levelKeys": […],
             "messageKeys": […], "extraColumns": ["logger","trace_id"],
             "epochUnit": "auto", "numericLevels": "auto" } }
```

- **0.6 и раньше** не знают `keyed`: `parseEntry` кладёт его в `meta` и переписывает дословно, а схема читается как регексная из запасных `blocks` — одна колонка `Message` со всей строкой. Файл не удаляется (он разбирается) и не теряет ключевую часть при пересохранении. Если пользователь в 0.6 правит блоки, 0.7 их не использует — ключевая часть главнее.
- **Версия 4 отвергнута**: из-за удаления неразобранных файлов в `SchemaStore::sync` 0.6 стёр бы такую схему при первой правке каталога.
- **0.7:** `keyed` — ключ формата (`isSchemaFormatKey`), а не метаданные; каноническая строка схемы (`SchemaEntry::schema`, сессия, отпечаток манифеста встроенных схем) включает его. `blocks` ключевой схемы — всегда запасной `Message` (пишет `serializeDefinition`, читатель 0.7 их игнорирует).
- **Попутно, чтобы следующий формат не упёрся в ту же ловушку (сделано раньше шага 1, задача Q-23):** `sync` больше не удаляет файлы, которые не разобрал (только файлы, бывшие записями и выбывшие из списка). Тест — в `schema_store`.
- Сессия хранит схему каноническим определением — ключевая часть едет в ней сама; `SessionController::chooseSchema` сравнивает определения целиком.

### 6. Что видит пользователь

| Место | Что показано |
| --- | --- |
| Лог, «Filter blocks» выключен | Сырая строка, как сейчас |
| Лог, схема JSON Lines и «Filter blocks» включён | Выбранные колонки через пробел: `2026-11-18T10:00:00Z info Request failed` |
| Строка, которую схема не распознала (мусор, пустая, обрыв без ключей ролей) | Сырой текст (правило `formatDisplayText` «полей нет — сырая строка») |
| Log Fields | `Timestamp`, `Level`, `Message` + колонки из `extraColumns` |
| Entry Details | Колонки схемы, затем **все** ключи верхнего уровня строки (`LogPattern::keyValuePairs`), значения раскодированы; вложенный объект — его JSON-текст; блок pretty-print JSON — как сейчас |
| Фильтр по полю | По колонкам схемы; правило по ключу, которого нет в колонках, — «колонки нет в схеме» (`fieldMissing`, нейтрально), редактор схемы добавляет колонку в один щелчок |
| Save View As | Текст view (как сейчас); экспорт полей — F-9 |
| Вложенные объекты и массивы | Значение поля — их JSON-текст как есть; ключ роли достаётся по пути `log.level` |
| Многострочный (pretty-printed) JSON | Не JSONL: строки с отступом — продолжения, первая `{` — своя запись. Entry Details собирает запись и показывает её pretty-print — как сейчас |
| Порядок слитой вкладки | По моменту из ключа: эпоха числом больше не уводит записи в конец |

### 7. Редактор, встроенные схемы, автоопределение

- **Редактор** (`ConversionPatternDialog`): переключатель «Format: Blocks / JSON / logfmt» над цепочкой карточек. В режиме JSON/logfmt вместо цепочки — карточка `CardFrame` (инвариант 9) с полями: ключи времени, уровня, сообщения (списки через запятую, умолчания предзаполнены), единица эпохи, шкала числовых уровней, список колонок с кнопкой «Add keys from sample» (ключи, встреченные в образцах строк). Предпросмотр — та же таблица полей по образцам, через `matchLine`.
- **Встроенные:** `resources/patterns/json-lines.json` и `logfmt.json` по манифесту `BuiltinSchemas` (запасные `blocks` — `Message`). В `resources.qrc` и в списке теста `builtin_schemas`.
- **Автоопределение:** `PatternHeuristics::detectLineFormat(QStringView) → Blocks | Json | Logfmt` (единственное место правила «как выглядит строка JSON / logfmt») и `suggestKeyedSchema(sampleLines)` — формат и `extraColumns` из ключей, встреченных в большинстве образцов. Кнопка Auto-detect редактора на JSON-образце предлагает ключевую схему. F-6 зовёт то же `detectLineFormat` по первым строкам файла и предлагает встроенную «JSON Lines» / «logfmt».

### 8. Горячий путь и цена

- Ключевой разбор — один проход по строке без аллокаций и без регекса; классификатор метки зовётся по короткому значению, а не по строке. Ожидание (оценка, не замер): индексация JSONL с ключевой схемой не медленнее той же индексации без схемы; цель приёмки — **не хуже ×1,2** к прогону без схемы на том же файле.
- Замер: `lineindex_smoke --bench <file> <schema>` (режим уже принимает схему) против `--bench <file>`, и `--bench-resident` получает тот же необязательный аргумент схемы. Файлы — `scripts/generate_test_log.py --format jsonl|logfmt` (новый ключ: те же записи и доля многострочных, эпоха и числовой уровень по флагам), 2 млн строк. Цифры — в раздел «Сделано» шага 2.
- **Инвариант 1:** индексный бэкенд текст не материализует — поля по требованию тем же `extractFields`, как сейчас; `keyValuePairs` зовёт только Entry Details для одной записи.
- **Инвариант 3:** вся новая работа — в воркере парсера и индексатора; GUI-путь батча не меняется.
- Сканер каталога остаётся на эвристике (счётчики и время файла без схемы) — как у регексных схем сегодня.

## Что получается бесплатно, а что нет

- **Фильтры по полю, Search, Row Highlighters по полю, выбор колонок, Save View As** — бесплатно: колонки обычные, значения через `value()`.
- **Время из ключа** — бесплатно для таймлайна, Time Filter, Go to Time, статистики, порядка слитой вкладки: момент лежит там же, где сейчас (индекс и `LogEntry`).
- **F-9 (экспорт полей в CSV / JSON)** — колонки схемы с раскодированными значениями достаются бесплатно через `value()`. Не бесплатно: «все ключи строки» в JSON-экспорте (не только колонки) — F-9 зовёт `keyValuePairs` в своём воркере; решается в F-9.
- **Не бесплатно:** смена схемы на уже открытом файле — метки и границы из ключей требуют перечитать файл (шаг 3); статистика «топ сообщений» по-прежнему считает текст строки, а не поле `Message`.

## Проверки

- **Эталон — заданные значения, а не второй разборщик.** Корпус `keyed_schema` пишет ожидаемые поля и моменты руками; сравнение с `QJsonDocument` — только как дополнительная проба на случайных объектах (фаззинг: случайный объект → строка через `QJsonDocument` → наши поля равны его значениям).
- **Политика времени:** `timestampFromValue` на строке ISO обязана давать тот же момент, что `detectTimestampMs` на той же строке, — закрепить в `lineindex_smoke` рядом с регекс-эквивалентностью.
- **`logstore_equivalence`** — главный трос: фикстуры JSONL и logfmt во всех 33 конфигурациях фильтров плюс правила по полю (`Level`, `Message` с раскодированным значением).
- **Хвост:** объект, дописанный частями (обрыв посреди строки в кавычках, посреди `\u`-последовательности, посреди вложенного объекта), — на обоих бэкендах та же запись и поля, что у файла, записанного разом.
- **Совместимость:** файл схемы с `keyed`, прочитанный путём 0.6 (`deserializeDefinition` без знания `keyed` — имитация в тесте), даёт валидную регексную схему; пересохранение сохраняет `keyed` в метаданных.

## Чего не делаем

- Многострочный (pretty-printed) JSON как одна запись — нужен разбор через строки и своё правило границы.
- JSON после текстового префикса (CRI / Docker: `2026-… stdout F {…}`, `INFO {"a":1}`) — позже блоком «JSON-объект» в регексной цепочке на том же `keyedline`.
- Колонки на каждый ключ файла автоматически и фильтр по произвольному ключу вне колонок.
- Поля, вычисленные из нескольких ключей (`@mt` с подстановкой свойств Serilog), уровень Serilog CLEF по умолчанию (отсутствующий `@l` = Information).
- Схема в сканере каталога (счётчики, время и фильтр по содержимому — по эвристике).
- Статистика «топ сообщений» по полю `Message`.
- Другие форматы ключ-значение (GELF, CEE `@cee:`, `key: value` YAML-подобные).

## Сделано

### PR 1. Ядро ключевой схемы — 25 ноября 2026

Новый модуль ядра `src/keyedline.*` (`DENDROLOG_CORE_SOURCES`): `KeyedDefinition`, `KeyedLine::PairReader` (пары JSON-объекта и logfmt без аллокаций), `KeyedLine::Lookup` (колонки по ключам), `KeyedLine::unescape`. `LogPattern` получил ключевой движок (`PatternDefinition::keyed`, `isKeyed`/`keyed`, `scanKeyed`, `keyValuePairs`; `matchLine`, `extractFields`, `fieldNames` и (де)сериализация с `keyed`), `FieldSpan` — бит «экранировано» (`size`/`isEscaped`/`set`), `LogEntryFields::value` / `isEscaped`; пять читателей переведены (`FilterRuleSet::ruleContains`, `LogModel::formatDisplayText` и `displayTextLength`, две строки Entry Details). `LineClassifier`: `timestampFromValue`, `epochFromValue`, `levelFromValue`, `classifyKeyed` → `KeyedClassification`; детекторы `detectTimestamp[Ms]` / `detectLogLevel` принимают `QStringView` (значение — подстрока строки, без копии). `isSchemaFormatKey` знает `keyed`. Пункт «`sync` не удаляет неразобранные файлы» сделан раньше задачей Q-23. Тесты: новый `tests/keyed_schema`, `lineindex_smoke` (`testKeyedValues`), `schema_store` (`testKeyedSchema`). Пользователь пока ничего не видит: парсер и индексатор `classifyKeyed` ещё не зовут (PR 2), ключевую схему не создать без правки файла (PR 4) — `CHANGELOG.md` и справки не менялись.

**Цена горячего пути** (`keyed_schema --bench 200000`, облачная машина, Release; на строку): ключевая схема — `classifyKeyed` + `extractFields` **~380–390 нс**, регексная схема на тех же записях в текстовом виде (детекторы метки и уровня + `extractFields` регексом, как парсер сегодня) **~1350–1400 нс** — ключевая **×0,27–0,29** к регексной (цель ×1,2 выполнена с запасом). Путь индексатора (только `classifyKeyed`, поля по требованию) — ~200–215 нс, из них разбор пар и поиск колонок ~125 нс; детекторы без схемы на тех же JSON-строках — ~85 нс. Для PR 2 (цель — индексация с ключевой схемой не дороже ×1,2 к индексации без схемы): разница ~120 нс на строку против ~420 нс полной индексации строки на 2-ГБ замере — если ×1,2 не уложится, первым делом — разбор пар. Проверка в тесте — ключевая не дороже ×1,2 регексной (+20 мс на шум), под санитайзером только печать: санитайзер инструментирует наш разбор, но не pcre2.

**Решения сверх документа:**

- **`KeyedDefinition` — в `keyedline.h`, а не в `logpattern.h`**: перечисления единицы эпохи и шкалы уровней нужны `LineClassifier`, а ему незачем тянуть регексный движок. `struct` везде (MSVC).
- **Пустое значение — поля нет**, как у регексной схемы с пустым захватом; `null` и пустое не загораживают следующего кандидата той же колонки (`{"msg":null,"message":"x"}` → `x`). Приоритет кандидатов — порядок в списке ключей, где бы ключ ни стоял в строке; на одной позиции списка дословный ключ (`log.level`) главнее пути (`log` → `level`); повторный ключ — первый.
- **Терпимость разбора.** JSON: лишние запятые пропускаются, голый токен в конце оборванной строки принимается (строка без `'\n'` и так перечитывается дозаписью), вид скобки во вложенном не сверяется. logfmt: ключ — как у go-logfmt (всё выше пробела, кроме `=` и `"`); токен без `=` после первой пары пропускается (`msg=hello world` → `hello`); голое `null` — тоже «поля нет»; оборванное значение в кавычках обрывает разбор.
- **`unescape` один на оба формата**: последовательности JSON — надмножество того, что пишет logfmt. Неизвестная или битая последовательность остаётся как в файле, одиночный суррогат `\uD83D` — как есть. Признак экранирования ставится только значению-строке с обратной косой: значения без неё читаются без аллокаций.
- **Эпоха**: строка из цифр — тоже эпоха (`"ts":"1700000000"`), экспонента — нет; не больше 19 цифр (нс после 1973 года — 19 цифр; 20 — не читается, а не переполняется), только годы 0001–9999; отрицательная — вниз до мс (как у дроби строки). Число JSON / logfmt, не ставшее эпохой, сканеру строки не отдаётся. Время без даты (F-11) из значения не читается — у значения нет контекста файла.
- **Уровень**: строка из цифр — тоже по шкале; 8–9 при `Auto`, больше 7 при `Syslog`, меньше 10 при `Python`, дробь и отрицательное — «не уровень» (дальше эвристика по строке).
- **`classifyKeyed` сам делает откат на эвристику** (принимает `ClockDates` и отдаёт `leading`), а не только значения ключей: вызывающему (PR 2) хватит одного вызова и `KeyedClassification::isPrimary()`. Не ключевая схема — только эвристика, `matched = false`. Момент из ключа сбрасывает `clock->matched`.
- **`matchLine` ключевой схемы**: `BlockSpan::blockIndex` — номер колонки (блоки — только запасной `Message`); редактор раскрашивает по нему же.
- **Чужая ключевая часть** (неизвестный формат, единица, шкала, ключ не того типа) — отказ, как у неизвестного вида блока: схема не читается, файл переживает правку каталога (Q-23). Ключевая схема валидна, если имена колонок (роли + `extraColumns`) непустые и не повторяются без учёта регистра — правила привязаны к колонкам по имени.
- **Редактор схем до PR 4 не теряет ключевую часть**: `ConversionPatternDialog` хранит `keyed` загруженной схемы и возвращает его в `currentDefinitionFromEditor` (Apply правки описания или имени). Карточки блоков ключевой схемы и Add Block недоступны (подсказка: колонки задаёт файл схемы) — правка запасных блоков не подействовала бы, а молча терять её нельзя (находка ревью). Автоопределение, пресет и Grok заменяют схему целиком и сбрасывают `keyed` — это явное действие «сделать регексную». Ключевого режима в редакторе ещё нет.
- **Откат на эвристику по всей строке оставлен, как решено в документе** («хуже, чем без схемы, не бывает»): ревью заметило, что при нечитаемом ключе времени эвристика возьмёт самую левую дату строки, в том числе из чужого поля (`{"user":{"created":"2019-…"},"time":"bogus"}`). Так же строку читает приложение без схемы; сузить откат до значения ключа можно отдельной задачей, если это встретится на деле.
- **Длина строки view** (`LogModel::displayTextLength`) для экранированных значений считается без построения строки — `KeyedLine::unescapedSize` / `LogEntryFields::valueSize` (находка ревью: раскладка view зовёт её на каждую строку).
- **Разбор пар — SSE2** (x86-64: всегда есть; иначе по одному юниту): поиск `"` или `\` по 8 юнитов за шаг. Без него разбор пар стоил ~240 нс на строку из 180 символов, с ним ~80.

### PR 2. Загрузка из ключей — 25 ноября 2026

Классификация строки на загрузке — одна функция `LineClassifier::classifyLine(keyedSchema, line, year, clock, fields)`: её зовут `LogParser::parseFrom` (загрузка, дозапись, перечитывание оборванного хвоста), `LogIndexer::doIndex` (загрузка, порции, предварительный хвост) и `LogParser::analyzeFileForStats`. Ключевая схема (только при включённом извлечении полей, как любая схема) — момент, уровень и «распознана» из ключей с откатом на эвристику по строке; без неё — эвристика, как раньше. Резидентный парсер получает поля распознанной строки тем же проходом (`LogPattern::keyedFields` по найденным колонкам — без второго разбора); индексатор полей не строит, индексный стор извлекает их по требованию (`extractFields`, как с PR 1) — для него ничего менять не пришлось. **S-17 — 26 ноября 2026.** Цель ×1,2 к тому же файлу без схемы выполнена на всех трёх файлах. Замер — облачная машина, 4 ядра, Release, по 2 млн строк из генератора (`--format logfmt`, `--format logfmt --epoch`, `--format jsonl`), `lineindex_smoke --bench <file> [logfmt|jsonl]`, медиана 9 прогонов; шаг опроса конца индексации в замере уменьшен с 20 до 1 мс (шаг 20 мс давал шум ~4 %), «до» перемерено с тем же шагом:

| Файл, индексный путь | Без схемы | Ключевая схема до | Ключевая схема после |
| --- | --- | --- | --- |
| logfmt, ISO | 0,42–0,43 с | 0,545 с (×1,30) | 0,457 с (**×1,07**) |
| logfmt, эпоха в мс | 0,43–0,45 с | 0,511 с (×1,14) | 0,438 с (×1,02) |
| JSON Lines, ISO | 0,43–0,46 с | 0,550 с (×1,23) | 0,459 с (×1,00) |

Резидентный путь (`--bench-resident`, медиана 5): logfmt и JSON Lines — ×1,14 (до — ×1,16–1,27, шум этого замера больше); здесь ключевая схема строит поля записи, и разбор строки идёт до конца. `keyed_schema --bench`: классификация без полей — 88 нс на строку JSON против 86 нс у детекторов без схемы (до — ~185 нс).

Что было дорого (callgrind на 200 тыс. строк logfmt, индексатор): `Lookup::scan` — ~1400 инструкций на строку, из них пары — `nextLogfmt` с поиском концов ~100 на пару, `consider` ~130 на пару; строка читалась до `msg`, хотя индексатору сообщение не нужно. И вторая, неожиданная часть: голое значение logfmt `ts=2026-11-18T10:00:00Z` начинается с цифры и было «числом» — `timestampFromValue` отвергал его (число не читается как текст), и момент брала эвристика по всей строке. Это ещё и дефект: момент — самая левая метка строки, а не значение `ts` (`start=… ts=…` — момент `start`).

Сделано:

- **Классификация без полей кончает строку на метке и уровне.** `KeyedLine::Lookup::scan(line, hits, neededColumns)` (и `LogPattern::scanKeyed`) — разбор кончается, когда у первых `neededColumns` колонок найден первый ключ-кандидат. `classifyLine` без полей (индексатор, `analyzeFileForStats`) просит две — Timestamp и Level; с полями (резидентный парсер) — все. Ответ «распознана» не меняется: найденная колонка роли — уже «да»; второй кандидат (`time`) разбор не останавливает — первый (`ts`) может стоять дальше. Тест — `keyed_schema` (`testEarlyExit`): заданные случаи (поздний главный ключ, повтор, `null`, путь `log.level`, ключ с `\u`, оборванная строка) и 4000 случайных строк обоих форматов — классификация без полей равна классификации с полями, разбор двух колонок — полному разбору для них.
- **Голое значение logfmt — «число» только вида `[-]цифры[.цифры]`** (форма, которую читает `epochFromValue`; у JSON вид значения не изменился). `2026-…`, `5xx`, `1e3` — текст: метка читается сканером меток по значению ключа, уровень — словарём. Тест — `keyed_schema` (`testClassifyKeyed`): `start=… ts=…` — момент из `ts`; вид пар по токенам.
- Конец первого ключа logfmt, найденный конструктором `PairReader` (проверка «строка — пары»), не ищется второй раз.

Чего не делали: разбор logfmt без `Pair` на каждую пару (ключ против корзины до разбора значения), предложенный в постановке, — после первых двух пунктов индексатор читает две пары на строку, и выигрыш остался бы только у резидентного пути (там разница с прогоном без схемы — в основном построение полей записи).

**Решения сверх документа:**

- **Одна функция `classifyLine` с указателем на схему** (nullptr — без схемы), а не `classifyKeyed` по ссылке: вызывающему не нужно заводить пустую схему для «извлечение выключено», и правило «ключевая схема действует только с извлечением полей» записано у вызывающих одной строкой (`extraction && pattern.isKeyed()`).
- **`analyzeFileForStats` берёт то же правило со схемой своего парсера** (ключевая и извлечение включено), но сканер каталога схему не задаёт — его счётчики остаются на эвристике, как в документе («Чего не делаем: схема в сканере»). Правило при этом одно на три места, и тест закрепляет обе стороны. Регексная схема в счётчиках по-прежнему не участвует (её цена — регекс на каждую строку).
- **Поля резидентной записи — из того же прохода** (`LogPattern::keyedFields`): без этого строка разбиралась бы дважды (`classifyKeyed` и `extractFields`).
- **Ранний конец разбора строки** — когда у каждой колонки найден её первый кандидат (`rank 0`): следующий ключ ничего не поменяет (повторный ключ — первый, кандидат хуже не вытесняет лучшего). На строке с ключами после `msg` это главная экономия; значение и «распознана» от этого не меняются.
- **Тест хвоста частями сравнивает с файлом, прочитанным разом**, а не с заданными значениями после каждой порции: оборванный объект законно распознаётся по-разному в зависимости от места обрыва (пары до обрыва), эталон для промежуточных состояний — то, что вкладка показала бы на тех же байтах. Итог после последней порции — против заданных значений.
- **`appendIndexedTail(…, markNew)`** в `tests/common/testdocuments.h` — дописанные строки можно не помечать «новыми», чтобы сравнить вкладку с загруженной разом.
- **Промежуточное ограничение до PR 3 (находка ревью):** смена схемы на открытой вкладке переизвлекает только поля, а дозапись после смены уже классифицируется новой схемой — у вкладки, переключённой с регексной (или без схемы) на ключевую и обратно, старые строки держат прежние моменты и границы, новые — из ключей. Так же было и с регексной схемой (дозапись решала «первичная ли» по новой схеме); перечитывание файла при смене ключевой части — PR 3. Без правки файла схемы ключевую схему до PR 4 не выбрать. Снято в PR 3.
- **Имена ключей не из ASCII (находка ревью):** с ключом вроде `время=` распознавание строки зависит от декодера файла, а индексная вкладка при смене или пересмотре кодировки строки не переклассифицирует (`rereadWithNewDecoder` без переиндексации) — резидентная перечитывает. Это то же известное ограничение, что у регексной схемы с не-ASCII литералами (`docs/roadmap.md`, «Осталось после шага 3а из F-1»), туда и записано; ключи по умолчанию и значения времени и уровня — ASCII, их это не касается.

### PR 3. Смена схемы перечитывает файл — 26 ноября 2026

Смена схемы на открытой вкладке, при которой меняется то, что схема решает при ЧТЕНИИ, перечитывает файлы этой вкладки (F-5: одной, а не всех). Что именно — `LogViewWidget::readingSignature`: ключевая часть схемы без `extraColumns` (формат, ключи ролей, единица эпохи, шкала уровней), пока включено извлечение полей; иначе пусто. Подпись сравнивают `setFieldSettings`, `setParserPattern` и `setExtractionEnabled` — смена в любую сторону (было или стало `keyed`, «Filter blocks» у ключевой схемы, другие ключи ролей) зовёт `rereadAfterSchemaChange`. Резидентный путь — `startReencode(file, rekey)`: разбор в сторону новой схемой, затем `invalidateFileRows` (локатор, закладки, история), `replaceEntriesForFile` под одним reset и порция локатору в порядке файла; индексный — `startFullReload` (переиндексация, как у переписанного файла, Q-19). Файл, чей проход идёт, перечитывается по его концу (`FileReloadState::schemaRereadPending`; у резидентного вместе с отложенной сменой кодировки — один разбор). Позиция — строка (источник + `RecordId`) и её место на экране, снятые до перечитывания; запрос к `RecordLocator` уходит после сброса строк её файла (`requestRereadPosition` → путь `m_pendingPosition` из R-4: пользователь, успевший что-то сделать, главнее). Entry Details — раздел **Keys (N)**: все пары `LogPattern::keyValuePairs` строки по схеме её файла (`LogModel::fileSchemaFor`; окно передаёт её в `showEntry`), с копированием `⧉`. Описания встроенных JSON Lines и logfmt говорят про ключи в Entry Details. Тесты: `logview_lifecycle` (`checkKeyedSchemaSwitch`, оба бэкенда: без схемы → JSON Lines → без извлечения → с извлечением → регексная → другая регексная → JSON Lines → только колонки → без схемы; на каждом шаге строки, моменты, уровни и id записей = вкладка, открытая сразу с этой схемой, текущая строка выделена и на своём месте экрана, закладка на своей строке; история переходов после всех смен; смена посреди первой загрузки), `mainwindow_smoke` (`scenarioKeyedSchema`: JSON Lines на открытой вкладке, регексная и обратно, «Apply Schema to All Tabs» с обеими, раздел Keys в Entry Details).

**Решения сверх документа:**

- **Перечитывание решает вкладка, а не контроллер.** Схему ставят несколько путей (док, «Apply Schema to All Tabs», сессия, `Ctrl+Shift+T`, память файла — все через `FieldSchemaController::applyToView` → `setFieldSettings`, тесты — напрямую); правило в одном месте у владельца файлов. Контроллер не менялся.
- **Регексная → регексная файл не перечитывает** (как требует таблица PR): границы записей регексной схемы по-прежнему остаются с загрузки — так же и «Filter blocks» у регексной схемы (известное с F-12: дозапись после смены решает «первичная ли» по новому состоянию). Колонки ключевой схемы (`extraColumns`) тоже не перечитывают — момент, уровень и границу они не меняют.
- **Переизвлечение полей контроллером оставлено** и на резидентной вкладке, которая перечитывается: пока идёт разбор, старые записи показывают и фильтруют колонки новой схемы без рассогласования. Работа двойная — задача S-21.
- **Индексная вкладка на время переиндексации пустеет** (как при Q-19), а не держит старые строки до замены: индекс файла один, single-writer; подменить его под одним reset — отдельная работа без пользы для позиции, которую и так возвращает локатор.
- **Ключи строк при перечитывании меняются** (моменты, id записей), поэтому резидентный путь здесь, в отличие от смены кодировки, сбрасывает строки файла для закладок, истории и локатора (`reencodeRekey`); смена кодировки ключей не меняет и идёт прежним путём.
- **Восстановленная позиция, которая ещё ждёт строку** (`applyState`), при смене схемы ищется заново после сброса строк: ключ, найденный в старых строках, после перечитывания ничего бы не значил.
- **Позиция снимается до смены схемы** (`captureRereadPosition` в начале сеттеров): постановка новой схемы в модель успевает сдвинуть вид на строку, и место, снятое после, было бы уже сдвинутым. Тест смены схемы — на ASCII-фикстуре: на Windows кириллица рисуется запасным шрифтом другой высоты, и смена показанного текста сдвигает строку и без перечитывания (S-22).
- **Сбой перечитывания** (файл не открылся): резидентный путь повторяет перечитывание по концу следующего прохода по файлу (`schemaRereadPending`), индексный — следующая загрузка и так с нуля новой схемой. Схема, сменённая ещё раз посреди перечитывания, — позицию ищет последний проход. Резидентное перечитывание шлёт `fileParsingFinished`, как индексное: окно обновляет поля Time Filter и статистику по новым моментам.
- **Keys — отдельный раздел со всеми ключами**, включая те, что уже стали колонками: «все ключи строки» без правил, какой ключ какой колонке отдан (у роли несколько кандидатов). Ключи показываются, только пока схема действует (извлечение включено) — как колонки.

### PR 4. Редактор, встроенные схемы, автоопределение — 26 ноября 2026

`PatternHeuristics::detectLineFormat` (`Blocks` / `Json` / `Logfmt`) — единственное место правила «как выглядит строка JSON / logfmt»; `suggestKeyedSchema(sampleLines)` — ключевая схема по образцам, `keyedSampleKeys` — ключи образцов для колонок; `suggestSchema` на строке JSON / logfmt сам отдаёт ключевую схему (F-6 возьмёт то же). Встроенные `resources/patterns/json-lines.json` и `logfmt.json` (ключи по умолчанию, без колонок сверх ролей, запасной блок `Message`), в `resources.qrc`. Временный режим PR 1 «карточки ключевой схемы только для чтения» снят. Тесты: `pattern_smoke` (формат строки, предложение схемы), `builtin_schemas` (обе схемы на образцах pino / CLEF / structlog / ECS / logrus / slog / Loki — раскодированные поля, моменты на обоих бэкендах против заданных, доезд к пользователю прежнего выпуска, отказ при своём файле или имени), `schema_store` (`testKeyedEditor`: ключевой режим редактора целиком, Blocks → JSON → Blocks без потерь, Apply / Revert, Auto-detect, «Add keys from sample», живой предпросмотр). `CHANGELOG.md`, обе справки, `README.md`.

**Решения сверх документа:**

- **Правило формата строки не требует ключа роли**: `{` в позиции 0 и полная пара — JSON; logfmt — первый токен пара и пар не меньше двух (одна пара в начале — это и обычный текст «user=bob logged in»). «Распознана ли строка схемой» по-прежнему решает `KeyedLine::Lookup::scan` с ключами ролей; формат нужен, чтобы предложить схему и до того, как пользователь задал ключи.
- **Предложение по образцам**: формат — у большинства (больше половины) непустых строк, иначе регексное автоопределение по первой строке; колонки — ключи, встреченные больше чем в половине строк этого формата, по порядку первой встречи; ключ, совпавший с ключом роли без учёта регистра (`Timestamp`, `LogLevel`, `Message` у .NET), добавляется к ключам этой роли — колонка с именем роли была бы повтором (схема невалидна). Колонки не ограничены числом.
- **Auto-detect с ключевым предложением не трогает цепочку блоков** (меняет только формат и карточку): вернуться к прежним блокам можно форматом Blocks. Регексное предложение, пресет и Grok, как и раньше, заменяют схему целиком и переключают формат на Blocks, а поля ключевой карточки при этом остаются как были (`setKeyedEditor(…, keepFields)`); загрузка регексной схемы ставит в карточку умолчания.
- **Списки ключей и колонок — строкой через запятую**: проще списка с кнопками и проверяется тем же Apply / Revert; ключ с запятой в имени редактором не задать (только правкой файла) — не встречался.
- **«Add keys from sample»** добавляет ВСЕ ключи верхнего уровня строк предпросмотра в формате схемы, которых нет среди ключей ролей и колонок и чьё имя не совпало бы с колонкой без учёта регистра; ничего нового — сообщение в строке статуса предпросмотра.
- **Описание встроенной JSON Lines не обещает «остальные ключи в Entry Details»** — это PR 3; справка и `CHANGELOG.md` говорят, что ключи действуют при чтении файла: схему выбирать до открытия (смена схемы на открытой вкладке до PR 3 меняет только колонки).
- **`builtin_schemas` сравнивает поля через `LogEntryFields::value`** (раскодированное значение), а не `get`: у регексных схем это то же самое, у ключевых — то, что видит пользователь. Без извлечения полей ключевые схемы границы записей не задают — для них проверка «без схемы» пропускается.
- **`theme_mode` не менялся**: карточка — `CardFrame` (своя реакция на смену палитры), цвета легенды — те же полупрозрачные акценты, что у цепочки; редактор схем в сравнении картинок не участвует и раньше.
- **Находки ревью (исправлены):** Auto-detect, когда строки JSON в меньшинстве, строит цепочку по первой обычной строке (иначе `suggestSchema` на строке JSON предложил бы ключевую вопреки правилу большинства); ключ с запятой или пробелами по краям, загруженный из файла, переживает Apply нетронутого поля (поле помнит загруженный список), а «Add keys from sample» таких ключей не предлагает; вложенный объект под первым сегментом пути ключа роли (`log` у `log.level`) колонкой не предлагается; ключ короче трёх символов в ключи роли без учёта регистра не повышается (`T` — не `t`); ключевая схема без единого ключа роли невалидна (`validateDefinition`: «Set at least one time, level or message key») — она не распознала бы ни одной строки.
