# R-1. Устойчивый идентификатор записи

Статус: принят 17 ноября 2026, действуют рекомендованные варианты; PR 1 и PR 2 сделаны 18 ноября 2026 (см. «Сделано») · Объём: L, три PR · Зона: `logstore` (оба бэкенда), `logmodel`, новые `recordid` и `recordlocator` в `dendrolog_core`

На идентификатор опираются закладки (R-2), память файла (R-4), сессии (R-5), отметки на скроллбаре (R-6) и история переходов (R-7). Что и где хранится на диске, описано в `docs/design/R-5.md`.

## Задача и границы

Входит:

- идентификатор строки лога, который можно записать на диск и найти заново после перезапуска, дозаписи, ротации и смены бэкенда вкладки;
- явный отказ вместо чужой строки, когда файл переписан;
- ключ строки для работы в памяти и поиск по нему за O(log N) на обоих бэкендах;
- механизм, который по мере загрузки файла превращает сохранённые идентификаторы в ключи.

Не входит:

- интерфейс, закладки и формат файлов на диске (R-2, R-4, R-5);
- автоматический поиск переименованного при ротации файла;
- перевод якоря выделения `LogListView` на новый ключ (см. «Отвергнутые варианты»).

## Как устроено сейчас

- Идентичность записи в памяти — пара «id логической записи + указатель на `LogFile`» (`src/logmodel.h:57-63`, `src/LogListView.h:395-407`). Указатель не переживает перезапуск.
- Id логической записи зависит от схемы и флага извлечения на момент загрузки: строка первична, если совпала со схемой (`src/logparser.cpp:123-128`, `src/logindexer.cpp:175-184`). Тот же файл с другой схемой получает другие id и другие границы записей.
- Номер физической строки есть на обоих бэкендах: `LogEntry::originalLineNumber()` (`src/logentry.h:36-37`) и `line + 1` при материализации (`src/indexedlogstore.cpp:586`). Равенство номеров между бэкендами напрямую не проверяется: `logstore_equivalence` сверяет построчно текст, время, уровень, id записи и файл (`tests/logstore_equivalence/main.cpp:246-260`). Проверку добавляет PR 1.
- Байтовое смещение строки есть только в индексе (`src/lineindex.h:70-72`). Резидентный парсер читает через `QTextStream` и считает байты приближённо (`src/logparser.cpp:78`, `:87`, `:114`). До PR 1 он открывал файл в режиме `QIODevice::Text`; см. «Сделано».
- Поиск записи: индексный бэкенд — двоичный (`src/indexedlogstore.cpp:755-787`), резидентный — линейный проход по видимым или по всем записям (`src/residentlogstore.cpp:385-423`).
- Дозапись от переписывания отличает `FileChangeDetector`: размер и отпечаток 4 КБ перед концом прочитанного (`src/filechangedetector.h:28-32`, `:44`). Отпечаток — `qHash`, на диск не пишется (`src/filechangedetector.cpp:29-30`).
- Вкладка живёт с одним `LogFilePtr` на файл при дозаписи, полной перезагрузке и смене бэкенда (`src/logviewwidget.cpp:134-146`, `:203-231`, `:466-478`).
- Спул stdin — временный файл с pid в имени, удаляется вместе со спулером (`src/stdinspooler.cpp:32-33`, `:37-39`).

## Решение

### Три понятия

| Понятие | Где живёт | Состав | Зачем |
| --- | --- | --- | --- |
| `SourceIdentity` | диск | путь, размер на момент сохранения, отпечаток начала файла (до 4 КБ) и отпечаток 4 КБ перед сохранённым концом | Ответить, тот ли это файл и цел ли его прочитанный префикс |
| `RecordId` | диск | номер физической строки (с 1) и отпечаток её текста | Найти строку в проверенном источнике и убедиться, что это она |
| `RecordKey` | память | указатель на `LogFile`, номер строки, id логической записи, метка времени в мс | Найти строку в загруженном документе за O(log N) |

### Почему номер строки

Номер физической строки — единственная позиция, которая есть на обоих бэкендах и не зависит от схемы. Вкладка меняет бэкенд на лету, поэтому идентификатор обязан быть общим. Закладка привязана к строке, а не к записи: границы записей после перезагрузки с другой схемой могут сдвинуться, строка остаётся на месте.

### Идентичность источника

Проверка выполняется один раз при подключении файла, до первого батча: два чтения по 4 КБ.

| Состояние | Условие | Что с идентификаторами файла |
| --- | --- | --- |
| Valid | Файл есть, размер не меньше сохранённого, оба отпечатка совпали | Разрешаются по мере загрузки строк |
| Changed | Размер меньше сохранённого или не совпал хотя бы один отпечаток | Все отклоняются с причиной `SourceChanged`; ни одна строка не ищется |
| Missing | Файла по пути нет | Отклоняются с причиной `SourceMissing` |
| Ephemeral | Спул stdin | Не сохраняются; ключи в памяти работают до конца процесса |

Это та же гарантия, на которую уже опирается живое дочитывание: совпавшая граница означает, что прочитанный префикс цел. Отпечаток текста строки — вторая линия защиты: от правки в середине файла и от будущих изменений в разбиении на строки. Строка показывается только после того, как совпал и он.

### Отпечатки

SHA-1 из `QCryptographicHash`, первые 8 байт, в шестнадцатеричном виде. Для областей файла — по сырым байтам, для строки — по её ASCII-скелету (PR 2, см. «Сделано»: отпечаток по UTF-8 декодированного текста зависел бы от кодировки файла). Имя алгоритма записывается в файл рядом с версией формата.

### API хранилища

```cpp
// src/recordid.h
struct RecordKey {
    const LogFile* file = nullptr;
    qint64 line = 0;            // с 1, как LogEntry::originalLineNumber()
    int    logicalEntryId = -1;
    qint64 timestampMs = -1;
    bool isValid() const { return file && line > 0; }
};

// LogStore, с прокси в LogModel
virtual RecordKey keyAt(int visibleRow) const = 0;
virtual int rowForKey(const RecordKey& key) const = 0;         // -1: строка не видна
virtual int nearestRowForKey(const RecordKey& key) const = 0;  // следующая видимая, иначе предыдущая
```

Id записи и метка времени в ключе нужны резидентному бэкенду: вместе с файлом и строкой это полный ключ сортировки `LogEntry::operator<` (`src/logentry.h:78-112`), и строка находится `lower_bound` по компаратору «запись против ключа». Индексному достаточно файла и строки: `makeRef` плюс `lower_bound` по `rowLess`, как в `rowForEntry`.

| Операция | Резидентный | Индексный |
| --- | --- | --- |
| `keyAt` | O(1) | O(1), два чтения индекса |
| `rowForKey`, `nearestRowForKey` | O(log N) | O(1) в тождественном режиме, иначе O(log N) |
| Память на строку | 0 | 0 |

`rowForEntry` и `nearestVisibleRow` остаются как есть: на них стоит якорь выделения.

### RecordLocator

Класс ядра без виджетов, по одному на вкладку. Принимает сохранённые `RecordId`, отдаёт `RecordKey` сигналом `resolved(token, key)` либо отказ `refused(token, reason)` с причиной `SourceChanged`, `SourceMissing`, `LineAbsent` или `TextMismatch`.

Питается от тех же точек, что уже принимают батчи: `handleEntriesParsed` и `handleIncrementalEntriesParsed` отдают батч в порядке файла, `handleIndexBatchReady` — диапазон строк (`src/logviewwidget.cpp:357-382`, `:594-609`, `:270-284`). Ожидающие идентификаторы каждого файла лежат отсортированными по строке, поэтому батч обрабатывается за O(log K + число найденных), где K — число ожидающих идентификаторов. Сам батч не просматривается.

Проверка текста: на резидентном пути сразу, текст в батче. На индексном — фоновым заданием по снапшоту индекса со своим файловым дескриптором, K позиционных чтений; результат применяется на GUI-потоке и отбрасывается, если поколение источника устарело.

Обратное направление — `idFor(key, text)` — вызывается при создании закладки, когда строка на экране и её текст уже в кэше.

### Поведение при событиях

| Событие | Ключи в памяти | Сохранённые идентификаторы |
| --- | --- | --- |
| Дозапись хвоста | Не меняются: id записей и номера строк продолжаются | Действительны |
| Недописанная последняя строка перечитана | Ключ этой строки разрешается заново из батча | Отпечаток текста у недописанной строки пустой; фиксируется, когда строка завершена |
| Файл переписан, `startFullReload` | Все ключи файла возвращаются в ожидание | Источник проверяется заново: Changed → отказ |
| Смена бэкенда вкладки | Как полная перезагрузка | Находятся снова: источник тот же |
| Смена схемы без перезагрузки | Не меняются | Действительны |
| Ротация с переименованием | — | По старому пути Changed; перепривязка к переименованному файлу проходит проверку источника |
| Слитая вкладка | Ключ содержит файл | Хранятся по источникам |

### Стоимость на 200 млн строк

Памяти на строку нет. На батч индексатора — двоичный поиск по ожидающим идентификаторам. Проверка источника — два чтения по 4 КБ. Проверка K идентификаторов — K чтений в воркере. Инвариант 3 сохраняется.

## Отвергнутые варианты

| Вариант | Почему нет |
| --- | --- |
| Байтовое смещение строки | У резидентного пути смещений нет; пришлось бы переписать парсер на сырые байты |
| Id логической записи | Зависит от схемы и флага извлечения на момент загрузки |
| Только текст и время строки, без позиции | Повторяющиеся строки неразличимы; поиск — полный проход по файлу |
| Идентичность файла по inode или file index | Не переживает копирование и перенос на другую машину; редактор, сохраняющий заменой, меняет её при том же содержимом |
| `qHash` для отпечатков | Не обязан совпадать между запусками и версиями Qt |
| Плотная таблица «строка → запись» у резидентного бэкенда | Память на строку ради редкой операции |
| Перевести якорь выделения `LogListView` на `RecordKey` | Отдельная задача: трогает инвариант 10 и `logview_state`. Убрала бы линейные проходы резидентного `rowForEntry`; записать в план после 0.6 |

## Сделано

### PR 1 — 18 ноября 2026

`src/recordid.h` (`RecordKey`), `LogStore::keyAt` / `rowForKey` / `nearestRowForKey` на обоих бэкендах, прокси в `LogModel`. Проверки — `tests/logstore_equivalence` (ключи во всех конфигурациях фильтров против перебора и между бэкендами, номера строк против разбиения байтов файла) и `tests/logview_lifecycle` (номера строк на живой вкладке обоих бэкендов).

**Номера строк расходились — исправлено.** Предположение «на обычных файлах номера совпадают» не подтвердилось на краях:

- резидентный парсер отбрасывал пустую ПОСЛЕДНЮЮ строку (`"…\n\n"`, `"…\r\n\r\n"`, файл из одного `"\n"`) — пропуск «фантомной» строки, которой `QTextStream::readLine` за завершающим `'\n'` не отдаёт. Потерянная строка сдвигала номера всех строк, дописанных за ней на дочитывании, на единицу на каждую потерю;
- режим `QIODevice::Text` выбрасывал из текста каждый `'\r'`, а не только перед `'\n'`: строка с одиночным `'\r'` расходилась по тексту с индексным путём (а значит, расходился бы отпечаток текста из PR 2).

Исправление в `LogParser::parseFrom`: файл открывается без `QIODevice::Text` (`"\r\n"` снимает `readLine`), пустая последняя строка — строка. Исключение одно — файл из одного BOM: `readLine` съедает метку и отдаёт пустую строку, которой в файле нет (иначе UTF-16-лог, созданный писателем с одной меткой, получил бы фантомную строку 1 и сдвиг всех дописанных). Правило нумерации теперь одно и записано эталоном в тестах (`testdocs::expectedPhysicalLines`): строка — то, что кончается `'\n'` (`'\r'` перед ним снимается), плюс хвост без `'\n'`; за завершающим `'\n'` строки нет. Пользователь видит это как пустую последнюю строку в резидентной вкладке — так её уже показывал индексный бэкенд.

**Отклонения от дизайна и решения:**

| Что | В дизайне | Сделано | Почему |
| --- | --- | --- | --- |
| Файл в ключе | `const LogFile*` | `LogFilePtr` | Резидентный компаратор читает путь файла; сырой указатель закрытого файла висел бы, а новый `LogFile` мог бы занять его адрес и «найти» чужую строку. Сравнение — по указателю, как у `LogModel::EntryKey` |
| «Метки нет» | `timestampMs = -1` | `RecordKey::kNoTimestamp` (минимум `qint64`) | Метка до 1970 года — законный отрицательный момент у резидентного бэкенда. Индексный по-прежнему хранит «нет метки» как `-1` и переводит его в `kNoTimestamp` |
| Совпадение ключа | Индексному достаточно файла и строки | Оба бэкенда требуют совпадения id записи и метки | Резидентный ищет по полному ключу и иначе не нашёл бы строку; чтобы ответ не зависел от бэкенда, индексный тоже отвечает «нет» на ключ, чья строка теперь в другой записи (перезагрузка, другая схема). Ключ в памяти после этого заново даёт `RecordLocator` (PR 3) |
| Где лежит ещё не показанная строка | — | Ключ действителен, только когда строка уже показана модели | Индекс растёт в воркере раньше модели; так `nearestRowForKey` не отличается от резидентного, у которого строки до слияния батча нет |

**Соседние методы.** «Ближайшая видимая» теперь одна семантика: видна — она сама; скрыта — следующая видимая за её МЕСТОМ в порядке вкладки, за концом — последняя; нет в данных — `-1`. У индексного бэкенда место строки считает одна функция `visiblePlace` (тождество — O(1), иначе `lower_bound` по `rowLess`): на ней `rowForKey`, `nearestRowForKey`, `nearestVisibleRowForLine` (это `nearestRowForKey` для строки, номер которой прижат к файлу) и место скрытой записи в `placeAmongVisible`. `rowForEntry` и `nearestVisibleRow` не тронуты. У резидентного `placeAmongVisible` и `nearestVisibleRowForLine` остаются линейными: по id записи или номеру строки без метки ключ сортировки не построить, а плотную таблицу «строка → запись» дизайн отверг. Перевести их на ключ — естественная часть S-7 (якорь выделения на ключ). `findOccurrence` / `findRowWithLevel` (`LogScanSnapshot`) работают со стартовой строкой, а не с ключом, и с новым API не пересекаются.

### PR 2 — 18 ноября 2026

`src/recordid.{h,cpp}` (ядро): `RecordFingerprint` (отпечатки), `RecordId`, `SourceIdentity` с проверкой и JSON. К вкладке не подключены — это PR 3 (`RecordLocator`). Проверки — новый `tests/record_identity`; выравнивание хвоста с `'\r'` — случаи в `tests/logstore_equivalence` (номера строк) и `tests/logview_lifecycle` (живая вкладка, дозапись `'\n'` за `'\r'`).

**Отпечаток строки и кодировки (решение 1).** Дизайн считал отпечаток по UTF-8 декодированного текста. После F-1 текст строки зависит от кодировки файла: автоматика решает её по свидетельству и может пересмотреть, пользователь выбирает руками, на другой машине другая запасная кодировка. Отпечаток той же строки разошёлся бы. Сделано: отпечаток по **ASCII-скелету** — символы < U+0080 как есть, каждая серия символов ≥ U+0080 — один байт-заполнитель `0x80`, SHA-1 первые 8 байт (алгоритм `sha1-64-ascii`). Байтовый вариант `ofLineBytes` сворачивает так же серии байтов ≥ 0x80 и даёт то же значение без декодирования (пригодится фоновой проверке PR 3 на индексном пути). Это верно, потому что все кодировки, которые читает `TextDecoder`, ASCII-совместимы и тотальны: ASCII-байт — тот же символ, серия байтов ≥ 0x80 — серия символов ≥ U+0080 (битый UTF-8 — U+FFFD без поглощения следующего ASCII-байта, неопределённый байт однобайтной — C1). Тест сверяет это на всех байтах 0x01–0xFF (кроме `'\n'`) в пяти кодировках и на битых последовательностях (оборванная, overlong, суррогат, за U+10FFFF, одиночное продолжение). UTF-16/32 — только по декодированному тексту: других вариантов там нет; отпечаток UTF-16-файла равен отпечатку того же текста в UTF-8.

Отвергнуто: сырые байты строки на обоих бэкендах. Резидентный путь сырых байтов не хранит (они нужны были бы на каждую строку в горячем пути разбора, а пересчёт по требованию требует смещений, которых у него нет), а обратное кодирование текста не восстанавливает битый UTF-8 (U+FFFD) и само зависит от кодировки. Цена скелета: строки, отличающиеся только не-ASCII текстом при той же раскладке серий («Ошибка 1» и «Привет 1»), неразличимы — закреплено в тесте. Первая линия защиты — номер строки и идентичность источника, отпечаток — вторая; в логах ASCII-каркас (метка, уровень, поток, числа) почти всегда различает строки.

**Хвост с одиночным `'\r'` (решение 2).** Резидентный путь показывал оборванную последнюю строку без конечного `'\r'` (`readLine`), индексный — с ним. Сведено к резидентному виду: это же тот вид, который строка получит, когда допишут `'\n'` (`"\r\n"`), и он совпадает с эталоном нумерации `expectedPhysicalLines`. В индексе — код конца строки `LineIndex::kEolProvisionalCr`: строка предварительная, `'\r'` не текст, но байт файла — смещения и `endOffset` точны, якорь дочитывания не сдвигается. Дописанный `'\n'` делает из неё обычную `"\r\n"`-строку, дописанный текст — строку с `'\r'` внутри (как у резидентного пути). Отпечаток недописанной строки по-прежнему не хранится (`RecordId::hasText == false`).

**Края идентичности источника (решение 3).**

| Случай | Что происходит |
| --- | --- |
| Файл короче 4 КБ | Начало и конец — одна область `[0, size)`; при проверке начало читается по СОХРАНЁННОМУ размеру, поэтому доросший файл — Valid |
| Пустой файл | `size = 0`, отпечатки пустых областей: Valid, пока файл есть, и после дозаписи (строк, которые надо найти, нет) |
| Файл из одного BOM | Обычный файл из 3 байтов; дописанный — Valid, файл без BOM или с BOM UTF-16 вместо него — Changed |
| Вырос между снятием и проверкой | Valid (дозапись) |
| Усечён | Changed, даже на один байт |
| Переписан той же длиной | Changed, если изменились первые или последние 4 КБ сохранённого префикса; правка только в середине — Valid, её ловит отпечаток строки (`TextMismatch` в PR 3). Закреплено тестом |
| Переписан длиннее другим содержимым | Changed |
| Удалён, на месте файла каталог, файл не открывается | Missing |
| Переименован | По старому пути Missing (или Changed, если создан новый файл). Сравнение без пути: `checkAt(другой путь)` — проверка содержимого по новому месту, `sameContent` — две снятые идентичности. Это задел вторичного поиска памяти файла (R-4) |
| Спул stdin | `capture` возвращает Ephemeral без чтения (`StdinSpooler::isSpoolFilePath`: имя и временный каталог), `toJson` — пустой объект |
| Снятие по префиксу | `capture(path, size)` — идентичность первых `size` байтов (конец прочитанного); правка за ним не задевает. Размер больше файла — отказ |

**Отклонения от дизайна и решения:**

| Что | В дизайне | Сделано | Почему |
| --- | --- | --- | --- |
| Отпечаток строки | UTF-8 декодированного текста | ASCII-скелет, `sha1-64-ascii` | Решение 1 |
| Где версия и алгоритм | В заголовке файла (R-5) | В каждом объекте: `{"version":1,"hash":"sha1-64",…}` у источника, `{"version":1,"hash":"sha1-64-ascii","line":…,"text":…}` у строки | Формат файлов — R-4/R-5; объекты самодостаточны и проверяются без заголовка. Цена — ~35 байт на закладку. R-4 может вынести ключи в заголовок, сохранив проверку |
| Отказ при чтении | — | `fromJson` возвращает `nullopt` и причину: версия не 1, другой алгоритм, нет или не тот тип у поля, не 16 hex-цифр, относительный путь, нет ни `"text"`, ни `"partial": true`, номер строки < 1, отрицательный или дробный размер, число вне 2⁵³. Лишние ключи не мешают (R-5: читатель игнорирует неизвестные ключи) | Чужой идентификатор хуже отсутствующего |
| Отпечаток в памяти | Строка hex | `quint64`, hex только в JSON | Сравнение без аллокаций |
| Недописанная строка | «Отпечаток пустой» | `RecordId::hasText = false`, в JSON вместо `"text"` явная метка `"partial": true`; `matchesText` отвечает «да» (проверены номер и источник) | Пропавший `"text"` без метки — битые данные и отказ: иначе испорченная закладка совпала бы с любой строкой |
| Путь | Что открыл пользователь | `QFileInfo::absoluteFilePath()` того, что передали; регистр не нормализуется, `operator==` сравнивает его без учёта регистра на Windows; `sameContent` пути не смотрит и на неснятых идентичностях ложен | Нормализация имени файла памяти — R-4 |
| Файл не открывается | — | Missing | Проверить нельзя; «Changed» обещал бы, что содержимое другое |

**Цена.** Отпечаток строки не считается в горячем пути: ни парсер, ни индексатор его не зовут. `lineindex_smoke --bench` и `--bench-resident` на 300 МБ (3,5 млн строк) — в пределах шума до и после (1,33–1,53 с против 1,41–1,45 с; 3,52–3,55 с против 3,52–3,56 с). Снятие и проверка источника — два чтения по ≤ 4 КБ.

**Что нужно знать PR 3.**

- Отпечаток строки — `RecordFingerprint::ofLineText(messageAt)` на GUI-потоке либо `ofLineBytes` по сырым байтам из `SequentialLineReader` в воркере: значения равны для UTF-8 и однобайтных файлов, декодер воркеру не нужен.
- Последняя строка без `'\n'` (`lastLineProvisional`, `LogParser::tailState`) — `RecordId::forLine(…, complete = false)`.
- Идентичность снимать по концу прочитанного (`capture(path, consumedBytes)`), а не по текущему размеру: недочитанный хвост в неё не попадает.

## Проверки

- Сохранить идентификаторы, загрузить тот же файл заново обоими путями — найдены те же строки.
- Дописать хвост, в том числе продолжение многострочной записи и строку по частям, — идентификаторы действительны.
- Переписать файл другим содержимым той же и большей длины — источник Changed, ни одного `resolved`.
- Изменить одну строку в середине, не трогая начало и конец, — отказ `TextMismatch` только для неё.
- Переименовать файл и создать новый с тем же именем — по старому пути Changed, по новому пути старого содержимого Valid.
- Слитая вкладка из двух файлов, один из которых переписан, — идентификаторы второго не затронуты.
- Загрузить с другой схемой — идентификаторы указывают на те же физические строки.
- Счётчик обращений: число просмотренных ожидающих идентификаторов на батч не растёт с размером батча.

## Риски и затронутые инварианты CLAUDE.md

- Инвариант 3: обработка батча не должна зависеть от его размера. Закреплено проверкой счётчика.
- Инвариант 2: `RecordLocator` сигналит только на GUI-потоке; воркер проверки получает снапшот индекса.
- Инвариант 5: отпечатки областей файла — по сырым байтам, файл открывается без `QIODevice::Text`.
- Инвариант 11: поиск по ключу на индексном бэкенде идёт через `rowLess`, не через `lessRef`.
- ~~Номера строк двух бэкендов могут разойтись на краях~~ — закрыто PR 1: расходились, исправлено (см. «Сделано»).
- Компаратор «запись против ключа» обязан зеркалить `LogEntry::operator<`. Расхождение проявится как ненайденная строка; ловится `logstore_equivalence`.
- Метка без зоны читается как локальное время. Ключ в памяти живёт в пределах процесса, на диск метка не пишется, поэтому смена часового пояса машины идентификаторы не ломает.
- Предположение: после `truncateFrom` переиндексированная последняя строка получает прежний id записи. Если нет, срабатывает повторное разрешение из батча.
- Связь с F-2 (`docs/design/F-2.md`): путь в `SourceIdentity` — то, что открыл пользователь. Когда появится `LogSource`, идентичность берёт его (архив и имя внутри), а не путь временной копии; отпечатки считаются по распакованному содержимому.
- ~~Связь с F-1: отпечаток строки зависит от кодировки~~ — закрыто PR 2: отпечаток по ASCII-скелету от кодировки не зависит, хранить кодировку рядом с идентификаторами ради проверки не нужно (см. «Сделано → PR 2»).
