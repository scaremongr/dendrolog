# F-12. Запись начинает строка с ведущей меткой

Статус: принят и сделан 18 ноября 2026, для `0.5.0`. Задача `F-12` из `docs/roadmap.md`, найдена при F-10 (`docs/design/F-10.md`).

## Как устроено сейчас

Правило первичной строки — `LineClassifier::isPrimaryLine`, одно у `LogParser` (резидентная вкладка), `LogIndexer` (индексная) и `LogParser::analyzeFileForStats` (сканер каталога, Q-15): строка начинает запись, если её распознала схема **или** у неё есть и метка времени, и слово уровня. Остальное — продолжение текущей записи (до первой записи строка — сама себе запись). Схема участвует только при включённом извлечении полей (Filter blocks), а по умолчанию оно выключено.

Следствие: лог без слов уровня — access nginx/Apache, большая часть syslog, «метка сообщение» — без схемы становится одной записью. У строк нет своего момента: таймлайн пуст, фильтр времени и порядок слитой вкладки не работают, сканер показывает одну запись. Замер: access-лог генератора на 2 млн строк индексировался в **1** логическую запись.

Убрать требование уровня нельзя: после F-10 формы ISO, `yyyy/MM/dd` и access ищутся по всей строке (самая левая), а метки встречаются в теле сообщений — JSON, SQL, XML, тексте исключений. Правило «есть метка — новая запись» разорвало бы такие записи и дало бы кускам чужие моменты.

## Корпус и варианты

Корпус — строки, которые должны (П) или не должны (·) начинать запись без схемы. Варианты: **0** — нынешнее правило; **A** — метка с позиции 0; **B** — метка в первых 40 символах строки без ведущего пробела; **В** — выбранное (ниже). Прогон — сканер классификатора на этих строках (позиция метки и флаг ведущей); тот же корпус закреплён `testRecordBoundariesBackends` в `tests/lineindex_smoke`.

## Решение

Строка первична, если её распознала схема, **или** у неё есть метка и слово уровня (как раньше), **или** метка **ведущая**:

- стоит с позиции 0 — любая форма (syslog и фолбэк-формы только так и находятся);
- стоит с позиции 1 сразу за `[` (`[2026-11-18 10:00:00] …`);
- это форма access-лога (`dd/Mmm/yyyy:HH:mm:ss`) сразу за `[`, и строка не начинается с пробела или табуляции — поле времени Common/Combined Log Format.

Правило построчное, без состояния. Классификатор знает, где нашёл метку, поэтому флаг отдаёт сам: `detectTimestamp[Ms](…, bool* leading)`; `isPrimaryLine(schema, hasTs, leadingTs, hasLevel)`. Индексатор по-прежнему не гоняет регекс схемы на строках, первичных без неё (теперь и на строках с ведущей меткой).

Что меняется для пользователя: access, syslog и «метка сообщение» без схемы делятся на записи и получают момент; строка `2026-… query:` без уровня перед телом SQL теперь своя запись, а не хвост предыдущей. Что сохраняется: стек-трейсы, тело JSON/SQL/XML с меткой в середине или под отступом, текст исключения с датой — продолжения. Строка с меткой где угодно и словом уровня первична, как всегда (так было и до F-12; JSON-строка тела вида `"ts": "…", "level": "ERROR"` по-прежнему начнёт запись — риск прежний, не новый).

## Отвергнутые варианты

- **Метка в начале (A).** Просто, но access-лог — главный адресат задачи — остаётся одной записью.
- **Метка в коротком префиксе без отступа (B).** Порога нет (таблица выше): 40 символов режут тело сообщения и всё равно теряют access с IPv6-клиентом.
- **Режим на файл** («у строк с меткой в этом файле обычно нет уровня»). Нужно состояние разбора: его надо нести через дозапись (`ResumeContext`, якорь индексатора), через порции индексатора и в хвост сканера; решение «режима» меняется по мере чтения, и уже показанные строки пришлось бы перегруппировать. Лог из двух форматов вперемешку один режим не описывает. Построчное правило В даёт тот же результат на корпусе без состояния.
- **Метка за любой `[`** (не только access). `x [2026-…]` — частая форма упоминания времени в тексте сообщения; у access-формы скобка — признак поля CLF, а в теле она встречается разве что внутри кавычек (`"[18/Nov/…]"` — за `"`, не ведущая).

## Проверки

- `lineindex_smoke`: флаг ведущей метки сверяется с регекс-эталоном (`refDetectTimestamp`) на корпусе и 20 000 строк фаззинга; `testRecordBoundariesBackends` — корпус выше на обоих путях загрузки (границы, моменты, 10 записей), и дозапись, начатая телом JSON с меткой, — как свежая индексация.
- `logstore_equivalence`: фикстуры без слов уровня — смешанные формы с телом JSON (один файл) и вместе с access-логом (слияние, оба сценария подключения).
- `dirscanner_smoke`: абсолютные счётчики (лог с баннером — 6 записей; access, IPv6-access, syslog, `[метка]` и тело JSON — 4 записи, From/To) и согласие с вкладкой.
- `builtin_schemas`: без схемы (как при выключенном Filter blocks) у встроенных схем, где у каждой записи есть метка с датой (access, nginx error, оба syslog, Spring Boot, Serilog file, Python logging; Logback, Serilog console и Python basicConfig пропущены — в их образцах есть записи без даты, F-11), границы записей совпадают с границами по схеме, момент есть у каждой записи — на обоих бэкендах.
- На прежнем правиле новые проверки падают: `builtin_schemas` — 31, `lineindex_smoke` — 21, `dirscanner_smoke` — 4. Ни одно существующее ожидание не поменялось; комментарий «продолжение: уровня нет» в фикстуре `dirscanner_smoke` (там сверялось только согласие сканера и вкладки) исправлен на «запись».

Цена (2 млн строк, Linux, 6 прогонов, разброс облачной машины ±15 %): стадия 5 `--bench-stages` (декод + `detectTimestampMs` с флагом) — лог генератора 0,66–0,72 с до и 0,57–0,83 с после; access 0,15–0,23 → 0,18–0,21 с. Полная индексация `--bench`: генератор 0,9–1,1 → 0,8–1,2 с, access 0,6–0,7 → 0,6–0,7 с (записей 1 → 2 000 000). Различие в пределах шума: флаг — одно сравнение у уже найденной метки.

## Риски

- Тело сообщения, строки которого начинаются меткой без отступа (вставленный в сообщение чужой лог, CSV-дамп с датой в первой колонке), разобьётся на записи. Это и есть строки лога по виду; со схемой поведение то же.
- Найденное попутно: `[alert]` nginx error и подобные строки без слова из словаря прежде были продолжениями — теперь отдельные записи (уровень по-прежнему не задан, `ALERT` в словарь не входит).
