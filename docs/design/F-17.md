# F-17. Log Fields заново: поля отдельно от чтения, шаблон строки, подбор схемы, нейро-подсказчик

Статус: вторая редакция, 26 ноября 2026. Первая редакция (коммит `beb9c9c`) сохраняла движок и формат схем; в тот же день автор снял это ограничение: «движок можно полностью переделать, старое поведение не оставлять», при условии, что архитектура продумана («это уже не первый рефакторинг»), особое внимание — производительности, а разбор полей «максимально отвязан от остальной обработки»: идёт параллельно и независимо, view показывает результат по готовности — так, чтобы даже разбор каждой строки нейросетью не мешал показу и прокрутке. Код читался на `8418ebe`: F-4 готов, F-5 — PR 1 и 2 готовы, PR 3 идёт; шаг 1 этого документа (мера `SchemaFit`) запущен планировщиком по первой редакции и остаётся в силе. Задача `F-6` входит сюда шагом 8.

## Задача и границы

Жалобы автора: интерфейс Log Fields громоздкий и непонятный; правила разбиения сложные; нужен режим, который сам разбивает строки по нескольким десяткам образцов; разбор не должен нагружать просмотр больших логов.

Цели:

1. Открыл лог знакомого формата — поля уже есть; открыл JSON Lines — время, уровень и ключи уже есть. Ничего не нажимая.
2. Незнакомый формат — одна кнопка даёт варианты разбиения с долей разобранных строк файла; при желании вариант предлагает нейросеть.
3. Правило разбиения — одна строка, похожая на строку лога; правка — выделением на настоящих строках.
4. Выбор и смена схемы ничего не стоят: файл не перечитывается, вкладка не замирает ни на каком размере лога.

Входит: новая архитектура полей (три слоя ниже), новый движок и формат схемы, перевод каталога и сохранённых состояний, новый док и редактор, подбор схемы, нейро-подсказчик.

Не входит: табличный режим строк во view (U-18), несколько схем на один файл, анализ содержимого лога нейросетью, сам режим «каждую строку разбирает нейросеть» — но архитектура обязана его допускать (раздел 3 и шаг 6 проверяют это подставным медленным извлекателем).

## Как устроено сейчас и что именно мешает

Схема полей сегодня вшита в три места, и каждое делает её дорогой и запутанной:

| Где | Что делает схема | Чем это плохо |
| --- | --- | --- |
| **Загрузка** (`LogParser`, `LogIndexer`, `LineClassifier::classifyLine`) | Решает границу записи (`isPrimaryLine(schemaMatched, …)`); у ключевой схемы — ещё время и уровень каждой строки | Смена схемы = перечитывание файла (F-4, PR 3). Регекс схемы гоняется на загрузке: резидентный парсер — на каждой строке, индексатор — на каждой строке без ведущей метки («минуты на десятках миллионов строк», комментарий в `logindexer.cpp`). Схему нельзя подобрать после открытия, не заплатив вторым проходом |
| **Хранение** (`LogEntry::m_fields`) | Резидентная вкладка хранит спаны полей в каждой записи с момента разбора | Память и аллокация на строку; смена схемы — `FieldReextraction` (фоновое переизвлечение) и инвариант 4: остановить фильтры всех читателей, поставить поля на GUI-потоке, перефильтровать. Индексная вкладка полей не хранит и извлекает по требованию — два разных устройства одной вещи |
| **Интерфейс** | Галочка «Filter blocks» (`FieldSettings::extraction`) включает и извлечение, и показ «только выбранные блоки»; редактор — цепочка из 11 типов блоков с обёртками и разделителями | Выбранная схема ничего не делает, пока не включена галочка. Правило разбиения нельзя прочитать глазами: оно размазано по карточкам, а движок под ним — каскад «полный регекс → префиксы → re-sync» (`logpattern.cpp`, 1193 строки) |

Ещё: «Suggest schema» смотрит на одну строку; меры «сколько строк файла схема разбирает» нет; JSON Lines и logfmt требуют выбрать схему и включить галочку, иначе время из `"ts":1700000000` не читается; схемы, пресеты и встроенные схемы — три похожих понятия; редактор модальный.

Что хорошо и остаётся: `LineClassifier` (одна политика времени и уровней), `keyedline` (разбор JSON и logfmt без аллокаций), `FieldLayout` / `FileSchema` (колонки вкладки по имени, схема на файл — F-5), `FieldSchemaController`, спаны `LogEntryFields` (поле — кусок строки, без копии), встроенные схемы по манифесту, оба бэкенда за `LogStore`.

## Архитектура: три слоя

```text
 байты файла
     │
 ┌───▼──────────────────────────────────────────────────────────────┐
 │ 1. ЧТЕНИЕ (LogParser, LogIndexer)                                  │   не знает о схеме полей
 │    строки, кодировка, ФОРМАТ СТРОК (plain / JSON / logfmt),        │   решает порядок, время,
 │    время, уровень, граница записи                                  │   уровень, идентичность строк
 └───┬──────────────────────────────────────────────────────────────┘
     │ строки (резидентно — в памяти, индексно — на диске)
 ┌───▼──────────────────────────────────────────────────────────────┐
 │ 2. ПОЛЯ (FieldSource, FieldExtractor)                              │   чистая функция
 │    поля = extract(текст строки, схема); не хранятся в записях,     │   (текст, схема) → спаны;
 │    считаются там и тогда, где нужны; медленные — в фоне            │   ничего не решает о строках
 └───┬──────────────────────────────────────────────────────────────┘
     │ спаны по требованию / «ещё не готово» + сигнал «готово»
 ┌───▼──────────────────────────────────────────────────────────────┐
 │ 3. ПОТРЕБИТЕЛИ: view, Entry Details, фильтр по полю, Search,       │   показывают строку сразу,
 │    экспорт, редактор, SchemaFit                                    │   поля — когда пришли
 └──────────────────────────────────────────────────────────────────┘
```

Три правила, на которых всё держится (станут инвариантами `CLAUDE.md`):

- **Чтение не знает о схеме полей.** Порядок строк, время, уровень, границы записей и ключ строки (`RecordKey`) от схемы не зависят. Следствие: смена схемы никогда не перечитывает файл, не сбрасывает модель, не трогает закладки и историю.
- **Поля — функция, а не данные.** `LogEntry` после публикации неизменяем; полей в нём нет. Следствие: инвариант 4 в части полей, `FieldReextraction` и «остановить читателей перед сменой схемы» исчезают; оба бэкенда получают поля одним путём.
- **Медленный извлекатель не вызывается на GUI-потоке.** У извлекателя объявлен класс цены; дорогой считает в фоне, view в это время показывает сырую строку и обновляется по сигналу. Следствие: скорость показа и прокрутки не зависит от того, насколько дорог разбор.

### 1. Чтение без схемы: формат строк файла

То, что сегодня приходит из схемы в загрузку, заменяется свойством ФАЙЛА — **форматом строк**, который определяется сам, как кодировка (F-1), и так же хранится на файл.

```cpp
struct LineFormat {                       // src/lineformat.h, ядро
    enum class Kind { Plain, Json, Logfmt };
    Kind kind = Kind::Plain;
    bool levelStartsRecord = false;       // Plain: запись начинает ещё и ведущее слово уровня
    // Json / Logfmt: ключи ролей, единица эпохи, шкала уровней — то, что было KeyedDefinition
    QStringList timeKeys, levelKeys, messageKeys;
    EpochUnit epoch = EpochUnit::Auto;
    LevelScale levels = LevelScale::Auto;
    enum class Origin { Undecided, Auto, User } origin = Origin::Undecided;
};
```

- **Правило одно — `LineFormatDetector::decide(первые строки)`**, его зовут `LogParser` и `LogIndexer` в начале прохода, до первой классифицированной строки (как `EncodingDetector::advance`); решение сообщается сигналом раньше первой порции. Поэтому бэкенды согласны по построению. Большинство непустых строк начала — JSON-объект или logfmt (`detectLineFormat`, уже есть) → `Json` / `Logfmt` с ключами ролей по умолчанию (списки из F-4). Иначе `Plain`.
- **`Plain`, граница записи:** прежнее правило F-12 без `schemaMatched` — «метка и слово уровня ИЛИ ведущая метка». Дополнение `levelStartsRecord`: если в начале файла меньше 10 % строк с меткой, а не меньше половины начинаются со слова уровня (с позиции 0 или за `[`) — запись начинает и такая строка. Это закрывает единственное, для чего сегодня нужна была схема на загрузке (`WARNING:root:…`, `[INFO] …`), и делает это без схемы. Решение — на файл, а не на строку: в логе с метками ведущее `ERROR:` посреди многострочной записи записи не начинает (иначе запись без метки уехала бы в конец вкладки).
- **Мало строк** (растущий лог, stdin): пока непустых строк меньше 20 — `Undecided`, строки классифицируются как `Plain`; на двадцатой — решение, и если оно не `Plain` без дополнения, файл перечитывается один раз (он по определению мал).
- **Дозапись, переход порога, слитая вкладка** несут решённый формат, как `FileEncoding`: у индексной вкладки — в `IndexedLogStore` на файл, у резидентной — во вкладке (`m_fileFormats`).
- **Выбор пользователя** — индикатор в строке статуса рядом с кодировкой («Plain text», «JSON Lines», «logfmt», пункт «Keys…» для своих имён ключей времени, уровня и сообщения). Смена перечитывает файл — тем путём, что уже построен в F-4, PR 3 (резидентный — замена записей под одним reset, индексный — переиндексация, позиция через `RecordLocator`). Это редкое явное действие; обычная смена схемы полей сюда не попадает никогда.
- **Сохранение:** только выбор пользователя — в `TabSource`, памяти файла и сессии (как выбор кодировки).
- **`classifyLine(keyedSchema, …)` → `classifyLine(lineFormat, …)`**; `isPrimaryLine` теряет параметр `schemaMatched`; парсер и индексатор теряют параметр схемы (его добавил F-5, PR 2).
- Сканер каталога зовёт тот же детектор: счётчики уровней JSON-логов в дереве становятся верными.

Что теряется: «запись начинается там, где сработала схема» для экзотических форматов без метки и без уровня в начале строки. Там каждая строка станет своей записью. Задел оставлен: проход принимает правило начала записи значением, и правило «по схеме» можно добавить явным выбором на файл — не делаем, пока нет запроса.

### 2. Извлекатель и шаблон строки

**Интерфейс** (`src/fieldextractor.h`, ядро):

```cpp
class FieldExtractor {                  // неизменяемый; делится между потоками через shared_ptr<const>
public:
    enum class Cost { Inline, Background };  // Inline — можно звать на GUI-потоке; Background — только в воркере
    virtual QStringList fields() const = 0;  // колонки схемы
    virtual Cost cost() const = 0;
    // Спаны по колонкам схемы. upTo >= 0 — дальше этой колонки можно не разбирать.
    virtual bool extract(QStringView line, LogEntryFields* out, int upTo = -1) const = 0;
    // Пачкой; по умолчанию — цикл по extract. Для извлекателей, которым выгодна пачка (сеть).
    virtual void extractBatch(const QVector<QStringView>& lines, QVector<LogEntryFields>* out) const;
    virtual MatchReport explain(QStringView line) const;   // где и почему разбор остановился
};
```

Реализации: `TemplateExtractor` (новый движок, `Inline`; с участком-регексом — `Background`), `KeyedExtractor` (обёртка `keyedline::Lookup`, `Inline`), `LegacyPatternExtractor` (нынешний `LogPattern`, живёт до шага 9). Будущий извлекатель «каждую строку разбирает модель» — ещё одна реализация с `Cost::Background` и своим `extractBatch`; ни чтение, ни view для него менять не придётся.

**Шаблон строки** — новый движок и новый формат схемы. Правило разбиения — одна строка, которая выглядит как строка лога:

```text
{Timestamp:time} [{Thread}] {Level:level} {Logger:word} - {Message}
```

Грамматика:

```text
шаблон   := элемент*
элемент  := литерал | пробел | поле | необязательное
поле     := '{' имя? (':' вид)? '}'
необяз.  := '{?' элемент* '?}'          — участок может отсутствовать; без вложенности
литерал  := любой текст; '{{' и '}}' — сами фигурные скобки
пробел   := пробелы в шаблоне = один или несколько пробелов и табуляций в строке
имя      := имя колонки; пусто или '_' — участок разбирается, но колонкой не становится
вид      := time | level | int | num | hex | uuid | ip | word | quoted | path
          | text | greedy | rest | /регекс/
```

| Вид | Что берёт |
| --- | --- |
| `time` | метку времени — все формы `LineClassifier` (ISO, access, syslog, время без даты, зона) |
| `level` | слово словаря уровней (`kLevelWords`) |
| `int`, `num`, `hex`, `uuid`, `ip`, `path` | токен своей формы |
| `word` | до пробела |
| `quoted` | строку в кавычках, значение — без кавычек (экранирование — бит `FieldSpan`, как у JSON) |
| `text` | до ПЕРВОГО вхождения того, что стоит в шаблоне следом: литерала либо поля `time` / `level` / `ip`; если следом необязательный участок — до первого из двух: его начала или того, что стоит за ним |
| `greedy` | до ПОСЛЕДНЕГО вхождения следующего литерала |
| `rest` | до конца строки |
| `/регекс/` | совпадение регекса с этой позиции; извлекатель становится `Background` |
| не указан | перед литералом или необязательным участком — `text`, перед пробелом — `word`, в конце шаблона — `rest` |

Правила разбора — их пять, и они заменяют каскад:

1. Строка читается слева направо один раз. Литерал обязан стоять на своём месте, поле берёт токен своего вида.
2. Значение поля — без окружающих пробелов (`[     main]` даёт `main`).
3. Необязательный участок пробуется; не сошёлся — пропускается, его поля пусты.
4. Разбор остановился посреди шаблона — поля, сошедшиеся слева, остаются; остаток строки уходит в последнее поле `rest` (мягкая деградация, как сейчас у префиксного каскада). Строка принята, если сошёлся хотя бы один отличительный элемент: `time`, `level`, `ip` или литерал от трёх знаков.
5. Не сошёлся первый элемент — строка не принята, полей нет.

Возвратов нет, кроме одного уровня у необязательного участка; цена — линейная по длине строки. Re-sync («пропустить слабый блок и найти следующий якорь») уходит: его случаи выражаются явным `{? … ?}`, который умеет находить вывод структуры (раздел 6).

Встроенные схемы в новом виде (все десять блочных выражаются, две syslog-схемы — одним шаблоном; проверка — прежние ожидания `tests/builtin_schemas`):

| Схема | Шаблон |
| --- | --- |
| Logback / Log4j | `{Timestamp:time} [{Thread}] {Level:level} {Logger:word} - {Message}` |
| Spring Boot | `{Timestamp:time} {Level:level} {Pid:int} --- [{Thread}] {Logger:word} : {Message}` |
| nginx / Apache access | `{Client:ip} {Ident:word} {User:word} [{Timestamp:time}] "{Request}" {Status:int} {Bytes:word}{? "{Referer}" "{UserAgent}"?}` |
| nginx error | `{Timestamp:time} [{Level:level}] {Pid:int}#{Tid:int}: {Message}` |
| Syslog (RFC 3164 и ISO) | `{Timestamp:time} {Host:word} {Process}{?[{Pid:int}]?}: {Message}` |
| Serilog console | `[{Timestamp:time} {Level:level}] {Message}` |
| Serilog file | `{Timestamp:time} [{Level:level}] {Message}` |
| Python logging | `{Timestamp:time} - {Logger} - {Level:level} - {Message}` |
| Python basicConfig | `{Level:level}:{Logger}:{Message}` |

**Файл схемы, версия 4** (`<configDir>/patterns/*.json`):

```json
{"name": "Spring Boot", "description": "…", "version": 4, "type": "line-template",
 "template": "{Timestamp:time} {Level:level} {Pid:int} --- [{Thread}] {Logger:word} : {Message}"}
```

**JSON Lines и logfmt схемой больше не являются.** Время, уровень и сообщение — из формата строк файла (раздел 1); полем является любой ключ по имени. Колонки вкладки для такого файла — роли (`Timestamp`, `Level`, `Message`) плюс ключи, которые пользователь показал или привязал к правилу; список ключей для дока берётся из начала файла. Встроенные схемы «JSON Lines» и «logfmt», режим Format в редакторе и `PatternDefinition::keyed` уходят; `keyedline`, `classifyKeyed`, `timestampFromValue`, `keyValuePairs` и все тесты разбора остаются.

**Перевод старого.** `SchemaConverter::fromBlocks(PatternDefinition) → шаблон`: обёртки и разделители становятся литералами, виды блоков — видами полей, `ignored` — полем без имени, блок-константа — литералом, пользовательский регекс — `/регекс/`. Каталог переводится при первом запуске: файл версии 3 переписывается в версию 4, оригинал — в `patterns/converted-from-v3/`. Определения внутри сохранённых состояний (сессии, память файла, `Ctrl+Shift+T`) переводятся при чтении тем же конвертером; ключевая схема в состоянии читается как «схемы нет» (формат строк определится сам, свои имена ключей переходят в выбор формата). Поведение на отклоняющихся строках может отличаться от прежнего каскада — по слову автора это допустимо; встроенные схемы обязаны пройти прежние ожидания.

### 3. Источник полей: `FieldSource`

Один на вкладку, владелец — `LogModel` (как `RecordLocator`); единственный вход для всех, кому нужны поля.

```cpp
class FieldSource : public QObject {             // src/fieldsource.h, ядро
public:
    // Смена схем файлов вкладки: поколение++, кэш пуст. O(1), строки не трогаются.
    void setSchemas(FileSchemaSet schemas);
    // GUI-поток: поля строки для показа. Inline-извлекатель считает сразу (и кладёт в кэш),
    // Background — возвращает Pending и ставит строку в очередь фонового расчёта.
    FieldLookup fieldsFor(const RecordKey& key, QStringView text);
    // Воркеры: значение-снимок (shared_ptr схем + раскладка колонок); extract зовётся прямо в воркере.
    FieldScanner scanner() const;
signals:
    void fieldsReady(const QVector<RecordKey>& keys);   // модель превращает в dataChanged
};
```

- `FileSchema` (F-5) держит `shared_ptr<const FieldExtractor>` вместо `LogPattern`; раскладка колонок вкладки `FieldLayout` и перенос «колонка схемы → колонка вкладки» — как есть.
- **Кэш** — LRU на несколько тысяч строк, ключ — файл и номер строки (не номер ряда: вставки и фильтр его не портят), сбрасывается сменой поколения и сбросом строк файла.
- **View и Entry Details** зовут `fieldsFor`. `Inline`: разбор экрана — сотня вызовов по долям микросекунды, дальше попадания в кэш; состояния «ожидание» пользователь не видит вовсе.
- **Фоновый расчёт** (`Background`): одно задание на вкладку в отдельном пуле с пониженным приоритетом потока. Очередь — «последние запрошенные первыми» с отсевом: считаются строки экрана и ближайших двух экранов, прокрученные мимо выбрасываются. Текст строки задание получает значением (view его уже прочитал, чтобы нарисовать) — диск и кэш вьюпорта не трогает. Результат — `QFutureWatcher` на GUI-потоке, устаревшее поколение отбрасывается, готовые строки сливаются в один `dataChanged` не чаще раза в 30 мс; позицию и выделение держит существующий якорь view. Полных фоновых проходов по файлу «на всякий случай» нет: по всему файлу поля считают только явные операции — фильтр по полю, экспорт, поиск — они уже фоновые, с прогрессом и отменой.
- **Фильтр по полю** (оба бэкенда, воркер): `FilterRuleSet::matchesLine` получает не готовые поля, а ленивый доступ — поле извлекается один раз на строку и только если правило до него дошло:
  - *предфильтр по строке:* правило «поле содержит X» сначала ищет X во всей строке; нет — ответ известен без разбора (и для Include, и для Exclude);
  - *ранняя остановка:* `extract(line, out, upTo = старшая нужная колонка)` — для `Level` или `Thread` разбирается только начало строки;
  - регекс по полю идёт по короткому значению поля, а не по строке.
  Так фильтр по полю стоит примерно как текстовый. Синхронный резидентный фильтр (до 100 тыс. записей на GUI-потоке) остаётся только для `Inline`; с `Background`-извлекателем фильтр всегда фоновый.
- **Экспорт, Search, статистика** берут `FieldScanner` и считают в своём воркере.
- **Смена схемы:** `setSchemas` → view перерисовывает видимое; если применены правила по полю или показ выбранных полей — обычная перефильтрация и `dataChanged`. Переизвлечения, остановки читателей и reset нет.

Сверхмедленный извлекатель (секунды на пачку, сеть) в этой схеме работает для view и Entry Details как есть. Для фильтра по полю ему понадобится хранилище готовых результатов на файл и дофильтрация по мере прихода — это часть будущей задачи про такой режим; здесь закладывается только то, что нужно, чтобы она не трогала чтение и view.

### 4. Мера соответствия: `SchemaFit` (шаг 1, в работе)

Одна функция «сколько строк разбирает схема» для подбора, вывода структуры, подсказчика, дока и редактора.

- **Кандидат** — строка, начинающая запись по правилу чтения (раздел 1; время без даты — с контекстом, F-11). Если кандидатов меньше 20 % непустых строк — кандидаты все непустые строки без ведущего пробела и табуляции.
- Счётчики: `full` (сошёлся весь шаблон), `partial` (принята с остановкой), `missed`, `loose` (принята строка-не-кандидат), заполненность по колонкам, до 50 промахов с причиной данными (`MatchReport`).
- `coverage = (full + 0.5·partial) / candidates`; `specificity` — среднее число непустых полей, кроме последнего, на принятую строку. Сравнение: покрытие с шагом 0,02, затем `specificity`, затем меньше `partial`. Схема со `specificity` < 1 сама не выбирается (иначе шаблон `{Message}` побеждал бы всегда).
- Пороги: «подходит» — покрытие ≥ 0,90 и `specificity` ≥ 2; «сомнительно» — от 0,50.
- Бюджет времени на схему (150 мс) — от тяжёлого регекса.
- `SchemaFitJob` — по файлу вкладки в пуле: первые 300 строк и 2000 равномерно, текст через `LineCursor` снапшота всех строк; поколение, отмена; запускается по требованию, не на вставку строк.
- Шаг 1 пишется поверх `LogPattern`; шаг 2 переводит меру на `FieldExtractor` (меняется один адаптер и `explain`).

### 5. Нейро-подсказчик

Модель не разбирает лог: получает несколько десятков строк и возвращает **шаблон** — одну строку. Шаблон компилируется, проверяется `SchemaFit` на настоящих строках и показывается как вариант с числом. Строку-шаблон модели выдать гораздо проще и надёжнее, чем дерево блоков, а ошибку компиляции можно дословно вернуть ей на исправление.

| Модуль | Цель | Что делает |
| --- | --- | --- |
| `src/schemaproposal.*` | ядро | текст запроса, маскировка, разбор и проверка ответа, уточняющий запрос |
| `src/aischemaclient.*` | `dendrolog_app` | HTTP через `QNetworkAccessManager`, отмена, тайм-аут 180 с, повторы; провайдер — интерфейс, первая реализация — Claude API; адрес сервера — параметром (шов для тестов) |
| `src/secretstore.*` | `dendrolog_app` | ключ вне ini |

**Запрос** (Claude API, Messages; SDK для C++ нет — сырой HTTP):

```text
POST https://api.anthropic.com/v1/messages
content-type: application/json
x-api-key: <ключ пользователя>
anthropic-version: 2026-10-21
anthropic-beta: server-side-fallback-2026-07-01

{"model": "claude-opus-5-5", "max_tokens": 16000, "fallbacks": "default",
 "system": "<грамматика шаблона, правила, три примера «строки → шаблон»>",
 "messages": [{"role": "user", "content": "<строки-образцы>"}],
 "output_config": {"effort": "medium",
   "format": {"type": "json_schema", "schema": {"type": "object",
     "properties": {"template": {"type": "string"}, "comment": {"type": "string"}},
     "required": ["template", "comment"], "additionalProperties": false}}}}
```

- Модель по умолчанию — `claude-opus-5-5`, в настройках это строка. `thinking` не передаётся (у модели размышление включено всегда), глубина — `effort`, явно.
- `fallbacks: "default"`: строки журнала безопасности может отклонить классификатор — сервер сам повторит на запасной модели.
- Ответ: до чтения — `stop_reason` (`refusal` — «модель отклонила запрос», `max_tokens` — «ответ оборван»); затем первый блок `content[]` с `type == "text"` — JSON.
- 401 — «ключ не принят»; 429, 529, 5xx — до двух повторов (`retry-after`; `x-should-retry: false` запрещает); прочие 4xx — текст ошибки.
- Цена — по оценке 5–15 центов за запрос на модели по умолчанию.

**Проверка ответа** (ответ — недоверенные данные): шаблон длиннее 2000 знаков или больше 32 полей — отказ; компиляция — ошибка с позицией; `SchemaFit` на ИСХОДНЫХ строках с бюджетом времени (`/регекс/`, не уложившийся в бюджет, — отказ). Ошибка компиляции или покрытие < 0,90 — один уточняющий запрос: прежний шаблон, текст ошибки, до 10 не подошедших строк. Шаблон с `/регекс/` помечается «медленный». Ничего не применяется само.

**Согласие и приватность:** выключен по умолчанию (Settings → AI). Перед КАЖДОЙ отправкой — окно: хост, число строк и символов, точный текст; «Mask values» и «Cut lines to 300 characters» включены; галочки «больше не спрашивать» нет. Маскировка: метки времени и слова уровней целы, остальные цифры — `0`, hex от 8 знаков — `a` той же длины, почта — `user@example.com`, IP — из документационного диапазона; в окне сказано, что маскировка уменьшает, а не исключает утечку. Имя файла, пути, имя пользователя и машины не отправляются. Ключ — переменная окружения `ANTHROPIC_API_KEY` либо настройки: DPAPI на Windows, файл 0600 на Linux (в portable-режиме на Linux не сохраняется); в ini, сессиях и трассировках ключа нет. Тела запросов не логируются. При открытии файла и в фоне подсказчик не вызывается никогда.

**Где появляется** — окно подбора схемы (шаг 5), не дожидаясь нового редактора.

### 6. Вывод структуры по строкам: `SchemaInference`

До 200 строк → до трёх шаблонов-вариантов с `SchemaFit::Result`. Детерминированно, офлайн, миллисекунды.

1. Только строки-кандидаты. (JSON и logfmt сюда не доходят — они не схема.)
2. Токены с типами: метка, уровень, IP, UUID, hex, число, число с единицей, путь, строка в кавычках, группа в скобках, `key=value`, слово, серия знаков-разделителей, пробелы — теми же сканерами, что у видов шаблона.
3. Якоря — литералы из нескольких знаков (` - `, `: `, ` --- `, `]: `), стоящие в ≥ 95 % строк в одном порядке, делят строку на отрезки; отрезок с гуляющим числом слов — одно поле `text`.
4. Внутри отрезка слева направо: позиция — поле, пока ≥ 85 % строк согласны в типе; токен в 15–85 % строк — `{? … ?}`; согласие распалось — `{Message}`.
5. Имена по статистике колонки: `Timestamp`, `Level`, `Thread` (скобки, мало разных значений), `Logger` (имена через точку), `Pid` (почти постоянное число), `Id` (UUID или длинный hex, много значений), `Ip`, `Host`, `Process`; остальные — `Field1…`.
6. Варианты: полный заголовок; осторожный (до первого спорного места). Каждый компилируется и оценивается; покрытие < 0,60 — отбрасывается. Две устойчивые группы строк — заметка «в файле два вида строк».

Результат вывода — буквально последовательность литералов и полей, то есть шаблон; отдельного промежуточного представления нет.

### 7. Окно подбора, док, подбор при открытии

**Окно «Find a Schema»** (шаг 5; позже становится панелью редактора): слева варианты — лучшие схемы каталога по `SchemaFit`, варианты вывода структуры, «AI» (если включён; иначе «Ask AI… (set up)» ведёт в настройки); справа таблица образцов выбранного варианта (колонка — поле, строка — настоящая строка вкладки) и список не подошедших с причиной словами. Кнопки: **Use for This Tab**, **Save to My Schemas**.

**Док Log Fields:**

```text
Schema: [ Spring Boot · auto        ▾ ]  [Edit…]  [⋯]
Parsed 99.6% · 3 lines did not match
Show in the log:  (•) Whole line   ( ) Selected fields
   [x] Timestamp  [x] Level  [ ] Thread  [x] Logger  [x] Message
```

- Галочки «Filter blocks» и флага `FieldSettings::extraction` больше нет: поля ленивые, выбранная схема работает сразу и ничего не стоит при загрузке. Остаётся `showFields` — показ только выбранных полей. Чтение старых состояний: `showFields` = прежний `extraction`.
- Список схем показывает покрытие текущей вкладки и ставит подходящие первыми. Меню «⋯»: Detect for This Tab, Apply Schema to All Tabs, Find a Schema…, Manage Schemas…. Слова «block» в интерфейсе нет.
- У JSON-файла вместо списка схем — «JSON Lines · keys» и ключи начала файла галочками, «Add Key…».

**Подбор при открытии** (бывшая F-6, одобренный автором «профиль под тип лога»). Так как поля ленивые, подбор идёт ПОСЛЕ появления первых строк, в пуле, и открытие не задерживает; файл не перечитывается при любом размере.

1. Есть сохранённое состояние (память файла, сессия, `Ctrl+Shift+T`) — оно.
2. **Имя:** пользователь раньше выбирал схему для файла с таким именем — она, если покрытие ≥ 0,50. Ключ — имя в нижнем регистре без хвоста ротации, серии цифр заменены на `#`; таблица в ini `[SchemaByName]`, до 200 записей; запись появляется, когда пользователь сам выбирает схему в доке.
3. **Содержимое:** `SchemaFit::rank` каталога по первым строкам; лучшая — если «подходит».
4. Иначе схема по умолчанию (последняя выбранная в доке), если её покрытие ≥ 0,50; иначе без схемы и кнопка Find a Schema.

Сообщение — строка статуса «Schema: X (auto)» и пометка `auto` в доке. Выбор другой схемы или «No schema» запоминается (память файла, таблица имён) и больше не оспаривается. Настройка «Pick a field schema automatically when a log is opened», включена. Набор «схема + фильтры + подсветка» профилем не делаем: подстановка фильтров без спроса прячет строки.

- **Одно сохранение:** Apply to Tab, Save, Save As…; закрытие с правками спрашивает. Пресеты сливаются со схемами (New ▾: Empty, From Sample Lines, From Template, Import Grok… — Grok переводится в шаблон той же таблицей соответствий). Пользовательские пресеты из ini один раз переносятся в каталог.

## Производительность: бюджеты и чем они проверяются

Числа ниже — критерии приёмки шагов. Тесты проверяют счётчики (вызовы, проходы), а не секунды; секунды и наносекунды печатают режимы замера и записываются в этот документ по итогам шага.

| Что | Бюджет | Чем проверяется |
| --- | --- | --- |
| Загрузка с выбранной схемой | Равна загрузке без схемы: схема не участвует | У парсера и индексатора нет параметра схемы (шаг 7); до него — `lineindex_smoke --bench` и `--bench-resident` со схемой и без, разница в пределах шума |
| Формат строк JSON / logfmt на загрузке | Не дороже ×1,10 к `Plain` (сейчас ×1,00–1,07) | те же режимы замера |
| Разбор строки шаблоном | Не больше ×0,35 цены нынешней регексной схемы на корпусах встроенных форматов; без аллокаций на строку | `tests/line_template --bench`; счётчик аллокаций в тесте |
| Смена схемы вкладки | O(1) на GUI-потоке: ни reset, ни прохода по строкам | счётчики сигналов модели и вызовов `extract` |
| Отрисовка экрана | Вызовов `extract` на GUI-потоке не больше числа видимых строк, повторная отрисовка — 0 | счётчик в `FieldSource` |
| `Background`-извлекатель | 0 вызовов на GUI-потоке; самое долгое событие GUI-потока при прокрутке, фильтре и выборе строки, пока извлекатель заблокирован, — не больше 50 мс | подставной блокирующий извлекатель, замер как в `scrollbar_marks --bench` |
| Фильтр по полю | Не больше ×1,3 времени текстового фильтра с тем же образцом; вызовов `extract` не больше числа строк, содержащих образец (правило Contains) | счётчик в тесте; `tests/field_source --bench` на обоих бэкендах |
| Память резидентной вкладки | Меньше нынешней (нет спанов в записи) | замер RSS на файле 300 МБ до и после шага 3 |
| Подбор схемы при открытии | Не задерживает первую порцию строк; одно задание в пуле | порядок событий в `logview_lifecycle` |
| Фоновая работа | Один поток пониженного приоритета на вкладку; только видимые строки и два экрана вокруг | счётчик поставленных и отброшенных запросов |

## Проверки

- **`logstore_equivalence` — главный трос и здесь.** После шага 3 поля обоих бэкендов идут одним путём, но тест остаётся дифференциальным: правила по колонкам во всех конфигурациях обязаны дать прежние результаты. После шага 7 фикстуры JSON Lines и logfmt проверяются без схемы против тех же заданных моментов, уровней и записей.
- **Эталон — настоящие строки с заданным ответом:** корпуса `line_template`, `schema_inference`, ожидания `builtin_schemas`.
- **Счётчики вместо секунд:** бюджеты таблицы «Производительность» — вызовы `extract` по потокам, проходы загрузчиков, сигналы модели.
- **Подставной медленный извлекатель** — обязательная часть шага 6: архитектурное требование «разбор не мешает показу» закреплено тестом, а не обещанием.
- **Подсказчик без сети** — локальный сервер теста; ответ модели — таблица враждебных ответов.
- **Ожидание состояния, не времени** (P-6, P-10); новые задания — `QtConcurrent::run` + `QFutureWatcher`, прослойка TSan их знает; пул пониженного приоритета — обычный `QThreadPool`.
- **Совместимость:** каталог версии 3, состояния версии 1 с блочной и ключевой схемой, ini с `fieldFilterEnabled` — читаются; эталонные файлы `document_state` остаются в наборе.

## Риски и затронутые инварианты CLAUDE.md

- **Инвариант 4** переписывается шагом 3: «`LogEntry` неизменяем после публикации; поля — функция текста и схемы, в записи не хранятся». Новые инварианты: «чтение не знает о схеме полей» (шаг 7) и «`Background`-извлекатель не вызывается на GUI-потоке» (шаг 6).
- **Инвариант 7:** схема, показ полей и колонки остаются пер-вкладочными; формат строк — на файл.
- **Инвариант 3:** `fieldsFor` — только для видимых строк; на вставку строк поля не считаются.
- **Инвариант 10:** `dataChanged` от пришедших полей не двигает вид — закрепляется триггером в `logview_state`.
- **Границы записей меняются** у файлов, где их сегодня задаёт схема; номера записей (`RecordKey`) таких файлов после обновления другие. Закладки и память файла находят строки по номеру и отпечатку (R-1), от id записи не зависят.
- **Только что сделанное:** шаг 7 удаляет ключевой вид схемы и параметр схемы у загрузчиков (F-4, PR 4 и F-5, PR 2 — работа последних двух дней). Раскладка колонок, схема на файл и весь разбор `keyedline` остаются; уходит именно то, что привязывало схему к загрузке.
- **Мягкая деградация проще прежней** (нет re-sync): строки, которые сегодня разбираются «через дыру», будут разобраны до места расхождения. Страхуют необязательные участки и корпуса.
- **Фильтр по последнему полю** (`Message`) требует разбора всего шаблона на строках, прошедших предфильтр, — бюджет ×1,3 проверяется именно на нём.
- **Перевод каталога** необратим для пользователя только внешне: оригиналы версии 3 остаются в `converted-from-v3/`.
- **Приватность подсказчика** — раздел 5; нарушение любого пункта — дефект.
- **Объём окна:** новые окна — отдельные классы; в `mainwindow.cpp` — только открытие.
- **MSVC:** новые типы объявлять одним ключевым словом (`struct LineFormat`, `class FieldExtractor` — везде одинаково).

## Решения за автором

Если автор не возразил, принимается рекомендованный вариант.

| Вопрос | Рекомендация |
| --- | --- |
| JSON Lines и logfmt — формат строк файла, а не схема | Да: определяются сами при чтении, как кодировка; свои имена ключей — в выборе формата |
| Граница записи больше не задаётся схемой | Да; для логов без меток — автоматическое правило «ведущий уровень»; правило «по схеме» явным выбором — только если понадобится |
| Старые схемы | Переводятся в шаблоны автоматически, оригиналы сохраняются рядом; точного совпадения поведения на отклоняющихся строках не обещаем |
| Регекс в шаблоне (`/…/`) | Разрешён, такая схема считается медленной: поля во view — в фоне |
| Подбор при открытии | Подставлять молча (вид строк не меняется, загрузка не замедляется), сообщение — в строке статуса |
| Нет подходящей схемы | Схема по умолчанию — только если разбирает хотя бы половину строк; иначе без схемы |
| Провайдер подсказчика | Claude API по ключу пользователя; локальная модель (Ollama, LM Studio) — отдельным маленьким шагом после шага 5, если нужна работа без отправки строк наружу |
| Согласие на отправку | Каждый раз, с точным текстом; маскировка включена по умолчанию |

## Чего не делаем

- Режим «каждую строку разбирает модель» и хранилище его результатов — архитектура его допускает (шаг 6), сама задача отдельная.
- Модель внутри программы; анализ содержимого лога нейросетью; запросы к модели без окна согласия.
- Полный фоновый расчёт полей всего файла «заранее» и материализованную таблицу полей: фильтру хватает предфильтра и ранней остановки; вернуться, если замеры шага 3 покажут обратное.
- Несколько схем на один файл; разбор `key=value` внутри сообщения в отдельные поля.
- Вложенные необязательные участки и альтернативы в шаблоне.
- Правило начала записи по схеме (задел оставлен в разделе 1).
- Профиль «схема + фильтры + подсветка» при открытии; табличный режим строк во view (U-18); перетаскивание границы поля мышью.
