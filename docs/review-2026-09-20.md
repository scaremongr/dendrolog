# Ревизия DendroLog — 20 сентября 2026

Проверенная версия: `0.3.0`, коммит `3e35a17`. Это ревизия текущей реализации и предложение следующего этапа разработки. Исправления приложения в рамках ревизии не вносились.

**Вывод:** у проекта уже достаточно функций для полноценного просмотрщика. Следующий полезный этап — достоверный и удобный разбор инцидента: найти событие во всём документе, понять его время и окружение, сопоставить источники, сохранить результаты и вернуться к ним. Сейчас отдельные части этого сценария либо ненадёжны, либо требуют повторной ручной настройки.

**1. Что проверено**

- Прочитаны `CLAUDE.md`, README, changelog, справка, конфигурация сборки и CI; просмотрены основные пути загрузки, поиска, экспорта, фильтрации, состояния представления и сохранения настроек.
- Собраны актуальные цели `DendroLog`, `pattern_smoke`, `lineindex_smoke`, `dirscanner_smoke`, `logstore_equivalence`, `logview_state`.
- `ctest --test-dir build -C Release --output-on-failure`: **5/5 успешно, 142,76 с**. Журнал локального прогона: `build/audit-ctest.log`, подробный вывод: `build/Testing/Temporary/LastTest.log`.
- Выполнен дополнительный C++-пробник на Qt 6.8.3 с настоящими классами проекта. Исходник и результат оставлены в игнорируемом каталоге `build/audit-probe/`. Он проверяет поиск за пределами 200 000 строк, разбор времени и сравнение путей при экспорте.

**2. Сильные стороны, которые стоит сохранить**

- `LogStore` уже отделяет модель от двух способов хранения. Это хорошая основа для расширения без переписывания приложения.
- Есть полезные дифференциальные тесты хранилищ и проверки состояния представления. Их ценность существенно выше простых проверок «приложение запустилось».
- Реализованы фильтры по полям, профили, недеструктивный поиск, детали записи, таймлайн и статистика с эвристиками аномалий. Добавлять их заново в roadmap не нужно.
- Сборка, упаковка Windows/Linux и релизный workflow уже описаны. Основной следующий выигрыш находится в поведении приложения и пользовательских сценариях.

Результаты дополнительного пробника:

```text
SEARCH source_rows=200001 seeded_rows=200000 result_rows=0 direct_match_row=200000
EXPORT_PATH_GUARD blocks_case_alias=0 alias_opens=1
```

Последняя строка синтетического документа содержала единственное `AUDIT_NEEDLE`. Быстрый поиск нашёл её, модель панели результатов — нет. Таким образом, два интерфейса поиска дают разные ответы на один запрос.

Проверка временных меток на машине с локальным смещением UTC+02:00:

| Вход | Наблюдаемое поведение |
| --- | --- |
| `2026-09-20T10:00:00Z` | Принят как локальные 10:00; ошибка относительно явно указанного UTC — минус 2 часа. |
| `2026-09-20T10:00:00+02:00` | Получился тот же момент, что для предыдущей строки, хотя эти входы обозначают разные моменты. |
| `2026-09-20T10:00:00.1Z` | Дробная часть — 1 мс вместо 100 мс, дополнительно потеря зоны. |
| `2026-09-20T10:00:00.123456Z` | Детектор не распознаёт метку. |

Сравнение двух хранилищ не обнаружит общую ошибку их `LineClassifier`: нужны проверки на заранее заданный правильный результат, а не только на эквивалентность реализаций.

**4. Что из `CLAUDE.md` требует уточнения**

- В разделе тестов написано «четыре», фактически зарегистрировано пять.
- Синхронность быстрого поиска и экспорта, различие порядка одного файла между хранилищами, тяжёлая сортировка при присоединении файла и дефект wrap подтверждаются текущей реализацией.
- Формулировка «выделение и прокрутка сбрасываются на каждой порции» требует уточнения: `LogListView::setModel` уже восстанавливает запись и якорь после reset. Сам reset остаётся, поисковая подсветка очищается, восстановление может менять позицию, но утверждать полную потерю выделения на каждом батче без отдельного воспроизведения нельзя.
- В документе отсутствует ограничение Search Results первыми 200 000 строками.
- README обещает отзывчивый поиск на огромных файлах, а быстрый поиск остаётся синхронным. Обещание следует согласовать с фактическим поведением.
- Комментарий про «план (2.9)» в индексном поиске не заменяет актуальную задачу с критерием готовности.

Предлагаемый основной сценарий: «открыл несколько логов → нашёл ошибку → изучил окружение и связанные события → отметил выводы → сохранил разбор → продолжил позже».

| Возможность | Что добавляет к существующим функциям | Разумный первый объём |
| --- | --- | --- |
| Контекст найденного события | Фильтр оставляет совпадения, но соседние строки часто объясняют причину ошибки. Нужны идентичность источника, позиция/контрольные признаки записи и обработка изменившегося файла.

Корреляцию по `traceId`/`requestId` удобно развивать после фильтра из поля и схем по источникам. Коррекцию часов отдельных источников — после исправления часовых поясов. Сравнение двух прогонов и сохранённый индекс на диске имеют смысл, когда подтвердится частота соответствующих сценариев.

**6. Что улучшать в GUI**

Главный резерв — понятность состояния и доступность частых действий. По коду видно девять док-панелей и несколько отдельных механизмов поиска/фильтрации; общий косметический редизайн пока не является обязательным условием прогресса.

- Рядом с результатами явно показывать область поиска: весь документ или видимые строки, применённые ограничения, продолжается ли поиск, полон ли результат. Различать «совпадений нет» и «проверена только часть».
- Сделать общую строку активных условий с быстрым снятием каждого условия и «сбросить всё». Сейчас отдельные индикаторы уже есть — их стоит развить до читаемого объяснения текущей выборки.
- Разделить извлечение полей, отображение колонок и область поиска. Сейчас доступность фильтра по полю зависит от `Filter blocks`; скрытие колонок не должно неожиданно менять смысл запроса. Несуществующее поле после смены схемы должно быть обозначено явно, а не незаметно превращаться в поиск по всей строке (`FilterRuleSet::bindFields`/`ruleContains`).
- Вынести включение авто-дочитывания в заметный элемент со статусом. Текущий правый клик по Reload трудно обнаружить без справки.
- Для долгих операций использовать понятные отдельные состояния: что обрабатывается, прогресс, отмена, ошибка. Одна общая строка статуса и полоса не объясняют несколько параллельных загрузок и вычислений.
- Сделать понятный пустой экран: открыть файлы, сканировать каталог, недавние рабочие сессии, небольшой пример схемы.
- Предложить несколько готовых раскладок: чтение, поиск, анализ. Сохранение положения доков и сброс раскладки уже существуют.
- В индексном режиме явно отражать ограничения переноса строк. Это продуктовый вопрос: пользователь должен понимать, почему длинная строка читается через детали записи и какие действия доступны.

**7. Где оправдан рефакторинг**

`mainwindow.cpp` — 3505 строк, `LogListView.cpp` — 2797. Размер сам по себе не доказывает дефект; здесь важнее сосредоточение разных жизненных циклов в одних классах.

1. При исправлении поиска выделить управление запросом и результатами из `MainWindow`: снимок документа, фоновое выполнение, отмена, поколение запроса, публикация найденных ссылок. Использовать существующие механизмы снимков вместо копирования первых N строк в резидентную модель.
2. При исправлении экспорта выделить отдельную операцию: снимок строк и выбора полей, последовательное чтение, безопасная запись, ошибки, прогресс и отмена. Не обращаться к GUI-модели из фонового потока.
3. Для закладок и сессий определить состояние документа отдельно от виджетов: источники, фильтры, схема, позиция, находки. Это даст проверяемую сериализацию и упростит восстановление.
4. Геометрию/якоря `LogListView` выделять постепенно при исправлении wrap, сохраняя проверки поведения. Полная замена собственного view одновременно с новыми функциями резко расширит риск регрессий.
5. В CMake выделить общую библиотеку ядра для приложения и тестов: сейчас исходники ядра повторно перечисляются и компилируются в нескольких тестовых целях. Это вторичная задача после исправления поведения.

**8. Проверки, которых не хватает для следующего этапа**

- Поиск уникального совпадения после 200 000-й строки, в конце файла и в нескольких источниках; отсутствие совпадений, отмена и устаревший результат после смены документа.
- Эталонные временные метки: `Z`, положительное/отрицательное смещение, 1/2/3/6/9 знаков дробной части, время без зоны и переход суток. Неподдерживаемая точность должна обрабатываться явно.
- Экспорт: идентичность исходника, ошибка записи, отмена, соответствие фильтрам и видимым полям. Штатные тесты не покрывают путь `MainWindow::on_actionSaveAs_triggered`.
- Жизненный цикл `LogViewWidget`: дописывание многострочной записи по частям, ротация/пересоздание, переход порога размера, закрытие вкладки во время работы. Текущие тесты отдельных компонентов не заменяют проверку этой цепочки.
- После исправления wrap — обычные строгие проверки видимости и достижимости последней строки.
- Нагрузочная матрица: один файл / несколько, метки по порядку / вразнобой, редкое / частое / отсутствующее совпадение. Измерять длительность операции, память и паузы event loop отдельно. Сначала зафиксировать воспроизводимую базу на целевой машине, затем выбрать допустимые бюджеты; цель 20 ГБ ещё требует подтверждения.

| 3. Сохранённый разбор | Можно собрать находки и продолжить работу после перезапуска. | Контекст вокруг события, фильтр из выделения, закладки/заметки, рабочая сессия. | Реальный разбор нескольких файлов сохраняется и восстанавливается с корректной обработкой изменённых источников. |
| 4. Разнообразие источников | Удобно сопоставлять логи разных компонентов. | Схемы по источникам, JSONL/типизированные поля, корреляция и поправки времени по необходимости. | Проверено на конкретном наборе пользовательских форматов и расследований. |

Рекомендуемый ближайший набор задач: **безопасность экспорта → полнота Search Results → корректное время → wrap и отменяемый поиск**. После него первая крупная новая возможность — **сохраняемый разбор с закладками и контекстом**.

Не стоит одновременно начинать переписывание GUI, плагинную систему, удалённый сбор логов и AI-анализ. Эти направления можно рассматривать при появлении конкретного сценария, но сейчас их польза менее обоснована, чем исправление найденных ограничений.
